# tests/ —— 这个套件怎么跑（用之前先看这一页）

> 全量 **1484 项 / 103 个测试文件**。串行跑一遍要 **99 秒**（实测），用下面的 runner 并行跑 **12~17 秒**；
> 改一个文件通常只牵出 **100~250 项**，**3~10 秒**。

一句话规则：**改哪儿跑哪儿，别跑全量；拿不准就先 `--list` 看一眼。**

```bash
python3 scripts/dev/run_tests_for.py --changed                  # 日常：跟上一次比，只跑受影响的
python3 scripts/dev/run_tests_for.py csharp/tools/ToolExecutor.cs   # 明确知道改了什么
python3 scripts/dev/run_tests_for.py --all                      # 部署前，12~17 秒
```

## 〇、什么时候**不用**跑这些（先读这一节，别把力气花错地方）

> 2026-10-21 用户明确要求：**验证强度要和改动性质匹配。**
> 「不是最终的测试阶段（即当前还在验证的话对于变异验证不需要去做，浪费时间），
>  也不需要跑全量测试。」

### 两类改动，两套要求

| 改动性质 | 判据（自问） | 要求 |
|---|---|---|
| **探针 / 诊断代码** | 它的产出是**一条日志读数**，还是**线上行为的变化**？ | **编译通过 → 部署 → 上机取数。** 不写契约、不做变异验证、不跑全量 |
| **定案改逻辑** | 这个行为以后必须一直成立吗？搞错了会不会静默出错？ | 契约测试 + **变异验证** + 全量（或受影响子集） |

### 为什么探针不该套全套验证

探针是**用完就丢**的东西，活一轮就删：

- **它的价值全在"读到什么"**，不在"以后一直成立"。真机取到数，探针就完成使命了；
- 给它写契约 + 变异验证，投入大、收益为零 —— 下一个人（可能就是自己）上来第一件事就是把探针删掉；
- 真正需要钉死的是**定案那一版**：等探针把方向定下来，再对**真正的修复**做契约与变异验证。

**反例（值得做）**：`mutate_check_ai_action_sync.py`（22 条）。那是定案修复 ——
同步回调不走挂起通道，这条行为以后必须一直成立，而且搞错了会**静默**退回"空等 120s"。
变异验证一轮就抓出 6 条假绿，这钱花得值。

**反面教材（浪费，已删）**：10-21 给格子探针写的那套 —— 14 条变异 + 8 条契约。
探针本身写得没问题，但那 14 条变异**不可能**改变"下一次上机读到什么"；
第一轮抓出的 4 条假绿也只是断言范围问题，不是被测对象的缺陷。
**该做的是编译 + 部署 + 看日志。** 两个验证文件写完即删，留在这里的只有这条教训。

### 边界：探针也要验的是什么

只有一种情况探针需要专门核对：**读数口径可能撒谎**。
这时要验的是"这行日志能不能代表那个事实"，而且通常**一两次手动核对就够**，不必上变异框架。

> 实例（10-21，真的会骗人）：格子探针若用二参
> `WorldUnitMgr::GetUnit(point, range)`（@0x376BE20，内部 `xor r9d,r9d` 把
> `isGetHideUnit` 硬编码成 **false**），一个「在同格但被隐藏」的 NPC 会查不到 ⇒
> 日志显示「格上人数=0」⇒ 我们误判成「格子表没更新」⇒ 去做一次**根本不需要**的大改。
> 这种属于「读数会把人带沟里」，值得在写探针时就避开（这里就是改用三参版）；
> 但它不值得配一整套变异验证。

### 一句话

**探针阶段：编译 + 部署 + 上机。定案阶段：契约 + 变异 + 子集/全量。**
不要用"证据很硬"来给探针加码 —— 证据硬不硬，取决于**读数准不准**，不取决于给它写了多少测试。

## 一、为什么不能"按文件名猜"

本仓的契约测试是**按文本路径耦合**的，不是按 import：

改 `csharp/tools/ToolExecutor.cs` 会打到 `test_trade_contract` / `test_spar_choice_contract` /
`test_drama_slots_contract` / `test_unit_id_contract` 这些**名字里毫无线索**的文件 ——
它们只是从同一个 `.cs` 里抠字符串做断言。

所以"该跑哪些"这张表**不能猜**。历史上猜过一版（09-17 的 AST 静态扫描），
10-17 拿实测对拍发现它两头都错：

| | 静态猜的 | 实测真相 |
|---|---|---|
| 改 `ToolExecutor.cs` 影响 | 252 项 | **87 项** |
| 改 `agent_loop.py` 影响 | 253 项 | **1 项** |
| 漏掉的真实依赖 | — | **172 个源文件 / 346 处** |

现在的表是**实测出来的** —— 见下面"依赖快照"。

## 二、依赖快照（`scripts/dev/.depmap.json`）

一个 pytest 插件（`scripts/dev/_read_probe.py`）跑全量时把这些拦下来：

| 拦什么 | 得到什么 |
|---|---|
| `Path.read_text` / `open` / `read_bytes` | 这个用例**读了**哪些文件（契约测试抠 `.cs` 源码走这条） |
| `SourceFileLoader.get_data` | 这个测试文件**导入了**哪些模块 |
| `Path.glob` / `rglob` | 这个测试**扫描**了哪些目录的哪些模式 |
| `sys.monitoring` 的 `PY_START` | 这个用例**真的执行了**哪些模块的代码 |

前三条好理解；第四条是必需的补充 —— `tools/text_render.py` 这种**被调用**的模块，用例既不读它、
也不一定直接 import 它（是 `bridge.py` 转手 import 的）。只靠前三条实测**漏 8 条**，
而退化成"传递 import 闭包"又太粗（扇入从 190 涨到 **929**，占全量 64%，等于没筛）。

### 三条归属规则

| 怎么发生的 | 算谁的 |
|---|---|
| 用例体内显式读（`_read("tools/X.cs")`） | **那一个用例** ← 精确度主要来自这里 |
| 模块导入 | **整个测试文件**（import 只执行一次，落在哪个用例上取决于执行顺序） |
| 模块级（import 时）显式读 | **整个测试文件**（import 时就执行了，影响全文件） |

## 三、改了什么 ⇒ 会跑什么（完整规则）

改文件 `S` 时，**并集**选中：

| # | 规则 | 粒度 |
|---|---|---|
| a | 实测**读过** `S` 的用例 | 单条用例 |
| b | 实测**执行过** `S` 的代码的用例 | 单条用例 |
| c | 实测在**模块级**读过 `S`、或**直接 import** 了 `S` 的测试文件 | 整个文件 |
| d | **扫描范围覆盖** `S` 的测试文件（`rglob("*.cs")` 那种） | 整个文件 |
| e | `S` **本身就是测试文件** | 整个文件（且继续按 a~d 找别的依赖它的测试） |
| f | **快照之后被改过**的测试文件 | 整个文件（强制，与 `S` 无关） |
| g | **快照里没有**的测试文件（新增的） | 整个文件（强制，与 `S` 无关） |
| h | 含**解析不出来的动态 import** 的测试文件 | 整个文件（强制，与 `S` 无关） |

> `f`/`g` 是"**宁可多跑**"那一边：快照对它们不可信。它们由 `Selection.forced` 单列，
> `--list --explain` 能看出来"这些不是因为你改的东西才跑的"。

**没有任何测试依赖 `S`** 时，会明确打印一行告诉你（不是静默跳过）：

```
[run_tests_for] ⚠ csharp/__NobodyReadsThis.cs 没有任何测试读它、也没有测试扫描它所在的目录
                ⇒ 改它不会跑任何测试（如实报告，不是漏跑）
```

## 四、新增 / 修改 / 删除时的行为

这一节是最容易出问题的地方 —— 快照里没有的东西，静态和实测**都**不知道它依赖什么。

| 情形 | 行为 | 为什么 |
|---|---|---|
| **新增测试文件** | **整文件跑**（规则 g） | 对它一无所知：不知道它读什么、执行什么 |
| **改了已有测试文件** | 该文件**整文件跑**（规则 f） | 它的依赖可能已经变了 |
| **新增源文件** | 由**扫描范围**兜住（规则 d） | 探针记的是"读过哪些文件"，新文件上轮没读过 |
| **删除 / 重命名源文件** | `--changed` 用快照里的源文件清单**反查** | 删除的文件**没有 mtime**，`--changed` 扫不到 ⇒ 否则"改名了却全绿" |

**结论：不会漏跑，只会多跑。** 直接跑是安全的。

### 让新测试回到精确选择（几秒，别重跑全量）

```bash
python3 scripts/dev/run_tests_for.py --probe --probe-files tests/test_new_feature.py
# 也可以一次多个：--probe-files tests/a.py tests/b.py
```

它只跑这几个文件，把结果**并入**快照（其余文件原样保留），并把它们的 mtime 按磁盘现状记下 ——
于是它们立刻从"强制整文件跑"变回"精确到用例"。

实测（7.8 秒采 2 个文件）之后：

```
改 tools/zz_demo.py      → 只命中 test_greet_reads_the_module
改 ToolExecutor.cs       → 只命中 test_unrelated
改 agent/initiative.py   → 命中 0 条
```

**什么时候值得采**：看那文件大不大。十几条用例的不用管（整文件跑也就几秒）；
像 `test_room.py`（81 条 / 12.3s）这种值得采一下。

**不采也不会漏** —— 采快照是**优化**，不是必需步骤。每次 `--all` 或 `--probe` 之后，
快照本来就是最新的。

## 五、命令一览

| 命令 | 用途 |
|---|---|
| `run_tests_for.py <文件…>` | 按改动挑子集并跑 |
| `run_tests_for.py --changed` | 与上次子集运行的 mtime 基线比，自己找改动 |
| `run_tests_for.py --changed-since <文件\|时间戳>` | 与指定基线比 |
| `run_tests_for.py --only-tests <测试文件…>` | 已知测试文件，直接跑 |
| `run_tests_for.py --list <文件…>` | **只列不跑**（连子进程都不起）|
| `run_tests_for.py --list --explain <文件…>` | 逐条打印**为什么选中它** |
| `run_tests_for.py --all` | 全量（并行）|
| `run_tests_for.py --probe` | 重采**全量**快照（~2.5 分钟）|
| `run_tests_for.py --probe --probe-files <测试文件…>` | **增量**采快照（几秒）|
| `run_tests_for.py --probe --force …` | 没跑绿也照样装（破鸡生蛋用）|
| `--jobs N` | 并行度（默认 = 核数，上限 12）|
| `-- <pytest 参数>` | 透传给 pytest |

**排查"为什么跑了这些"**：

```bash
python3 scripts/dev/run_tests_for.py --list --explain tools/text_render.py
```
```
    tests/test_ability_desc_contract.py::test_abilities_empty_slots_are_skipped
        理由：test_ability_desc_contract.py import 了 tools/text_render.py
```

## 六、并行

按**文件**分片 + 按历史耗时 LPT 装箱，每片一个 pytest 子进程。

**必须按文件分**：本仓 13 个测试用**写死的** `/tmp/agent_loop_test_*` 目录，
把同一个文件的用例拆到两个进程会互相 `rmtree`。

耗时表 `scripts/dev/.test_durations.json` 每次跑完用 `--durations=0` 的真实数据更新。

**并行会让计时敏感的测试偶发失败**（实测 `test_multi_npc_turns_run_in_parallel` 靠
"两个 NPC 的回合肉眼可见地并行"断言，12 片抢 CPU 时就不稳）。所以分片红了会
**串行复跑一次**：过了就如实报成"并行争用偶发"并**明确打印**（不悄悄放过）；还是红才是真失败。
想彻底避免：`--jobs 1`（串行，99s）或 `--jobs 4`。

## 七、契约测试（`test_run_tests_for_contract.py`，23 条）

它钉的**不是"表长什么样"，而是几条可靠性属性**：

1. **不漏跑**：快照说"某用例读了/执行过 `S`" ⇒ 改 `S` 必须选中它；
2. **不许升级全量**：`ws_channel.py` 这种高扇入改动也必须留在子集里
   （旧版的 `FANIN_UPGRADE=15` 闸门正是死在这里 —— 扇入最高的 6 个文件全被打成全量，**已删除**）；
3. **`--changed` 覆盖全仓**（旧版扫不到 `agent/ transport/ room/ session/ llm/ storage/ config/ prompts/`）；
4. **新增文件也命中**：快照里没有的新 `.cs`，落在扫描范围内仍要命中；
5. **新增测试文件一律跑**（规则 g）；
6. **删除的源文件要报出来**（且不能把测试自己造的临时 fixture 误报成"源文件被删"）；
7. **增量采快照只动指定的文件**，其余原样保留；
8. **`--list` 绝不真跑**（子进程都不该起）；
9. **分片不许把同一个文件切开**。

## 八、改了这个 runner 本身怎么办

**必须跑端到端验证**（这是唯一有说服力的判据）：

```bash
python3 scripts/dev/verify_subset_soundness.py
```

它做的是：**对源文件施加变异 → 跑全量记录真红了哪些 → 问子集是否覆盖**。两个判据：

- **判据 A（实用，必须过）**：只跑子集时它自己会不会红 —— 防的是**静默放行**
  （子集绿、全量红）。这是真正要防的事。
- **判据 B（严格，最好过）**：全量新增红的每一条是否都在子集里。

跑完逐字节 md5 还原校验（有往返自检，遇到 CRLF 这类有损情况会**跳过那个文件**而不是改坏它）。

**它抓到过的真 bug**（都是这套机制自己的）：

| bug | 后果 |
|---|---|
| 相对 import 被整段跳过（`from ..tools.text_render import render`） | 变异 `text_render.py` 后全量红 48 条，**子集漏 8 条** |
| 改测试文件时只跑了它自己 | 没跑"执行了它代码"的其他测试文件 |
| 验证脚本把子集那次跑在**变异还原之后** | 恒绿、判据完全失效 |
| 探针回调里做 syscall（`Path.resolve()`） | 每函数调用一次磁盘 IO，全量**卡死在 14%** |
| pytest 遇到**不存在的 node id** 会放弃整趟 | 测试改名后整个分片"没跑"，**看起来像跑完了** |
| 耗时表写成"覆盖"而非"求和" | `test_ws_channel.py` 记成 0.04s（真实 10.5s），分片严重失衡 |

## 九、诊断：绿了但你觉得没跑对？

| 现象 | 看什么 |
|---|---|
| 只跑了几项 | `--list --explain` 看理由；确认不是"改的文件真的没人依赖" |
| 跑了整个文件 | 该文件在 `Selection.forced` 里（比快照新 / 是新增的）⇒ 增量采一下 |
| 跑了 400+ 项 | 改的是高扇入文件（`ws_channel.py` 454、`agent_loop.py`）—— import 它的测试多，属实 |
| 分片偶发红 | 串行复跑的结果会打印出来；真失败会写明"串行复跑仍红" |
| 快照可疑 | `--probe` 重采（要求全量跑绿；拿不准加 `--force`）|
