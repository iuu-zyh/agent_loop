## 一、目标与非目标

### 目标（本轮做完）
让 L1 运行时上下文与 SystemPrompt 屉子**支持多人在场**，并把"谁在说话"统一进消息文本。
**全部在 Python 侧完成，不改 C#、不改存档格式。**

1. L1 段清单**动态化**（可增可减），差分机制按"当前清单 ∪ 上一步清单"工作
2. 新增 **`present` 段**（当前在场者名单，**恒非空**，由 Python 按房间名单成文）
3. 新增 **`other:<npc_id>` 段**（每个同席者一段，轻量"可观测面"）
4. **离场清理**：段从清单消失时清三处（屉 / `_last_l1` / `_retained_ctx`）
5. 修复 `_resync_runtime_ctx_baselines` 的 O(n²) 与失效的 break 判据
6. **统一命名**：发给模型的 user 消息带 `说话人：内容`（含单聊）
7. 下游消费方适配：`compaction/compress.py` 说话人判据、`history.py` 的 peer 分支

### 非目标（本轮不做，属于 P1/P3）
- Room 编排（发言顺序、投递、轮转游标、K 上限）
- 沉默哨兵 `【沉默】` 的处理
- C# 侧 `get_context` 返回 `raw.others`（**但 Python 必须能在没有它时正常工作**）
- C# 多说话人 UI
- 动作工具的 `target` 参数

## 三、设计决策

### D1：段清单**推导**，不**维护**

不引入可变清单 + `append/pop`，而是每步从当前真实数据推导出 `segs` 字典，
再与上一步的键集合求差。离场 = `previous - current`，**自动覆盖所有离场路径**
（关窗、NPC 死亡、C# 解析失败、压缩折走），不需要在每个业务出口记得清理。

> 依据：`dialogue_agent.py:106-108` 已有的教训——硬编码段清单「漏了完全静默」。

### D2：`present` 段**恒非空**，由 Python 按房间名单成文

| 场合 | 文案 |
|---|---|
| 单聊 | `此刻并无他人在场，只有玩家与你相对。` |
| 群聊 | `此刻在场者：玩家、李四、王五（连同你共四人）。` |

**这是绕开 F5 的关键**：单聊状态也有自己的非空文案 ⇒ 进/出房间**两个方向都是内容变化** ⇒ 差分必然触发。
因此**不需要**给 `other:*` 段写"撤回"逻辑。

数据源必须是 **Python 自己一定知道的名单**（后续由 `Room.members` 提供），
**不能依赖 C#** —— 它一旦为空，F5 的 bug 就原样复现。

判据是**名单内容**（比对文本），不是**人数**：李四走、王五来，人数不变但名单变了。

### D3：`other:*` 一人一段（而非"在场"一整段）

成本对比（N 个同席者，每人变化率 r、描述 c token）：
- 一整段：段长 ≈ N·c，任一人变化即整段重发 → 长期 **O(N²)**
- 一人一段：每段长 ≈ c → 长期 **O(N)**

且转录里每次只追加一小段，压缩压力同步下降。

### D4：`other:*` 只给**可观测面**

| 给 | 不给 |
|---|---|
| 姓名、性别、种族、境界、宗门 | 气运 |
| 容貌档位、声名档位 | 近况经历 |
| 位置 / 是否同格 | 悟性、战力裸值、体魄 |
| **与我的**关系与好感 | 性格注解 |

原则：**L1 是"抬眼就能看到的"，不是"查过资料库"**。要细节请调 `inspect_unit`。

### D5：统一命名走**投影**，不改账本 ★

发消息带 `说话人：` 是**呈现层**的事，账本保持原文。理由：

| | 改账本（在 `create_user_message` 里加前缀） | **投影（本轮采用）** |
|---|---|---|
| UI 气泡 | 会显示 `玩家：你好` ✘ 需另修 `history.py` | 干净 ✔ |
| 压缩材料 | 会双重前缀（自身再拼一次 `玩家：`）✘ | 不受影响 ✔ |
| 既有 442 个测试 | 断言玩家文本的会挂 | 全部不动 ✔ |
| 账本语义 | 记的不再是玩家真输入 | 忠实记录 ✔ |
| 先例 | — | `_attach_turn_images` 已经是"发前投影"✔ |

规则（判据 = `source.kind`）：

| `source.kind` | 例子 | 加前缀？ |
|---|---|---|
| 无 | 玩家真消息 | ✔ `玩家：` |
| `peer` | 同席 NPC 的话 | ✔ `<speaker>：` |
| `initiative` | `（NPC主动传音：…）` 舞台指令 | ✘ |
| `plugin` | L1 段 / BUSY_NOTE / 初次相识 | ✘ |

格式：**`说话人：原文`，原文一字不改**（时间戳 `[1年M月] ` 留在冒号之后）。

### D6：没有 `raw.others` 时**退化为单聊**

C# 尚未改。所以 `raw.others` 缺失 ⇒ 不产生 `other:*` 段 ⇒ 行为与今天一致。
多人路径可**用假 bridge 注入 `raw.others` 完整测试**，不阻塞在 C# 上。

### D7：段顺序与 order

```
time → self → player → present → other:<id>... → recent
```
`context(order=)` 给稳定递增值（`assemble` 用 `sorted`，等值 order 的顺序依赖插入序，
而插入序会随"哪段变了"漂移）。消息顺序由循环决定，order 只为 `assemble` 确定性。

### 6.3 执行中发现的问题（计划里没写到的）

**① `_resync` 还有第二个潜伏 bug：旧值覆盖新值。**
原实现倒序扫描、**对每条命中都无条件回填**，`seen` 只用来判 break 计数。于是同一段的
**更旧**消息会把刚回填的新值盖掉。docstring 声称"每段只取最新一条"——那描述的是**意图**，
代码没做到。段清单动态化后消息条数随在场人数上升，这个洞会放大，故一并修掉（`seen` 当去重闸）。
> 回归测试：`test_t11_resync_takes_newest_per_segment_and_clears_dropped`。

**② 同席段一开始会**编造**「一介散修」。**
只看生成的文本时发现的：roster 点名了某人、但 C# 还没给明细时，`format_other_segment`
会输出「不存在的人，一介散修。」——把"不知道"写成了"知道"。
已改为：**一条实质信息都没有时整段返回 ""**（「在场」段已经声明他在场，同席段留空即可；
等明细到了内容从 "" 变实，差分自动重发）。
> 回归测试：`test_t3b_other_without_detail_does_not_fabricate`。

**③ 「你与他结着陌生之谊」是病句 —— 而且**玩家段**早就有这个问题。**
模拟脚本打出来才看见：`relation` 为 `陌生`（C# 无关系时的合法取值）时套
`你与{ta}结着{rel}之谊` 会拼出「结着陌生之谊」。
抽出 `_relation_phrase` 供**三段共用**——新建的同席段与既有的玩家段口径统一，
`陌生/无/不认识` 一律走「素不相识」。
> 既有行为（道侣/仇人）逐字不变，`test_bridge_tools.py` 的断言未动。

**④ 桥取数失败会被误判成"所有人都离场了"。**
`segs` 原本只在 try 内赋值。一旦取数抛异常，`segs` 未定义/为空 →
③-1 的 `previous − current` 会算出**全集**，把整份 L1 状态连同屉一起抹掉。
已加显式兜底：异常分支 `segs = {}`，跳过清理与发送（容器与会话状态原样保留）。
> 回归测试：`test_bridge_failure_does_not_wipe_segments`。

**⑤ 一个测试钉的是实现细节，不是不变量。**
`test_dialogue_agent_segment_dicts_not_hardcoded` 断言源码里存在
`'_segs = tuple(getattr(system_prompt, "_CTX_SEGMENTS"'`。段清单动态化后该行不复存在。
已改写为钉**新不变量**（两个基线字典空起手 + 离场清理走集合差），这比原来那条更贴近它
真正想守的东西（"段清单不许在 DialogueAgent 里写死第二份"）。

### 9.3 执行中发现的问题

**① 同席段的判空用的是"raw 里键在不在"，不是"渲染出来有没有字"。**
`title` 是 `[待真机]` 占位串、`personality` 是空 dict 时，**键都在但一个字都写不出来** →
产出「李四。」这种**空洞段** —— 正是该函数要防的"把'不知道'写成'知道'"。
已改成**先成文、再判空**（把各项算成变量，再用"有没有非空项"当判据）。
> 回归：`test_t15` / `test_t16` 末尾那两条。

**② 同席段的好感是**裸数字**，与自身段/玩家段口径不一致。**
`_intim_tier` 的 docstring 写着"避免把系统数值当台词：'好感已达200' 太像面板"，
而 `format_other_segment` **自己引用了这条教训、然后写了个 `好感87`**。
已统一走档位词（87 → 「日渐亲近」）。
> 回归：`test_t2` 现在断言 `"87" not in other`。

**③ 测试里有个经典 Python 陷阱（我写的）。**
```python
[t for t in texts if "—— 在场："]      # ✗ 非空字符串恒为真 → 匹配全部
[t for t in texts if "—— 在场：" in t] # ✓
```
漏了 `in t`，于是 `[0]` 取到的是第一条（当前时间）而不是在场段。**排查花了三轮**：
`grep`/`repr`/字节比对全显示字面量正确，最后靠"单独跑也失败、复现脚本却成功"定位到
是**测试源码本身**写错。教训：`if <literal>` 在推导式里不报错、不报警，只是**恒真**。

**④ C# 没有测试工程，真机也跑不了 ⇒ 加了一道源码级契约检查。**
`test_t17a` 从 `GameContext.BuildOthers` 正文刮出 `entry["…"]` 键名，
与 Python 消费的 17 个键**求差集**。已用**变异测试**验证它真能抓到问题
（把 `beauty_label` 改成 `beauty` → 测试立刻失败）。
它守的是本仓库**真实发生过三次**的故障模式（注释里反复写的
「C# raw 有字段 ≠ 模型看得到」：性格注解、性别、位置各一次）。
> ⚠ 正则只认 `entry["k"]` 与 entry 的初始化行 —— 裸刮 `["k"]` 会把嵌套 `point` 的
> `["x"]/["y"]` 也算进来（第一版就是这么错的，被测试当场抓到）。
