## 一、Room 是什么

### 1.1 一句话

> **Room 是一个「交谈身份」+ 一个「接力调度器」。**
> 它持有这个群**是谁、有谁、说过什么**，并按顺序把发言投递给各个 NPC 的 agent。

### 1.2 不是什么 —— 三条否定，都是踩过的

| ✘ 不是 | 为什么 |
|---|---|
| **不是地点** | 坐标不唯一（同一格上可能有好几场聚谈）；地名会撞车（同一地点先后多次聚谈）。而且「同一个酒楼里先跟甲单聊、再把乙叫过来」本来就是**两个**场合 |
| **不是另一个 agent** | 它不跑 LLM、没有 session、没有回合。它只做调度与记账 |
| **不是记忆的载体** | 模型**从不读** `Room.log`。NPC 的记忆在各自的 `session` 里 |

### 1.3 为什么必须有个 Room —— 三个消费者没人能替代它

| 消费者 | 它要的东西 | 只有 Room 能给的 |
|---|---|---|
| **群聊窗（UI 回放）** | 「这个群聊过什么」 | 玩家自己没有 session；任何成员的 session 都可能被压缩、被删、或是**后加入的** |
| **投递（增量）** | 「谁还没听到哪条」 | 需要一个**跨成员共享的发言序号**才能算增量 |
| **调度** | 「这轮该谁说话、说到第几个了」 | 轮转指针 + 本轮已发言计数，是群级状态 |

## 二、核心模型：广播 vs 经历

### 2.1 全景图

```
                      玩家（C# UI）
                            │
        ┌───────────────────┴───────────────────┐
        │ 1:1 窗                                 │ 群窗
        │ open_chat{npc_id, scene:""}            │ open_room{room_id}
        ▼                                        ▼
  project_ui_history(林婉清的 session)      project_room_history(Room.log)
  ← 只出单聊场合的回合                       ← 整个群的发言流水
        │                                        │
        ▼                                        ▼
  ┌──────────────────────┐              ┌──────────────────────┐
  │ 林婉清.session        │              │ Room.log             │
  │ 李四.session          │              │  seq/speaker/text    │
  │ 王五.session          │              │  （广播，全群一份）    │
  │  = 各自的「经历」      │              └──────────┬───────────┘
  │  收到广播 + 自己的回合  │◄──── 投递（增量）────────┘
  │  + 私域工具流量 + L1   │      把 log 里我没听过的塞进我的 inbox
  │  + 压缩纪要            │
  └──────────┬───────────┘
             │ derive_messages()
             ▼
        模型（NPC 的大脑）
        ★ 模型**从不读** Room.log
```

**两条读路径完全独立，只在「一次发言」这个写入事件上汇合。**

### 2.2 一份发言的生命周期

玩家在群里说一句，林婉清接一句，李四再接一句：

```
t0  玩家：「你们怎么看青须藤？」
    C# → Python: room_message {room_id:"g3", text:"你们怎么看青须藤？"}

    ① Room.log 追加                              ← 写入点 A（1 份）
       {seq:7, speaker:"player", text:"你们怎么看青须藤？"}

t1  调度：本轮点名 [林婉清, 李四, 王五]

    ── 轮到林婉清 ──
    ② 投递                                       ← 写入点 B（每人一份）
       delta = log 里 seq > 我的游标 且 speaker ≠ 我 → [#7]
       林婉清.inbox(next-step) += {text:"你们怎么看青须藤？"}   source=None → 玩家
    ③ 设场合（内存，不落账）
       set_scene("g3") ; set_roster(["李四","王五"])
       send("（轮到你说话了。）", source=plugin) → next-turn

    ④ 跑回合（落进林婉清**自己的** session）
       turn/start {turn:9, scene:"g3"}                    ← scene 落账
         user/message   玩家：[1年M月] 你们怎么看青须藤？    ← 从 inbox 领出
         [L1 段：在场：玩家、李四、王五 / 同席·李四 / 同席·王五]
         assistant/message  青须藤么……我听过些风声
       turn/end

    ⑤ 广播 + 推进游标
       Room.log 追加 {seq:8, speaker:"林婉清", text:"青须藤么……我听过些风声"}  ← A
       session.append("room/cursor", {"room_id":"g3", "seq":8})              ← 见 §3.3

    ── 轮到李四 ──
    ⑥ 投递 delta = [#7 玩家, #8 林婉清]
       李四.session 收到两条 user/message，
       其中 #8 带 source={"kind":"peer","speaker":"林婉清"}   ← 归属在这里
       ★ 林婉清的话**不会**投回给林婉清自己（规则：speaker ≠ 我）
    …
```

### 2.3 四条不变量

| # | 不变量 | 违反的后果 |
|---|---|---|
| **I1** | 每条 `user/message` 都住在某个 `turn/start..turn/end` 里 | 投影归属与删除跨度错位 ⇒ **假删除**（UI 说没了、模型还记得）。见 §4.2 |
| **I2** | 模型只读自己的 session；`Room.log` 永不进 prompt | 一旦混入 ⇒ 某个 NPC 会知道它没听过的事 |
| **I3** | 记忆与游标在**同一个文件**、同一次 flush | 游标超前 ⇒ 那几条发言**永久丢失** |
| **I4** | 同席发言落账存**原文**，归属走 `source` | 双重前缀「李四：李四：…」 |

## 三、数据结构

### 3.1 `Room`

```python
@dataclass
class Room:
    id: str                      # 稳定身份："g3" —— ★ 拉人踢人都不变，见 §4.8
    title: str                   # 群名（玩家可改；默认由成员生成）
    members: List[str]           # npc_id 列表，可增可删
    log: List[Utterance]         # 发言流水，只增不改
    created: int                 # 毫秒时间戳
    joined: Dict[str, int]       # npc_id → 入群时房内已说到第几条（★ 见 §4.1）
```

**刻意不放的东西**：

| 不放 | 为什么 |
|---|---|
| `cursors` | 放 agent 的 session 里（§3.3） |
| `round_pointer` / `spoken_count` | 调度状态是**运行期**的，随 Room 对象活在内存即可；落盘只落"谁在群里 + 说过什么"。挂起的轮次不值得持久化 |
| `members` 的关系/好感快照 | 那是 L1 的事（`raw.others[]`），每次取数现算 |

> `joined` 不是游标（`cursors` 仍然不放这里）：它只是**成员元数据** —— "这个人是几时进来的"，
> 与 `members` 同级。它存在的唯一理由是让「建群的初始成员」和「中途加入的新人」
> 在**都还没有游标**时可区分，见 §4.1 的 ★。

### 3.2 `Utterance`

```python
{"seq": 8, "uid": "g3#8", "speaker": "林婉清", "text": "青须藤么……", "time": 1736...}
```

实现为 `@dataclass Utterance`（上面的 dict 是它的 `to_dict()` 形态，也是落盘形态）——
用 dataclass 而不是裸 dict，是为了让 `u.speaker` / `u.seq` 有名字、拼错当场报错。

| 字段 | 说明 |
|---|---|
| `seq` | **房间内**自增序号，从 1 起。增量投递与游标都用它 |
| `uid` | `f"{room_id}#{seq}"` —— **全局唯一**。将来做"群窗删除"要靠它在各 session 里定位（见 §9.2） |
| `speaker` | `"player"` 或 `npc_id` |
| `text` | **原文**（不带 `名字：` 前缀 —— 前缀由 `_apply_speaker_labels` 在发给模型时才加） |

**`Room.log` 里放什么**：
- 玩家的发言
- NPC 的**发言正文**（回合收口后的 body）
- **公开动作**派生的第三人称事件行（如「林婉清掐指默算片刻」）

**不放什么**：只读工具的参数与返回（查询私有）、思考过程、L1 段（那是个人状态不是群内容）。

### 3.3 游标写在 **session** 里

```python
# 林婉清的 session 里多一条事件（不进 surface、UI 与模型都看不见）
session.append("room/cursor", {"room_id": "g3", "seq": 8})
```

**为什么不在 `Room.cursors` 里**：

```
存档事件：
  Room 先落盘 → 游标 = 10   ✔
  session 落盘失败/漏了 → 记忆里只有 8 条
读档后：游标说「我听到第 10 条了」，但记忆里没有 9、10
⇒ 第 9、10 条**永久丢失**（投递不会再来，因为游标说听过了）
```

放进 session 之后：**记忆与游标在同一个文件**，同一次 flush 一起落 ⇒ 不可能不一致。

**附带三个好处**：

1. 读档恢复 = 从自己的 log 折叠出最新值（跟 `request/header` 的折叠同一个套路）；
2. **「没有游标记录」= 刚入群** ⇒ 默认 = `log` 末尾（**看不到入群前的话**），语义天然正确；
3. `Room` 更瘦，`flush_all` 里 rooms 那部分只是一次全量重写。

**顺序规则（很重要）**：

```
① 先投递：agent.send(..., target="next-step")   → 落一条 agent/inbox/spliced
② 后推进：session.append("room/cursor", ...)     → 落一条 room/cursor
```

两条都 append 到**同一个 log**、走**同一次 flush**，顺序由 append 顺序保证。
反过来（先推游标）的话，"消息还在路上"这件事就没有记录，崩溃时会丢。

**这条事件对其它模块是隐形的**（已核对）：
- `SurfaceManager._apply`：`type not in SURFACE_TYPES` 且无 `surfaceOp` ⇒ 直接 `return` 忽略；
- `history.project_ui_history`：只认它关心的事件类型；
- `compress._render_transcript`：走 `derive_messages()`（surface 投影）⇒ 看不到；
- `Inbox.__init__`：只重放 `agent/inbox/spliced`。

新增一个辅助方法：

```python
# dialogue_agent.py
def cursor_for(self, room_id: str) -> Optional[int]:
    """我在这个房间投递到哪了。None = 没记录 = 刚入群 ⇒ 调用方按 log 末尾处理。"""
```

### 3.4 落盘布局

沿用现有存档命名空间（`persistence.world_root`）：

```
<storage_root>/worlds/<world_id>/
    ├── <npc_id>.jsonl          ← 已有的：每个 NPC 的 session（含 room/cursor 事件）
    └── rooms/
        ├── index.json          房间名录：room_id → {title, members, created}
        └── <room_id>.jsonl     发言流水（首行 header，其后每行一条 Utterance）
```

- `index.json` 存在的理由：**C# 要能列出"有哪些群"**（通讯录里的群列表）。否则关窗重开后无从知道 `g3` 存在。
- 形状跟 `save_session` / `load_session` 保持一致（首行 header、其后逐行 JSON）。
- **没有** `<npc_id>.jsonl` 在每个房间目录下 —— 那是旧设计的每房间每成员会话，
  已被「一个 NPC = 一个 session」取代。
- **时机**：与 agent 会话**同一次** `flush_all()` 落盘（见 §5.2）。

### 3.5 读写边界

| 数据 | 谁写 | 谁读 |
|---|---|---|
| `Room.log` | **只有编排器**（发言时 append） | 群窗投影、投递计算 |
| `Room.members` | 只有编排器（建群/加人/踢人） | 调度、投递范围、群窗标题、roster 计算 |
| `agent.session` 的 `room/cursor` | 只有编排器 | 编排器自己（投递时） |
| `agent.session` 的其余部分 | `DialogueAgent`（照旧） | 模型、1:1 窗 |
| `agent.roster` / `agent.scene` | 只有编排器 | `DialogueAgent._pre_step` / `history` 过滤 |

**★ 编排器绝不直接 append 会话内容**（除 `room/cursor` 这一条注记）——
会话内容一律通过 `agent.send(..., target="next-step")` 走 inbox，理由见 §4.2。

## 四、编排机制

### 4.1 增量投递 —— 核心规则

```python
def deliver(room, agent):
    me = agent.id
    cursor = agent.cursor_for(room.id)
    # ★ 起点：有游标用游标；没有游标时退回**入群位置**（不是 log 末尾！见下）
    start = cursor if cursor is not None else room.joined.get(me, room.last_seq)
    delta = [u for u in room.log if u.seq > start and u.speaker != me]
    for u in delta:
        agent.send(
            u["text"],
            target="next-step",     # ← 关键：回合内落面，不唤醒
            wake=False,
            source=None if u["speaker"] == "player"
                   else {"kind": "peer", "speaker": u["speaker"], "uid": u["uid"]},
        )
    if cursor is None or delta:
        agent.session.append("room/cursor", {"room_id": room.id, "seq": room.last_seq})
```

**规则一句话**：把「比我的游标新、且**不是我说的**」的发言按序投给我。

- **自己的话不投给自己** —— 它已经在自己的 `assistant` 历史里了。这也是游标可以"跳着走"的原因。
- **`uid` 存进 `source`** —— 为将来的"群窗删除"留的锚点（§9.2）。现在不加将来要改数据。

#### ★ 投递起点不能写成「没有游标就从 log 末尾起」（实现时踩到的坑）

初版本节写的是 `start = len(room.log) if cursor is None else cursor`，理由是
"`None` = 刚入群 ⇒ 看不到入群前的话"。**这条对中途加入的人是对的，对建群的初始成员是错的**：

游标是**懒写**的（要投递时才落 `room/cursor`）。于是「建群的初始成员，还没轮到过」
与「中途加入的新人」在数据上**完全一样**（都无游标），只能二选一 ——
要么初始成员永远收不到第一句，要么新人一进来就被灌入群前的全部历史。

实测症状：三人房第一次发言，`deliver` 对每个成员算出的 delta 都是**空**，
`agent/inbox/spliced` 里只有 nudge、没有增量 —— 回合照跑、日志无异常，
但**没有一个人听到玩家说了什么**。跑单测才会发现（`tests/test_room.py` R1）。

**修法**：把「入群位置」作为**房间的成员元数据**记下来（`Room.joined`，见 §3.1），
它与游标是两件事：

| | 存在哪 | 含义 | 谁写 |
|---|---|---|---|
| **游标** | agent 的 session（`room/cursor`） | 我**实际投递到**哪了 | 投递时 |
| **入群位置** | `Room.joined` | 我**进群时**房内说到哪了 | 入群那一刻 |

不变量 I3 **不受影响**：权威进度仍然只在 session 里，入群位置只回答
「一个还没有游标的人该从哪开始」；一旦投过一次，后续完全由 session 的游标说了算。
它丢了/对不上，最坏是**首次**投递起点错，不会造成「说听过了但记忆里没有」。

### 4.2 投递**必须**走 inbox 的 `next-step` ★

这是本轮设计里最重要的一条，有实测反例。

**✘ 错法**：回合外直接 `session.append("user/message", msg, {"surfaceOp": "append"})`

实测三个破口（`scripts/dev/probe_group_history.py` ①/②/③）：

| 破口 | 现象 |
|---|---|
| ① 投影/删除不一致 | 投影把游离消息算进**上一个已闭合回合**（显示 turn=1），但 turn 1 的删除跨度 `[1,14]` **不含** seq 15 ⇒ 删不掉 |
| ② 假删除 | 玩家删掉那一回合后，该条落进永不发射的 turn-0 容器 ⇒ **UI 里看着删了，`surface` 里还在** ⇒ 模型仍记得 |
| ③ 首回合前的投递静默丢弃 | `items` 只在 `turn/start` 建容器；之前的一切永不发射 |

**而且这个 bug 跑模拟看不出来** —— 实测两种形态下**模型看到的消息流一模一样**（内容与顺序全同），
坏的只有账本的记账结构。

**✔ 正确做法**：`agent.send(text, target="next-step", wake=False, source=...)`

- `Inbox.claim()` 先吃光 `next-step`、再吃一条 `next-turn` ⇒ **全部增量按序落在本回合 step 1**，
  紧跟着才是 nudge —— 正是想要的顺序；
- 消息必然住在某个回合里 ⇒ 不变量 **I1** 成立 ⇒ `history.py` / `history_ops.py` **零改动**；
- 与既有的「玩家插话 next-step」是同一条路；
- 没轮到发言的旁听者：增量留在筐里，**账本不涨**（省钱）；读档靠 `agent/inbox/spliced` 恢复。

**反例留存**：`probe_group_history.py` 不会因为代码演进"自动变绿" —— 它是给未来想改回回合外 append 的人看的。

### 4.3 `scene` / `roster` / `members` 三者的分工 ★

**三个不同的东西，不要塞进一个字段。**

| | 放哪 | 会变吗 | 用途 |
|---|---|---|---|
| **这是单聊还是某个群** | `agent.scene`（`""` = 单聊；其它 = 群 id）→ 落 `turn/start` | **不变**（群 id 稳定） | UI 回放过滤 |
| **这个群有谁** | `Room.members` | 会变（加人/踢人） | 调度、投递范围、群窗标题 |
| **此刻在场有谁** | `agent.roster` | 每步/每回合变 | L1 的「在场」「同席·X」段 |

**为什么 `scene` 不能从 `roster` 派生**（我提过、被推翻）：

微信群可以随便拉人踢人而记录不断，靠的是**群有一个稳定 id**，成员只是它的属性。
若 `scene = f(roster)`，一拉人 key 就变 ⇒ 历史在 UI 上断成两段、老段**没有任何窗口入口**（孤儿）。

⇒ **`scene` 必须是独立的稳定字段，`set_scene` 必须保留。**

**编排层的义务**：进群 `set_scene(room.id)`、**离群必须 `set_scene("")`**。
漏了的话之后的单聊回合都带着群标签 ⇒ 在 1:1 窗里凭空消失，而且**是静默的**
（回合照跑、模型照看，只有 UI 少东西）。防线：把两侧设置收进 `Room.enter()` / `Room.leave()`，
**`set_scene("")` 只有一个调用点**。

### 4.4 发言顺序：接力调度

**已定的策略**：全员轮流 + 可弃权 + 每轮上限 K + 轮转指针。

```python
def plan_round(room, speak_first: list[str] = (), k: int = 3) -> list[str]:
    """本轮依次点名的候选名单。

    - 起点：`speak_first`（玩家在 UI 上点名的人）优先，其余按**轮转指针**顺序补齐；
    - 每轮"实际说了话"的人不超过 k 个；有人弃权就继续点下一个补位；
    - 候选名单最多列 len(members) 个（全员都被点过一次就结束本轮）。
    """
```

**轮转指针**：指向本轮**最后一个实际发言者**的下一位。下一轮从那里继续 —— 保证不会永远从同一个人开始。

**K 的作用**：N 大时（比如 8 人）不必每轮都跑 8 个回合。K=3 意味着"这一轮最多 3 个人开口"。

**玩家点名**：P1 **不做**文本里的名字识别（脆弱）。由 C# 在 UI 上传 `speak_first`（玩家点了谁的头像就谁先说）。

**玩家插话不打断本轮**：玩家的 `room_message` 只 append 到 `Room.log`；本轮跑完再开新一轮。

**成本**：只有被点名的人跑回合 ⇒ **沉默的旁听者零成本**（不建回合、不调 LLM）。✔

**调度器要可插拔**（留给将来"启发式选人"）：

```python
class SpeakerOrder(Protocol):
    def order(self, room: Room, kicker: str, k: int) -> list[str]: ...
```

### 4.5 沉默哨兵与弃权

被点名 ≠ 非说不可。约定：模型回 `【沉默】` 或空 ⇒ 本回合弃权。

> ⚠ 光有常量是死代码 —— 模型不知道有这个选项就永远不会回它。
> 落地需要**两件事一起做**，缺一不可：
> ① `room_flow.py` 里定义 `SILENT_SENTINEL = "【沉默】"` 并做判定；
> ② **把"可以回【沉默】弃权"讲到模型看得见的地方**。
>
> ★ 实现时选了 **nudge 正文**而不是等 P2 的规则段，理由有三条：
> ① 弃权路径在 P1a 就活着（不必等 P2，R3 也才测得动）；
> ② 「不要写名字前缀」在这里讲最有效 —— 模型刚看完一串 `李四：…` 的转述，
>    正处在最容易模仿那个格式的位置；
> ③ nudge 天然是 per-turn、挂在对话尾部的，**不扰动上游前缀缓存**（工具表与 system 恒定，
>    见 README 附录二 G.5）。P2 的规则段是它的加强版，不是替代。
>
> 实际文案（`room_flow.NUDGE_TEXT`）：
> `（轮到你说话了。只说你自己想说的话，不要写名字前缀，也不要替别人说话。若你此刻无话可说，只回【沉默】。）`

判定是**精确匹配**（外加几个带标点的写法），**不做模糊匹配**——
把真实短回复误判成沉默，比漏判一次沉默严重得多。判据见 `room_flow.is_silent`。

```
跑完回合后：
  若 body 去掉空白 == "" 或 body == SILENT_SENTINEL：
      ① 不写 Room.log 正文、不广播气泡
      ② **游标照常推进**（他真的看到了那些话）
      ③ Room 内部记一条 silent 计数（供调度判断本轮是否已够 K 人开口）
```

★ ② 很重要：弃权 ≠ 没听见。游标推进的逻辑与"说了话"完全相同（都在投递时统一推）。

### 4.6 私有查询 / 公开动作

设计原则（沿用 `docs/archive/2026-09-17-群聊编排/设计草案.md`）：

| 类别 | 工具 | 在房间里的表现 |
|---|---|---|
| **查询类** | `inspect_unit` / `search_units` / `query_world`（= `READONLY_TOOLS`） | **私有** —— 结果只进调用者自己的上下文，别的成员看不到 |
| **动作类** | 其余 6 个 | **公开** —— 除执行外，**派生一条第三人称事件行**广播进 `Room.log` |

**为什么查询必须私有**：① 多人共享一份 `tool-call`/`tool-result` 会破坏 session 的配对不变量
（`pairing_balanced` 会判不合法）；② 会教模型在该查的时候模仿别人发 `tool-call`。

**公开动作的事件行**由一张**白名单表**决定措辞（`(tool, op) → 第三人称模板`）；
**表外的组合默认静默**（宁可不说，也不要编错）。

> `tools/room_narrate.py` 已建（09-22），目前**只落了 `world_ai_action(spar)` 一条**：
> 切磋应战之后要占掉一整场战斗的时间（`_run_round` 持 `room_lock` 串行跑成员），
> 全群一个字都不知道只会以为这一轮卡死了。其余动作类的第三人称模板**仍是待办**，
> 加一条写一条，别一次铺开 —— 措辞表外的组合按上面的规矩**默认静默**。
>
> ★ 切磋这一条还钉住一个边界：**"结果全局可见"只能走发言行，不能共享 `tool/result`**。
> 成员的 tool 结果必须与他看到的 `tool_call` 成对（同一 `tool_call_id`），把别人的结果插进
> 他的消息流就是孤儿 tool 消息，OpenAI/Anthropic 网关直接拒（`pairing_balanced` 也判不合法）。
>
> ★★ 而且这条发言行是**旁白**：进 `Room.log`（成员照常经 `deliver` 读到），进群窗，
> 但**画成「行动记录」行、不画气泡**（`_say_and_emit(narration=True)` 的帧带 `narration:true`
> → `ApplyRoomSay` 转 `AppendActionRow`；重开窗走 `project_room_history` 的 `tool_result` 条目，
> 所以**重开窗也还在**）★★ —— 09-22 用户拍板："不该以 NPC 气泡发，要以工具返回结果形式显示"。
> 实机表现正是如此：那行被画成发起人的气泡，而旁白里还引用了**玩家的原话**
> （`唐炎：「厉害，我输了。」` 出现在姜萌的泡里），挂谁名下都不对。
> 玩家侧不丢信息：那次工具调用与它的结果本来就在「行动记录」里（群聊的 `step` 帧带
> `room_id`，`tool_call`/`tool_result` 两行照常渲染）。
> **两类行别混**：提案 / 应下 / 解除那几条叙述行仍走气泡（那是"当众做的事"，
> 落在发起人名下是刻意的）；旁白走这条新岔路。加新措辞时先想清楚属于哪一类。

### 4.7 nudge（催话）

被点名后，编排器发一条**不进 `Room.log`** 的促发消息：

```python
agent.send("（轮到你说话了。）", source={"kind": "plugin", "plugin": "@python-harness/group"})
#      → 默认 target="next-turn"，与增量（next-step）区分开
```

- `source.kind == "plugin"` ⇒ 模型可见（`surfaceOp=append`）、**UI 不可见**（`history.py` 滤除）、
  压缩材料里被入口拦掉；
- 与增量（next-step）分开投递通道，顺序由 `claim()` 保证：**增量在前、nudge 在后**。

> 待定（P1 可调）：现在模型看到的顺序是 `[增量…, nudge, L1 段…]`。
> 读起来更顺的是 `[增量…, L1 段…, nudge]`（先看状态再被催话）。
> 属编排层排布，不影响正确性。

### 4.8 生命周期

| 动作 | `Room.id` | `members` | `log` | 各成员的 `scene`/`roster` | 游标 |
|---|---|---|---|---|---|
| **建群** | 新建（Python 生成） | 初始成员 | 空 | 进群者 `enter()` | 全部 = 0（会收到全部） |
| **加人** | **不变** | `append` | 不变 | 新人 `enter()` | 新人 = **log 末尾**（看不到入群前的话） |
| **踢人** | **不变** | `remove` | 不变 | 被踢者 `leave()` | 保留（他确实听过那些话） |
| **关窗** | 不变 | 不变 | 不变 | 全员 `leave()` | 落盘保留 |
| **重开** | 同一个 id（从 `index.json` 加载） | 恢复 | 恢复 | 重新 `enter()` | 从 session 折叠恢复 |
| **散场** | 不变 | 不变 | 不变 | 全员 `leave()` | 落盘保留 |

```python
# ★ 这两个方法在**编排器**（room_flow.RoomFlow）上，不在 Room 上 ——
#   Room 不持有 agent（§3.1），所以它没法自己调 agent.set_scene。
#   本节初稿把 enter/leave 画在 Room 里，与 §3.1 自相矛盾，已按实现改正。

class RoomFlow:
    def enter(self, agent, room):
        agent.set_scene(room.id)
        agent.set_roster(room.roster_for(agent.id))

    def leave(self, agent):
        agent.set_scene("")            # ★ 唯一调用点（单聊路径另有一道，见 §4.3）
        agent.set_roster([])

    def add_member(self, room_id, npc_id):
        room = self._require(room_id)
        room.add_member(npc_id, joined_at=room.last_seq)   # ★ 入群位置，见 §4.1
        for m in [npc_id]: self.leave_if_live(m)

    def kick(self, room_id, npc_id):
        room.kick(npc_id)
        self.leave_if_live(npc_id)     # 被踢者若正带群标签，必须复位
```

### ★ `enter` / `leave` 的作用域是「回合」，不是「在群里」

本节初稿写的是"建群 → 进群者 enter()、关窗 → 全员 leave()"。**那是错的**，两个原因：

1. **一个 NPC 可以同时属于多个群**（它确实都经历过），而 `scene` 是**单个字段** ——
   "进群设、关窗复位"会让两个群互相覆盖；
2. 更要命的是**静默故障**：玩家在群里开会时打开某个成员的 1:1 窗发一句话，
   那个单聊回合会带着群标签 ⇒ 在 1:1 窗里**凭空消失**（回合照跑、模型照看，只有 UI 少东西）。

**实现的写法**：`scene`/`roster` 由**回合驱动**声明并复位 ——
`ChatHub._run_turn(scene=..., roster=...)` 在拿到 agent 锁之后设、在 `finally` 里复位；
单聊路径不传 ⇒ 默认 `scene=""`/`roster=[]`。于是

- 群聊回合：`RoomFlow` 传 `room.id` + `room.roster_for(me)`；
- 单聊回合：默认 `""` / `[]`，与改动前逐字节相同；
- **`set_scene("")` 有两个调用点**（`_run_turn` 的 finally、`RoomFlow.leave`），
  互为防线 —— 任何调用顺序下都不可能把群标签漏在单聊回合上。

代价只有一处、且可接受：同一 NPC 在两个群之间来回时，`other:*` 段会来回增删一次
（它的情况**确实**变了，本来就该重发）。同群内的连续回合**不会**重发 ——
差分基准是屉（`_last_l1`），而复位 `roster` 不经过 `_pre_step`，不动屉。

### 成员变动后**不**刷他人 roster

初稿写的是"加人/踢人后遍历所有在场者重设 roster"。既然 roster 的作用域已经是回合，
这条就**冗余了**：下个回合开跑前会按最新 `members` 现算，L1「在场」段的差分自然触发。

真正剩下的义务只有一条：**被踢/退场的人如果身上还带着群标签，要复位**（`leave`）。

## 五、一致性

### 5.1 两边"不一致"的场景 —— 都应该是这样

| 场景 | `Room.log` | 该 NPC 的 `session` | 判定 |
|---|---|---|---|
| **压缩** | 不变 | 群聊段折成纪要 | ✔ 房间记录是**事实**，个人记忆**本该有损** |
| **1:1 窗删回合** | 不变 | 单聊段被删 | ✔ 删除是**个人记忆**操作 |
| **加人** | 不变（id 也不变） | 新人只有入群后的 | ✔ 与微信一致 |
| **踢人** | 不变 | 被踢者停在那一刻 | ✔ |
| **NPC 死亡** | 不变 | 保留（历史） | ✔ |
| **存档** | 落盘 | 落盘 | ⚠ 必须**同一次 `flush_all()`** |
| **群窗删一条** | 墓标（投影与投递都跳过） | 精确剔除（`drop_seqs`；折进纪要的除外） | ✔ **两边同时删**（§9.2 定稿） |

**一句话记住分工**：

> `Room.log` 回答「**当时到底说了什么**」—— 客观、不可变、全群一份。
> `session` 回答「**这个 NPC 现在记得什么**」—— 主观、会被压缩和删除、每人一份。

### 5.2 落盘一致性

**规则**：`Room` 与所有 agent 会话在**同一次存档事件里**落盘。

```python
# agent_loop.flush_all() 现在只刷 agent；加上 rooms
def flush_all(self):
    ...
    for a in agents:
        if a.session.log:
            save_session(a.session, self.sessions_root)
    for r in self.rooms.values():
        if r.log:
            save_room(r, self.rooms_root)      # index.json + <id>.jsonl
```

理由：房间流水与成员记忆是**同一次经历的两面**。只落一边会造成
「群窗有、NPC 不知道」或「NPC 知道、群窗没有」。两者一起落，语义上就是
"存档 = 这个世界的完整快照"。

**崩溃语义**：账本本来就是内存的，崩溃即丢（现有语义就是"随存档固化"）。
两边一起丢 ⇒ 仍然一致。

**读档**：`discard_all()`（`load_happened` 触发）里也要清 `self.rooms`，与 agent 舱同时丢。

### 5.3 加锁顺序

现有：`handle_message` 走 `_turn_slots`（全局并发闸）→ `_lock_for(npc_id)`（该 NPC 串行）。

编排层新增一个**房间锁**：

```
room_lock  →  turn_slot  →  agent_lock
```

- 编排器持有 `room_lock` 跨整轮（防两轮交错投递）；
- **每个发言者各自取 `turn_slot` + `agent_lock`**（不整轮霸占并发闸 ⇒ 其他 NPC 的单聊能插进来）；
- `(turn_slot, agent_lock)` 的相对顺序与 `handle_message` 一致 ⇒ **无环、无死锁**。

**单聊与群聊的关系**：`handle_message` 不取 `room_lock`，所以玩家在群里开会时
仍可打开某个成员的单聊窗。此时消息走 `next-step`，会在该成员**当前回合的下一步**被领走
—— 与既有的「玩家插话」同一条路。**是否可以接受属产品决定**（§9.4）。

### ★ `room_message` 是**事件**，不是 RPC（本节初稿归类错了）

初稿把"玩家在群里说一句"列在 RPC 下面，但既有架构里**「玩家说了一句话」一律是事件**：

| 方向 | 形态 | 例子 |
|---|---|---|
| C# → Python，「发生了一件事」 | **event** | `player_message` / `npc_initiative` / `compact` / **`room_message`** / **`room_skip`** |
| C# → Python，「问一次答一次」 | **request** | `open_chat` / `get_history` / `open_room` / `list_rooms` |

理由不是洁癖：事件是**不等回执**的，结果通过 `text_delta` / `room_say` 流式回推；
而一轮接力含最多 K 个完整回合（每个都调 LLM），若走 request，发送方就得等整轮，
接收循环还会被堵死（连"玩家插话"都进不来）。

```jsonc
// 玩家在群里发言（触发一轮接力；立即返回，接力在后台跑）
{"event":"room_message", "room_id":"g3", "text":"…", "speak_first":["王五"]}

// 玩家按了群窗的「跳过」（09-17）：这一轮他**不置一词**，NPC 按轮转自己接下去
{"event":"room_skip", "room_id":"g3"}
```

### 6.1.1 跳过（09-17）：触发轮次的方式有两种，**轮次本身只有一条实现**

「一轮必须以玩家开口开始」这句产品约束，在代码里**从来没有对应的断言** ——
它只体现为一个事实：没有任何生产调用点调 `RoomFlow._run_round`。
`run_message` 把「玩家那句话」放在 `_run_round` **之前、`room_lock` 之外**落账，
所以"玩家开口"与"一轮"在代码里本来就是解耦的。跳过因此是一次**接线**，不是新机制：

| | 玩家发言（`room_message`） | 跳过（`room_skip`） |
|---|---|---|
| 入口 | `ChatHub.handle_room_message` → `run_message` | `ChatHub.handle_room_skip` → `run_round` |
| 玩家落账 | `_say_and_emit(PLAYER, text)`（写 `Room.log` + 回声帧） | **无**（玩家确实什么都没说） |
| 轮次实现 | `_run_round`（同一把 `room_lock`） | 同左 |
| 催话文案 | `NUDGE_TEXT` | `NUDGE_TEXT_SKIP` |
| 全员沉默时的终帧 `text` | 空（屏幕上至少有玩家那条气泡，"空"不等于"坏"） | `SILENT_ROUND_NOTE`（**必须给一句**：玩家一条气泡都没发，全空 = 与"按钮坏了"无法区分） |

两条入口的差异**只有上表最后两行**，它们在两个调用点上各自**显式写全**（`_run_round`
的这两个形参刻意不给缺省值）—— 摆成缺省值就等于把差异藏进函数体，下一个读调用点的人
看不出这两条路哪里不一样。

**跳过为什么需要自己的催话文案**（这不是措辞洁癖）：跳过那一轮**没有任何新投递**
（`deliver` 按 `seq > cursor` 取增量，而游标在每人上一次被点名时就推到了当时的 `last_seq`）。
⚠ 但要说准：**前情一直都在** —— 上一轮投给他的那些话已经 `append` 进他的 surface，
`derive_messages()` 每回合把整份 surface 交给模型。所以空的是"本轮增量"，**不是上下文**。
真正的风险是另外两条：① 他上一条自己的回复往往就是【沉默】（上一轮弃权才轮得到跳过），
紧接着又被问一次 ⇒ 模型有很强的动机**保持一致**；② 原句没说"玩家这一轮不会开口"，
于是一个刚答完玩家的 NPC 完全有理由认为**该等玩家接话** —— 等的人正是按下跳过的人。
用户对这个功能的原话定义就是这句文案该说的话：**「跳过 = 广播一句玩家没插话」**。

**那句话为什么走 plugin 消息、而不写进 `Room.log`**：
① `Room.log` 只装 `Utterance`（`room.py` 的 `log: List[Utterance]`，`say()` 是唯一写入口），
写进去只能是**一条玩家发言**，等于把话塞进玩家嘴里；
② 它会以 `kind="room", speaker="player"` 投给每个成员 ⇒ 在 NPC 的历史里渲染成一条
**玩家气泡**（他"记得"玩家说过「（玩家没有插话）」），群窗历史上也留一行；
③ 要放非发言事件得改数据模型（seq 分配 / `delta_for` / 群窗投影 / 按 uid 删除 / 落盘格式）。
广播的**对象**没有丢：nudge 是 per-turn 注入的，**每个被点名的成员都会收到这一句**。
玩家可见的那点痕迹由 C# 在点击处本地落一行系统提示（「（你没有插话，他们继续。）」——
即时、不落盘、不进任何 NPC 的记忆）。

**跳过的轮次语义与玩家发言轮完全一致**（因为它就是同一个 `_run_round`）：
`_round_no` 照常 +1 ⇒ **提案 TTL 会因跳过而推进**（这是对的：`pending_first` 与
`speak_first` 无关，跳过那一轮里对手方照样被优先点名）；`_pointer` 照常推进到
"最后一个实际发言者的下一位"；`k` 上限、弃权、成员级异常、解散途中收尾全部照旧。

**失败也必须回终帧**：`handle_room_skip` 的两条 except（群不存在 / 轮次异常）都走
`ChatHub._fail_room_round`（`phase="end"` + `error=True` + 人话原因）。C# 是"点击就置忙、
等终帧复位"的，漏帧 = 群窗一直显示"正在输入"（最长 240s 看门狗才自愈）。这条规约从
`handle_room_message` 的四个 except 里抽成了一个方法 —— 抄本超过两份必然在第三次改动时漂移。

**C# 侧**：按钮是 `BG/Input/SkipBtn`（发送键正上方 8px、同列同尺寸、出厂隐藏、
只在群聊点亮），补丁脚本 `scripts/dev/prefab_patch_chat_skip_button.py`（888 号段）。
两道额外守卫：① 忙态点击**拒绝**并给一行提示（与发送键**故意不同**：发送的排队是玩家插话、
有价值；跳过的排队只是再烧一整轮 LLM）；② 0 成员的群直接拒绝（`plan_round([])` 必然空转）。
点击**先落本地系统提示再发请求** —— 跳过这一轮玩家没有气泡上屏，这行提示是"我确实按到了"的
即时凭据。

### ★ 必须有「回合终帧」—— 初稿漏了，实现时踩到

初稿只列了 `room_say` 与一个语义含糊的 `room_state`（`speaking`/`round`）。两个问题：

**① 全员弃权 ⇒ C# 群窗永远卡在"正在输入"。**
弃权不写流水、不广播（§4.5），所以一轮里如果所有人都回 `【沉默】`，
C# **一条 `room_say` 都收不到** ⇒ 没有任何"这轮结束了"的信号 ⇒ 忙碌态挂着不放。
修法：`room_state(phase="end")` 是本轮**唯一的终止依据**，且实现上放在
`finally` 里**无条件发**（异常、全员弃权、`k` 用尽都发）。

**② `room_say` 与 `text_delta` 会画出两个气泡。**
单聊里流式正文走 `text_delta`、收尾走 `npc_reply`；群聊照搬这个分工，
于是 C# 的契约必须是：

| 收到 | 语义 |
|---|---|
| `text_delta{npc_id, room_id, part:"body"}` | 流式半截，贴进**该成员正在生成的那个气泡**（气泡由它**惰性创建**，见 09-17 的 C2） |
| `room_say{speaker≠player}` | 该成员的**最终正文** ⇒ **定稿/替换**那个气泡，**不是新气泡**（等价于单聊的 `npc_reply`） |
| `room_say{speaker=player}` | 玩家这句的**回声**。发送方本地已经显示过 ⇒ 按 **`uid`** 去重（★ 本地那条**没有 uid**，所以另配一份"待销账"表按文本对号，见下） |
| `room_state{phase="speak"}` | **点名广播**：记下"现在是谁在说"（忙碌态 + 逐行归属 + 忙标日志理由）。★ **09-17 起不预开气泡**；若上一条泡只有开头没正文，先撤掉它（兜底） |
| `room_state{phase="silent"}` | **该成员弃权**（09-17 新增）：撤掉可能存在的泡；**不复位忙碌态**（轮还在跑） |
| `room_state{phase="error"}` | **该成员这一轮出错**（09-17 新增）：撤空气泡 / 定稿半截正文 + 用 `text` 显示一行系统提示；**不复位忙碌态** |
| `room_state{phase="end"}` | **复位忙碌态**（唯一依据）；若活跃泡只有开头没正文 ⇒ 撤掉它；`text` 非空时补一行系统提示。★ 09-17 起 `text` 多了一种来源：**跳过那一轮全员弃权**（`SILENT_ROUND_NOTE`）—— 那一轮玩家没有气泡上屏，不给一句解释就与"按钮坏了"无法区分（§6.1.1） |

> ★ **`stats_update` 在群聊里必须带 `room_id`**（09-18 修）：群窗唯一准入判据是
> `AcceptsRoomFrame(room_id)`，而这个帧原先漏了它 ⇒ 被整帧丢掉 ⇒ 群窗底部统计行停在
> 预制体默认文本（用户截图那个 `None`）。现在它带 `room_id` + **本群口径** `roomUsage`
> （本群期间累计花费：总/输入/输出/缓存率/本群轮步；**不含各自的上下文与占用率** ——
> 每人一份账本，没有可加语义）。开群回执（`open_room`）同样回一份，供首屏立即刷新。
> 口径与取差位置见 `docs/reference/csharp-iron-laws.md` 2026-09-18-群聊统计行口径.md。

> ★ **弃权必须显式发一帧 `phase="silent"`**（09-17 复核发现的第三个静默故障）：
> 当时 `speak` 一到 C# 就开一条泡写上「甲：」，而弃权**不写群流水** ⇒ 永远等不到 `room_say`
> 去定稿它 ⇒ 屏幕上永久留着「甲：」；模型照提示回【沉默】时，哨兵文本还会被流式打进
> 气泡，屏幕上就是「甲：【沉默】」。旧 DLL 不认识这个 phase（`switch` 落空）⇒ 行为与
> 改动前逐字相同，所以是**加法**；`end` 与下一个 `speak` 各留一道"撤空气泡"的兜底，
> 覆盖"这一帧丢了"的情形。
> ★ 09-17 稍后（C2）起 `speak` **不再预开气泡**（正文到了才起泡），所以这条 silent 帧现在
> 主要是"撤掉流式期间已经开出来的那条泡"（哨兵被流进气泡的情形），逻辑一字不改。
>
> ★ **成员级异常也必须显式发一帧 `phase="error"`**（09-17 实机事故后补，第四个静默故障）：
> 异常分支原本**一个帧都不发**。实机（`agent_loop.log` 16:17:33）：姜萌的流式请求被
> **45s 挂钟硬顶**砍断（思考流已推 382 token）⇒ `room_flow._run_round` 里 `log.exception`
> （★ 09-18 起那道"整趟挂钟"已经**删掉**：换成首字/停顿两条存活看门狗，长回复不再被按秒
> 砍断；这一帧的文案也跟着分型成「模型一直没开口（首字超时）」/「模型说到一半卡住了」。
> 见 `docs/reference/csharp-iron-laws.md` docs/features/brain-liveness.md §4 与 2026-09-17-超时语义双身份.md ★）
> + `continue` ⇒ C# 那边：那条空气泡一直挂着、忙碌态不复位，直到**下一个成员的 `speak`**
> 顺手把泡撤掉（用户原话："她的气泡过了一会自己消失了，然后另一个人开始说话"），
> 而玩家**完全不知道她为什么没开口**。现在：异常当场发 `phase="error"`（`text` 给**人话**
> 归因，traceback 只进日志）+ C# 撤泡/定稿 + 一行系统提示「姜萌 这次没能开口：模型超时…，
> 本轮跳过」；**全员都没开口**时终帧 `end` 的 `text` 再汇总一次（单成员的解释不重复说）。
> ★ 与 `silent` 分开是**故意的**：弃权是模型的选择（正常结果），出错是我们的故障 ——
> 混成一个 phase 会让"她不想说"和"她卡死了"在屏幕上长得一模一样。
>
> ★ **玩家回声的销账**（同日复核）：本地那条泡是**同步**画出来的，而 uid 要等 Python 回帧
> 才知道 —— `SendRoomMessage` 是 fire-and-forget 的 event，回执里拿不到 uid，所以
> `_roomEchoSeen` 里**永远不会有本地这条** ⇒ 每条群消息都会画两遍。修法：发送时把文本压进

#### 6.2.1 群窗只显示两条过程线索（09-17 用户拍板）

**群聊里「系统组装」「运行时上下文」两块折叠不再渲染**（`ChatPresenter.OnStepEvent` 里
按 `IsRoomMode` 早退），只留：

| 保留 | 为什么 |
|---|---|
| 「内心思量」（`think`） | 是他"正在想什么"，与文本流一起构成可读的过程 |
| 「行动记录」（`tool_call`/`tool_result`） | 是他在群里做了什么（提案闸门、赠礼、切磋…），必须可见 |
| ~~「系统组装」/「运行时上下文」~~ | 多聊时**每个成员各来一套**，一屏大半是这些块（用户原话"不美观，没有必要"）。它们本来就**只实时不重放**（不进历史回放），所以群聊里去掉不产生任何缺口 |

★ 两条**接线铁律**（改这块之前先读）：

1. **帧照发、只是 C# 不画**。`dialogue_agent` 里 `step(sys)` / `step(ctx)` 的 `_emit_step`
   **不许删** —— `ChatPresenter.OnStepEvent` 收到后仍要 `NoteTurn(turn)`（回合号是
   `step(text)` 与 `room_say` 的**气泡去重判据**），只是不再 `AppendInputParts`。
   把发送端删掉 = 群聊里同一段正文会成两次泡（`NoteTurn` 在群聊路径上失去来源）。
   `NoteTurn` 必须排在 `IsRoomMode` 早退**之前**，这条有契约测试与变异条目钉着。
2. **单聊一个字都不许变**：早退判据是 `_window.IsRoomMode`，单聊照旧逐段差分显示。

**同一轮的两件配套**（气泡为什么不再"点名即开"）：

| 改动 | 症状 → 修法 |
|---|---|
| **点名不再预开气泡**（C2） | 旧写法 `speak` 就 `BeginNpcBubble(who + "：")` ⇒ 模型思考三四十秒期间挂一条空气泡；一旦弃权/出错，它还要等下一个人的 `speak` 才被撤掉（"气泡自己消失了"）。现在**正文到了才起泡**：流式走 `ApplyDelta`、整段正文走 `ApplyStep(step/text)`，两条路都带「名字：」前缀 + 精确 unitID |
| **折叠标题带说话人**（B） | 气泡不再预开 ⇒ 思考期间"谁在说"没了线索。故群聊折叠标题拼上说话人：`姜萌 · 内心思量 · 850 字`、`姜萌 · 行动记录 (3)`（`ChatWindow.SpeakerLabel`；单聊恒为原标签）。同时解决"成员出错/弃权后，剩下的 `内心思量 · 850 字` 是一段无主内容"（实机原话："不知道是谁的，看着很诡异"） |
| **成员边界关掉「内心思量」折叠** | `FinishThink()` 原先**只有单聊 `npc_reply` 那一处**调用（全工程唯一调用点）⇒ 群聊里思考折叠从不关闭，下一位的思考增量并进上一位那块（实机：一块折叠 850 字，而 Python 日志显示那位只推了 382 字；标题只写着第一个人的名字）。现在 `speak` / `silent` / `error` / `end` 四个边界各调一次（对"没有活着的折叠"是无害 no-op） |
| **群状态帧留痕** | `room_state` 这一族帧此前**零日志**，而它正是"谁被点名 / 为什么没人说话"的唯一解释来源（09-17 排查时 Player.log 里连"谁被点名"都查不到）。现在每帧一行 `群状态 speak 说话=姜萌 实例#4`，忙标也带上理由（`忙 ON 实例#4 ← 群点名 姜萌`） |


`text_delta` / `step` 还额外带 `room_id`：一个 NPC 可能同时在两个群里而两个群窗都开着，
光靠 `npc_id` 路由不清。`uid` 除了去重，也是将来"群窗删一条"的锚点（§9.2）。

> ★ **错误帧也必须带 `phase="end"`**（P1b 实现时发现的第二个静默故障）。
> `handle_room_message` 的异常兜底原本发的是 `room_state{room_id, error=true, text}`，

## 七、我的思路 —— 走过的弯路与修正

这一节记录判断的演化，避免后来者重走。

| # | 一开始的判断 | 为什么错 | 现在 |
|---|---|---|---|
| 1 | `Room.log` 是**唯一真相** | 只对**群窗与投递**成立。模型的真相是各自的 session | 见 §2.1 的分工图 |
| 2 | 每个房间目录下给每个成员存一份 session（`<npc_id>.jsonl`） | 同一 NPC 的单聊与群聊被切成两套历史 ⇒ 跨场合记忆要额外机制。而 `_lock_for(npc_id)` 本来就串行 ⇒ 不会并发冲突 | **一个 NPC = 一个 session**（"一辈子"） |
| 3 | 投递用"回合外 `session.append(..., surfaceOp=append)`"，**零核心改动** | 举的先例（`_inject_acquaintance_if_new`）是 **plugin 内部物**，与会话内容不是一类。**实测三个破口**，且跑模拟看不出来 | 走 inbox 的 `next-step`（§4.2） |
| 4 | `scene` 是「房间 id / 地点」 | 我用了 `"room:白帝城"` 这种例子，把语义暗示成地点。**地点根本取不到可用的值**，而且同一个地点可以是两个场合 | `scene` = **交谈身份标识**，不透明字符串 |
| 5 | `scene` 可以从 `roster` 派生（少一个字段） | 用户指出微信群可以随便拉人踢人而记录不断 —— 靠的是**群 id 稳定**。派生的话一拉人 key 就变 ⇒ 历史断成两段、老段没人能打开 | `scene` **独立稳定**，`set_scene` 保留（§4.3） |
| 6 | 游标存 `Room.cursors` | 游标在 Room、记忆在 session ⇒ 两次落盘之间出错会**永久丢几条发言** | 游标写进 **session**（§3.3） |
| 7 | 群窗从某个成员的 session 投影 | 玩家自己没有 session；成员会话可能被压缩/删除/是后加入的 | 从 `Room.log` 投影（§2.1） |
| 8 | 逐段"撤回"以处理同席者离场 | 冗余 —— 只要 `present` 段**恒非空**，进出场合都必然改变它的内容，差分天然通知模型 | 不做逐段撤回（P0 已定） |
| 9 | 群窗删除跟着 1:1 窗的"删回合"走 | turn 号**跨会话不可比**（实测：同一条发言在林婉清是 turn 2、在李四是 turn 1） | 用 `uid` 定位（§9.2 定稿：Room 墓标 + 各 session fan-out 剔除） |

### 9.2 已定稿：群窗「删除一条消息」= 群记录 + 各成员记忆，两边同删（09-17）

> **实施状态（09-17）**：**两侧均已落地** —— Python 全链路（墓标 / fan-out /
> `preview_room_delete` / `room_delete` / 守卫）+ C# 群窗删除 UI（行绑 uid、`DeleteBar` 复用、
> 一次往返重放、确认文案写明"成员记忆一并移除"），见 **§十八**；仅剩实机首测与真机验收。

删的对象是 `Room.log` 里的**一条发言**（`uid = f"{room_id}#{seq}"`）。三个落点同时发生：

| # | 落点 | 机制 |
|---|---|---|
| ① | **群记录**（群窗 / 重开回放 / 投递） | `Room.deleted_seqs` **墓标**（随 `to_meta()` 落盘 —— rooms 是**全量重写**，天然持久化；`Room.log` 保持只增不改）。`delta_for` 跳过墓标 seq ⇒ **还没听到的人永不再收到**；`project_room_history` 跳过 ⇒ 群窗与重开回放一致 |
| ② | **各成员记忆** | fan-out：每个成员 session 落一条 `history/delete {reason:"room_delete"}`（走 `drop_seqs` 路径；`user/message` 无 tool 配对，单剔一条不破坏 `pairing_balanced`） |
| ③ | **一致性** | 全在同一次 `flush_all()` 落盘 ⇒ 继承"随存档固化、读档回滚" |

**锚点（两种，缺一不可）**：

- **投递副本**用 `user/message.source.uid`（§4.1 早为此留的）—— NPC 发言的 peer 副本已有；
- **玩家消息（09-17 补锚点）**：群内投递的玩家消息此前 `source=None`（当年为"与单聊逐字节相同"
  刻意留空），事后定位不到。改为 `source={"kind":"room","speaker":"player","uid":…}`；
  **单聊路径不变**。需同步的消费点只有两处极小分支：`_apply_speaker_labels`（新 kind → `玩家：`）
  与 `history.py`（给它一个显式分支；其兜底本来就是"未知 kind → user"）。压缩材料按 role 回落，不受影响。
  R1 测试里"玩家的话 `source` 恒为 `{}`"的口径随之更新 —— 那是**单聊**契约，群内投递从此带锚点。
- **发言者自己的话**是 `assistant/message`，没有 uid：`_run_round` 在 `_say_and_emit` 之后往其
  session 追加一条 `room/utt {room_id, seq, node}` 注记（形状同 `room/cursor`，对 SurfaceManager /
  `derive_messages` / UI 投影 / 压缩材料全部隐形），记下"这条发言 = 我账本里的哪个节点"。

**fan-out 计划器（message 级；压缩耦合规则与"删回合"同款）**：

对每个成员：在**整份 log**（不只 surface —— 已被压缩折走的原始 seq 仍在 log 里）按 uid / 锚点
找目标节点，然后逐节点套 `history_ops.plan_delete` 的同款规则：

- 目标在目录里 ⇒ 剔除（`drop_seqs`）；
- **纪要节点**：其代表的 `shadowedSeqs` 传递闭包（**此前已删视为已覆盖**）**全部**被删才删纪要；
  **部分覆盖 ⇒ 纪要原样保留**（强行删会连带删掉别的记忆）。预览如实报告"该成员已把此条折进
  纪要，无法逐字删除"；
- `sourceEventSeqs` 替换节点、plugin 注入：沿用各自豁免规则；
- **fail-closed**：模拟新目录跑 `pairing_balanced`，不平衡整体拒绝（账本零写入）。

**取成员记忆的顺序是三级**（每级对应一种"记得但容易看不见"的人，缺一级就漏一种）：
活体（`store`）→ **冻结舱**（关窗未固化：对象与账本还在内存，重开窗原样复活）→
**磁盘账本**（**重启 / 读档后尚未激活**的人：`discard_all` 清空了内存，而开群窗不激活任何
成员）。第三级由 `AgentLoop.resume_if_on_disk` 提供：**磁盘确有账本才 resume**（不空建对象），
读盘失败 ⇒ **整体拒绝**（宁可删不成，不许静默漏删）。只查内存会把后两种人报成"没有副本"，
而删除后他一开窗照旧记得。

**找不到副本的**（内存与磁盘都没有：没听到 / 后加入 / 此前已删）⇒ 跳过；预览按成员计数如实报告。
重复执行**幂等**。

**守卫（09-17 拍板）**：一轮群聊进行中（`room_lock` 占用）、或**任一成员**正在回合 / 正在压缩
（`_compacting`）⇒ **整体拒绝**并提示（与单聊删除守卫同款；不做"跳过忙成员"—— 会留下
"有人忘了、有人记得"且 UI 无法表达）。**待回应提案的叙述行在挂起期间禁止删**（等收口后再允许），
避免"提案还挂着、公开记录没了"的错位。

**执行顺序**：先各成员 session 落 `history/delete`，最后写 Room 墓标；崩在中途重试可收敛（幂等）。

**做不到的（如实声明）**：已折进纪要的副本无法逐字遗忘（压缩的有损本质，单聊同理）；
已解散的群无从再删；删除随存档固化 / 回滚（同单聊）。

**接口（v2 实施）**：新 RPC `preview_room_delete` / `room_delete`（载荷 = `room_id` + 选中的 uids；
回执带新群历史 + 每成员报告，C# 一次往返重放）。C#：群窗的行改绑 **uid**（现绑账本 turn，
群行没有该字段）；选择 / 预览 / 确认复用 `DeleteBar`；与"压缩按钮"的显隐一并处理（见 §9.2.1）。

### 9.2.1 已定稿：多聊**不提供**手动压缩（09-17）

**现状是个死按钮**：群窗与单聊共用 `ChatWindow`，压缩 / 删除按钮在群窗里**仍可见**，但
`OnCompactBtnClicked` / `OnDeleteBtnClicked` 的第一道守卫都是 `CurrentNpcId` 非空 ——
而群聊模式刻意置空（`OpenForRoom`）⇒ 点下去**静默 return**，连提示都没有。
（守卫本身是**刻意**的，见 §12.2③「不可能拿群 id 去当 npc 用」；这里要补的只是**按钮随之隐藏**，
别让玩家看见一个按下去毫无反应的按钮。）

**为什么不提供**：压缩的单位是 **session**（`compact_now` 对整份 surface 选段、**不做 scene 过滤**）——
一个 NPC 一份账本 = 他一辈子的经历；`Room.log` 不是记忆、永不压缩（它是回放与投递的权威）。
"压群"的两种解释都不对：

- 压全员 = N 次摘要调用 × 每人的**全量历史**（含单聊与别的群），远超群窗按钮的暗示；
- 压某一个成员 = 作用域仍是他的全部记忆，正确归属地是他的 **1:1 窗口**。

且**自动压缩在群回合里照常发生**（回合边界 `compactor.maybe`）；手动压缩只是"强制提前压一次"，
到任意成员的单聊窗做**完全等价**（压缩本来就是全 scene 的）。

**改法（已落地，09-17）**：`SetRoomButtonsVisible` 里把 `CompactButton` 随开关显隐
（**删除按钮不再收** —— v2 已落地，群删走 uid 载荷，两个模式都用，见 §9.2）。

另有一道**命令拦截**（§15.9/§16.11 记的"群聊里 `/compact` 被当群消息发出去"）：
群窗输入 `/compact` 由 **C# 本地**拦下（清输入框 + 提示"压缩作用于某个 NPC 的全部记忆，
请到他的单聊窗口操作"，**不落本地气泡、不发请求** —— 群里根本没有这条，落了就是幽灵发言）；
`ChatHub.handle_room_message` 另有同口径兜底（旧 DLL / `chat_cli` / 将来新增的注入点），
判据与单聊同规约（先剥游戏时间戳再判），反馈走 `room_state(phase="end", error=True, text=…)`
—— 就是"一轮异常"那条既有终帧通道（C# 在终帧里显示这句 `text`）。

### 9.2.2 已落地：聊天帧队列（关窗期间缓冲；09-17 统一到单聊）

**问题**：玩家在群 / 单聊里说一句就关窗（去打架 / 换界面），Python 侧那一轮照跑；
`room_say` / `room_state` / `text_delta` / `step` 到达时窗口关着 ⇒ 被 `!IsOpen` 守卫丢掉。
重开窗的 `open_room` / `open_chat` 重放能把**说完的话**补上（落账后广播），补不回来的是两样：
① **正在说的那半截**（`text_delta`）；② **在跑什么 / 谁在说**（群聊 speak 状态、两边的
工具折叠与思考整段）。

**统一（09-17）**：一个队列 / 一个 tee 服务两个世界 —— 原 `RoomFrameQueue` / `RoomFrameTee`
更名为 `ChatFrameQueue` / `ChatFrameTee`；群聊与单聊共用一个类、两套桶（键 = `room_id` / `npc_id`）。

**落点（三层，缺一不可）**：

| 件 | 位置 | 职责 |
|---|---|---|
| `UI/ChatFrameQueue.cs` | 纯逻辑（零 Unity / 零 Newtonsoft） | 群聊：桶 + 轮 + baseline 判决；单聊：**整轮记录**（`user_say` 开段 / `npc_reply` 闭段 / `step` 回合号推进隐式闭段，delta 按 part 合并成累计文本，另有段闭合代数）。由 `csharp/tests/ChatFrameQueueTests` 直测（101 断言） |
| `UI/ChatFrameTee.cs` | 常驻静态订阅者（`ModMain` 建连后 `Attach`，与 `ContactDuty` 同规约） | 两路分流：有 `room_id` ⇒ 群白名单四帧 + **没人显示这个群**（`AbChatPanel.IsShowingRoom`）；无 `room_id` ⇒ 单聊白名单（`text_delta` / `step`）**一律收**（09-17 二次改造：与"谁在显示"无关，见下）+ 单聊 `npc_reply` 段闭合信号 |
| `ChatPresenter.SendOpenChatReplay` 的 `DrainSoloFrames` / `ApplyOpenRoom` 的 `DrainRoomFrames` | 各自重放（`ReplaceHistory`）**之后** —— 群还要在 `SetBusy(false)` 之后，单聊在 `ClearReplayGate` 与 `EnterSelecting` 之前 | 取该演的帧、逐帧走**字段版**应用（`ApplyRoomSay` / `ApplyRoomState` / `ApplyStep` / `ApplyDelta` / `AppendUserMessage`）、最后 `ForgetRoom` / `ForgetSolo`，并钉底（`HoldScrollAtBottom`） |
| `ChatPresenter._replayGate` | 单聊**渲染闸**：`SendOpenChatReplay` 请求发出前置位，回执里消费完落位 | 闸门期间单聊帧**不画**（它们已由 tee 记进队列）——"始终记"之后必须掐掉直播，否则同一帧被"重演 + 直播"画两遍 |

**单聊二次改造（09-17，勿改回）**：初版按"有人正显示这个 NPC ⇒ 不收"分流，实机暴露两条
补不回来的洞 —— ① 玩家只能在窗口开着时发消息、工具/思考也大多在关窗**之前**，这些帧被丢掉后
`open_chat` 的重放（只含**已闭合**回合）也补不回 ⇒ 重开窗是"后半截流式正文 + 没有我的输入 +
没有行动记录"；② 那个判据本身还是个静默丢帧开关（面板没走关闭契约 ⇒ 残留为真 ⇒ 帧永远只进
直播、不进队列，事后无迹可查）。现在：**记录归 tee（始终记）+ 谁负责画归渲染闸**；
玩家发言由 C# 在发送处补一条本地帧（`user_say` —— 单聊没有回声帧）。
另有两条配套：段闭合**代数**（`SoloEpoch`）用来发现"`open_chat` 快照过期"（请求发出到回执到达
之间刚好收口），批量重建后 `HoldScrollAtBottom()` 钉底保持几帧（否则视图停在顶部）。

**群聊桶按"轮"组织**：`room_state(phase="speak")` 开轮、`phase="end"` 闭轮；`text_delta` / `step`
没有 seq，**必须跟着它那一轮同留同丢** —— 否则会出现"delta 留下、它的 end 被丢"，重放时
`AppendDelta` 凭空建泡（`ChatWindow` 的防御分支）⇒ 活跃泡永久泄漏 ⇒ 删除/压缩入口被
`HasActiveBubble` 守卫挡死（功能性事故，不只是观感）。消费判决（`baseline` = 重放 items 的最大 seq）：

| 桶内对象 | 判决 |
|---|---|
| 已闭合轮 | `endSeq <= baseline` ⇒ **整轮丢**（屏幕已由重放呈现）；否则整轮留 |
| 未闭合轮 | 恒留（"正在说的"就是它）—— **但段内已出现 `0 < seq <= baseline` 的 `room_say` ⇒ 整段丢**（09-17 复核修：那条已落进 `Room.log`、重放已经画过；只丢 say 会留下永远等不到定稿的半截泡） |
| 轮外散帧（玩家回声 / 无配轮的 end） | `seq <= baseline` ⇒ 丢 |

**单聊桶只保"最后一个未闭合段"**：`npc_reply` 发出时账本必已闭合（`_run_turn` 先落账、后发帧），
而 `open_chat` 重放只出已闭合回合 ⇒ 收到过 `npc_reply` 的那一段**重放必然补全**，留在队列里
只会被重演成重复（工具折叠不归 `BubbleCommitPolicy` 管）。所以：`npc_reply` 到达 ⇒ 整段作废
（**无论有没有人显示** —— 显示中只是同步清段，兜住"回调失败残留"的过期段）；`step` 的账本
回合号变大 ⇒ 旧段隐式作废（防"`npc_reply` 丢帧"的死段演成幽灵泡）；段内只裁 delta。
消费时"直播优先"（单聊 `OpenChatAndReplay` 回调若已在直播 ⇒ 记欠账 + `ForgetSolo` 丢段：
段已被直播续写或已收口，留着 = 过期段）；段非空 ⇒ 重演后 `SetBusy(true)`（"还在说"是真的，
真回合若其实已死由 `BusyWatchdog` 自愈）。

**为什么去重只能靠 baseline**：群窗回放不带 `turn` ⇒ `BubbleCommitPolicy` 的
`Skip` / `OverwriteLastRow` 两档**对群窗不可达**（见 `ChatWindow.ReplaceHistory` 的注释）；
`_roomEchoSeen` 在开窗时刚被 `Clear()`，也指望不上。baseline 同时挡 NPC 定稿与**玩家回声**。

**裁剪**：两边都只裁 delta（`room_say` / `room_state` / `step` 永远保留 —— 丢 `end` 会让
忙碌态卡死、丢 `say` 会让内容缺口、丢 `step` 会让工具过程缺口）；群聊闭合轮只留最后 4 个
（丢最旧**整轮**，不撕结构）；群聊单桶与单聊单段各有 2000 帧绝对上限（正常远到不了）。
无归属 delta / step（连 `speak` 都没收到）一律**不收**：那种时序不可复原。

**生命周期**：群解散（`OnRoomDissolved`，放在"不是当前群就早退"**之前** —— 解散的往往不是
当前显示的那个群）、换存档（`ModMain.OnIntoWorldEvent`，与 `PortraitCache.ClearNameIndex`
并列）清桶；关窗 / 断线**不清**（正是要缓冲的场景）。判据异常一律当"没显示"（收）：
多收的帧由 baseline / 段闭合兜住，误判"在显示"会让帧真正丢失 —— 与快捷键屏蔽的失败姿态相反。

**诚实边界**：队列**修不了"帧没到达 C#"**（断线丢帧）—— 那只有重放能补；它的价值窗口 =
关窗 → 重开那一刻。单聊侧"重开窗瞬间恰在吐字"的场景与既有"直播优先"一致（半截从当下起、
收口全文覆盖，**内容不丢**，只少几秒观感）。

**测试**：C# 单测 74 断言（分桶 / 轮判决 / 单聊段 / 只裁 delta / 隐式闭合 / 生命周期）+
Python 契约 14 条（消费时序 / 判据与分流 / 生命周期 / **跨语言字段名**对齐）+ 变异验证
`scripts/dev/mutate_check_chat_frame_queue.py`（13 个变异全被捕获）。

### 9.3 未决二：房间粒度与"续聊"

本设计采用**微信群语义**：同一批人 = 同一个稳定群，可关窗重开续聊。
（设计文档 §10-E 问过"每次聚谈新建一个房间 vs 同一批人同一个房间" —— 此处定为**后者**。）

代价：**玩家无法"另起一段"**（同一个群会一直累积）。若将来要支持，加一个"新开一局"的动作即可，
`scene` 是不透明字符串 ⇒ **Python 侧的过滤代码一行不用改**。

### 9.4 未决三：房间里能不能单聊

玩家在群聊进行中打开某个成员的 1:1 窗并发消息 —— 现在**技术上允许**
（`handle_message` 不取 `room_lock`），消息会在该成员当前回合的下一步被领走。

两个方向：① 允许（与"玩家插话"一致）；② 群里禁止（UI 上禁用单聊入口）。
**建议 ①**，但需要在 UI 上让玩家明白"这句话只对李四说"。

### 9.5 未决四：群的创建入口

谁来决定"把这几个人叫到一起"？P1 假设 C# 侧有 UI 让玩家选人。
候选来源可以用现成的 `RelationNetwork.CollectSameGridUnits`（同格 NPC 枚举，已存在）。

**物理设定建议**：群聊 = **同格实地聚谈**（大家面对面）。影响措辞、L1「在场」段文案、
以及 `movement` 在房间里的语义。

## 十九、群成员的**精确身份**（`Room.member_unit_ids`，09-16 第 3 步；09-17 改为**随帧携带**）

### 19.1 为什么必须有它

群成员名单的真相在 Python（`Room.members` = **中文名**）。而 C# 侧凡是"要碰游戏本体"的地方
—— 逐行立绘取图（`PortraitCache.IdByName`）、成员开口时的 `GameContext.GetL1` ——
都必须先把中文名换成 `WorldUnitBase`。

**重开一个群时，C# 手里没有任何对象**：名单是 `open_room` 回包给的。于是只剩一条路 ——
`UnitLookup.Resolve(name)` 的 ④ 全图按名扫描，而这游戏"重名是常态不是例外"。
扫错的代价不是慢，是**静默错人**（文件头那次真机事故：不报错、不缺字段，只是把另一个人的
档案端给模型）。

### 19.2 数据的形状（三个刻意的决定）

| 决定 | 理由 |
|---|---|
| **`{npc_id: unitID}` 的 dict，不是与 `members` 平行的数组** | 平行数组两端一旦对不齐（过滤空成员、顺序不一致、C# 多塞一个）就会**把甲的身份安到乙头上** —— 不报错、只是画错脸。dict 让"谁的身份"由键自己带着走，这种失败模式不存在 |
| **可以缺项**（只覆盖一部分成员） | 老群、或建群时 C# 手上恰好没有那个人的精确身份。缺项只意味着"渲染他要多扫一次全图"，不影响任何语义 |
| **离群即失效**（`kick` 里 `pop`，`to_meta` 只带当前成员） | 与 `joined` 同款。留着会让"重入群"沿用可能已指向别人的旧身份 |

**空值一律不写键**（不写空串）：`"键不存在"` 是明确的"不知道"，空串会变成一个
"有身份但是空的"中间态 —— 而中间态一旦可达就会有人写出来。

### 19.3 链路（谁在哪一刻交出来的）

   └─ 拉人：add_room_members { ..., member_unit_ids }

   │          就是把猜测固化到磁盘、跨会话生效（Pin 注释同款理由）
