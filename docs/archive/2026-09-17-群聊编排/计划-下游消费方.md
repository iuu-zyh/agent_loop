## 二、实测事实（跑出来的，不是推的）

### 2.1 回合外 append：「投影归属」与「删除跨度」不一致

```
（单聊一回合 → 回合外投递 2 条 → 再跑一回合）

  ── 投影结果
     turn=  1 seq=  4 user       '单聊第一句'
     turn=  1 seq= 12 assistant  '[回显] 玩家：单聊第一句'
     turn=  1 seq= 15 peer(李四) '【同席】我先打个招呼'     ← ★ 被塞进**上一个已闭合回合**
     turn=  1 seq= 16 user       '【群聊】你们都在啊'       ← ★ 同上
     turn=  2 seq= 21 user       '嗯，都在。'
     turn=  2 seq= 22 assistant  '[回显] 玩家：嗯，都在。'

    删除跨度：{1: [1, 14], 2: [18, 24]}
    peer(seq=15) 投影归属 turn=1，该 turn 跨度=[1,14] → ★删不掉
```

**后果链**：UI 上删掉 turn 1 → `turn/start` 也被删 → 该条落进初始容器（turn=0，永不发射）
→ **UI 看着删干净了，但 `surface` 里还在 ⇒ 模型仍记得**。这是"假删除"，比不删更坏。

### 2.2 首个 turn 之前的回合外 append：静默丢弃

```
     complete_turns=0 items=0 → ★整条消失
```
`history.py` 的 items 只在 `turn/start` 建容器；`turn/start` 之前的消息落进初始容器
（`cur = {"turn": 0, ...}`，**不在 `turns` 列表里**）⇒ 永远不发射。

### 2.3 turn 号是**会话局部**的

```
    （同一句房间发言投给两人）
    林婉清   账本 seq=23  所属 turn=2
    李四     账本 seq=15  所属 turn=1
```
⇒ 房间**无法用 turn 号**做跨成员标识。而 `ChatWindow.RowMeta.Turn`（`ChatWindow.cs:1184-1199`）
注释明写"Python 侧删除以**完整回合**为单位（`plan_delete` 只信任 turn 编号）"——
所以"在房间里删掉某一轮"这件事，turn 号承载不了。

### 2.4 对照：走 inbox 的投递形态**三处全部自洽**

```
    （玩家房间发言 + 同席发言都走 inbox next-step，再 nudge）
  ── 投影结果
     turn=  1 seq=  7 user       '【群聊】你们都在啊'
     turn=  1 seq=  8 peer(李四) '林道友，别来无恙。'        ← 在**本回合**内部
     turn=  1 seq= 17 assistant  '[回显] （轮到你说话了。）'

    删除跨度：{1: [3, 19]}
    peer(seq=8) 归属 turn=1，跨度=[3,19] → ★可删（投影与删除一致）
    plan_delete([1]) ok=True ranges=[[3, 19]]，peer 在剔除集里? 是
```

### 2.5 `compress._render_transcript` 的实际输出（`probe3`）

```
韩立：你好。
林婉清：[回显] 玩家：你好。
韩立：（NPC主动传音：向玩家打个招呼）（缘由：想起旧事）      ← ★ bug：舞台指令被记成玩家说的
李四：林道友，别来无恙。                                    ← ✔ P0 修的 peer 归属，对了
```

## 三、逐项分析

### 3.1 `compaction/compress.py` —— 要改 2 处

#### (a) `initiative` 说话人判据错 ★ 真 bug，与上次修的 plugin 同一类

`initiative.py:58-69` 明写：意图被包装成"**伪 user 文案：括号舞台指令**"
（`（NPC主动传音：…）` / `（游戏内交互：你刚对玩家说了这样一句——「…」）`）。
它**不是玩家真言**，但 `_render_transcript` 只看 `role == "user"` ⇒ `玩家：（NPC主动传音：…）`。

- `history.py:85` 早就把它单列成 `kind=initiative`（不当玩家气泡）—— **两个消费方口径不一致**。
- P0 修 plugin 时我在 `compress.py:326` 的注释里明确写了"主动开口舞台指令是 `initiative`，该照旧进材料"——
  **"进材料"是对的，"记成玩家说的"是错的**。我只拦了 plugin，漏了 initiative 的**归属**。
- 危害同 plugin 且更重：纪要是**永久节点**，下次压缩还喂回来 ⇒
  "玩家主动传音说要打招呼"被写进关系摘要，越传越歪、无法自愈。

**改法**：`_render_transcript` 里给 `kind=="initiative"` 单开一条渲染分支，
产出舞台指令行（如 `[舞台指令] （NPC主动传音：…）`）而不是 `{玩家}：…`。

#### (b) peer 行缺少"第三方"标记

`李四：林道友，别来无恙。` —— 摘要器无法区分"李四"是**房间里另一个 NPC** 还是玩家的别名。
而压缩指令（`prompts/compaction/default.md`）的结构是彻底以玩家为中心的：
「与玩家（{player_name}）的关系」「玩家与 {npc_name} 之间未完成的事」「玩家已知与尚不知道的信息」——
**没有任何槽位容纳第三方** ⇒ 李四的话最可能被折进「与玩家的关系」。

**改法（两处小改，不做 transcript 头部图例——长记录里会被稀释/切掉）**：
1. 行内标：`李四（同席）：…`；
2. `prompts/compaction/default.md` 补一句：「标着（同席）的行是**其他在场角色**说的话，
   不是你也不是玩家；与他们有关的事实用其本名记入「剧情与近况」。」

> **不改**指令的 6 个分节：按人加节会在多同伴时爆炸，且节名是写死的。
> 靠行内标记 + 一句说明，让第三方事实自然落进「剧情与近况」。

### 3.2 `history.py` —— 已修一半，还差两处

| 项 | 状态 |
|---|---|
| `peer` 分支（不落成玩家气泡，归属 `source.speaker`） | ✔ P0 已做 |
| 回合外消息的归属（§2.1 / §2.2） | ✗ 见 §四 D1 |
| 场合标签 + 过滤（§3.3） | ✗ 待做 |
| `initiative` 分支 | ✔ 早就对（`history.py:85-93`） |

补充：`peer` 项目前只给 `speaker`（显示名）。C# 侧若要画头像需要 **unit id** ——
建议 P1 落账时同时带 `speaker_id`，`history.py` 透传（零成本，后加要改数据）。

### 3.3 UI 回放按场合过滤 —— 需要新机制，且有前置

**前置**："场合"这个标识今天**不存在**。最小落地顺序：

1. `dialogue_agent` 持有 `self.scene: str = ""`（P1 的 Room 设它；本轮默认空）；
2. `turn/start` 落 `{"turn": n, "scene": "..."}`；
3. `history.py`：每个 item **继承所在 turn 的 `scene`**；
   `project_ui_history(session, max_turns, scene=<哨兵>)`，缺省 = **不过滤**（向后兼容）；
4. **turn 编号必须保持账本原值**，绝不能因为过滤而重编号 ——
   `ChatWindow.RowMeta.Turn` 直接把它交回 `plan_delete` 当键（`ChatWindow.cs:1184-1199`）。

**1:1 窗显示什么？推荐：只显示单聊场合。** 三条理由：
- 这就是"按场合过滤"的字面意思；
- **与直播行为对齐**：`ChatPresenter.cs:485` 的 `if (npcId != _window.CurrentNpcId) { DiagDrop(...); return; }`
  本来就会丢掉"不是这个窗的 NPC"发的帧 —— 直播时李四的发言进不了林婉清的窗，
  **只有回放会把它塞进去**。过滤让两者一致，且 **零 C# 改动**；
- 备选（不过滤 = 现状）等于把 1:1 窗做成"与这个 NPC 的完整关系史"，
  但那就不是"按场合过滤"了。

**已知遗留**：P1 之前没有房间窗 ⇒ 群聊内容会**暂时无处可删**。这是 P1 的账，本轮结不掉，
但要在文档里写明（否则会被当成 bug 报上来）。

### 3.4 `history_ops.py` —— 算法不用改，周边三件事

| # | 事 | 判定 |
|---|---|---|
| 1 | peer 消息在删除区间里的归属 | ✔ **正确**：它不是 plugin、没有 `sourceEventSeqs` ⇒ 走"普通对话节点：seq ∈ range 即剔除"（`history_ops.py:191`），无需登记。已实测（§2.4） |
| 2 | 回合外消息**不在任何 turn 跨度里** ⇒ 删不掉 | ✗ 必须处理（§2.1）。修法取决于 §四 D1 |
| 3 | turn 号跨会话不可比 ⇒ 房间删除不能靠 turn 号 | ✗ P1 议题：房间的删除/去重/回放键得用 **Room 坐标**（Room.log 的 utterance seq），再逐成员换算 |
| 4 | 多成员删除必须**整体提交** | ✗ P1 契约：`plan_delete` 的 fail-closed 是单会话的；房间删除要"全员 dry-run 都过才一起落账"，否则一边删了一边没删 |

**已知残留（不改，只记录）**：纪要节点代表的内容若**部分**被删则豁免保留
（`history_ops.py:172` `rep <= (range_union | prior)`）。
⇒ 群聊内容进了混合纪要后，删单聊回合删不掉它。
这是有损摘要的固有代价，保守保留是正确取舍。

## 四、待决（需要拍板，之后才好动手）

### D1：同席发言的投递形态 —— 走 inbox 还是回合外 append ★ ✅ **定为乙（走 inbox）**

#### D1 到底在问什么（一句话）

群聊里李四说了一句话，这句话要进林婉清的账本（不然林婉清不记得）。**问题是：这句话什么时候、以什么方式写进去？**

- **甲**：Room 拿到李四的话，**立刻**直接塞进林婉清的账本（此时林婉清还没开始回合）；
- **乙**：Room 把李四的话塞进林婉清的**信箱**（inbox = 待办队列），林婉清**下次开回合时自己领出来落账**。

差别只在"夹在回合之间"还是"住在回合里面"。而账本现在是**按回合组织**的，玩家的消息也是在
**回合里面**落账的（`dialogue_agent.py:579`：回合开始后 `_pre_step` 领到信才落）。

#### 账本形态对比

场景：玩家先与林婉清单聊一句（turn 1）→ 进群 → 李四说「别来无恙」→ 玩家说「你们都在啊」→ 林婉清回「嗯，都在」。

**甲（回合外 append）**
```
turn/start        (turn 1)
  user/message    ← 单聊第一句
  assistant/message
turn/end
user/message      ← 李四：别来无恙        ★ 夹在两回合之间，不属于任何回合
user/message      ← 玩家：你们都在啊      ★ 同上
turn/start        (turn 2)
  user/message    ← 嗯，都在。
  assistant/message
turn/end
```

**乙（走信箱）**
```
turn/start        (turn 1)
  user/message    ← 单聊第一句
  assistant/message
turn/end
turn/start        (turn 2)
  step/start
    user/message  ← 李四：别来无恙        ★ 在回合里面
    user/message  ← 玩家：你们都在啊      ★ 在回合里面
    user/message  ← （轮到你说话了。）
    assistant/message
  step/end
turn/end
```

#### 为什么甲会出事

因为**两套代码都默认「每条消息都住在某个回合里」**：

1. **UI 回放**（`history.py`）：遇到 `turn/start` 才开一个"格子"，之后的消息往**当前格子**里放。
   甲形态下，李四那句是在 turn 1 的格子关闭之后到的 ⇒ 仍被放进 **turn 1 的格子**（格子还没换）。
2. **删除历史**（`history_ops.py`）：把"删第 1 回合"翻译成"删 `turn/start`..`turn/end` 的 seq 区间"。

⇒ **UI 显示它属于 turn 1，但 turn 1 的删除区间不含它。** 实测见 §2.1。

三条后果（均已实测）：

| # | 后果 | 说明 |
|---|---|---|
| ① | **假删除** | 玩家删掉 turn 1 → UI 上那条也不见了（它的"格子"`turn/start` 被删，它掉进永不发射的 turn-0 容器）→ 但账本里、`surface` 里都还在 ⇒ **玩家以为删了，林婉清还记得** |
| ② | **首回合前的投递彻底消失** | 玩家刚进房间、自己还没开口时李四先说的话，UI 上**永远看不到**（§2.2） |
| ③ | **顺序错位** | 玩家在群里说的「你们都在啊」，回放里显示成 turn 1 的一部分 —— 看着像上一轮单聊里自己说的话 |

③ 是观感问题；①② 是**数据问题**：UI 说的与模型看到的不是一回事。

#### 为什么乙没这些问题

乙形态下所有消息都在回合里面，实测（§2.4）投影归属与删除跨度**一致**，`plan_delete` 能剔除 peer。
⇒ **`history.py` / `history_ops.py` 一行都不用改。**

#### 代价对比

| | 甲 | 乙 |
|---|---|---|
| 要改的代码 | `history.py` + `history_ops.py`（约 30 行） | 只改 P1 那句投递 |
| "回合"这个概念 | 边界要放宽（含游离消息），后续消费者都得记得考虑 | 不变 |
| 王五只听不说 | 账本照涨 | 增量留在信箱，账本不涨 |
| 存档 | 直接就在账本里 | 信箱也一样存（`agent/inbox/spliced`），读档可恢复，不丢 |
| 与其他机制 | 新路径 | 与既有"玩家插话 next-step"同一条路 |
| 顺序 | 由 append 时刻决定 | `claim()` 先吃光 `next-step` 再吃一条 `next-turn` ⇒ 增量按序落在**本回合 step 1**，正是想要的 |

#### 原设计为什么选了甲，以及为什么那个理由不成立

设计文档 §3.2 说甲是"零核心改动"，举的先例是 `_inject_acquaintance_if_new`（`ws_channel.py:781+`）——
那条也是"直接 append 不进筐"。

**但先例不成立**：初次相识备注是 **plugin 内部物**（UI 看不见、不属于任何回合、也不参与删除）；
而李四说的话是**会话内容**，正是要被回放、被删除的东西。拿"内部物"的先例套"会话内容"，
就撞上了上面三条。

#### 汇总表

| | 甲：回合外 append（P1 现状设计） | **乙：走 inbox（推荐）** |
|---|---|---|
| 形态 | `session.append("user/message", msg, {"surfaceOp":"append"})` | `agent.send(text, target="next-step", wake=False, source=...)` |
| `history.py` | 要改（游离消息归属） | **零改动** |
| `history_ops.py` | 要改（`_turn_spans` 并入前缀游离段） | **零改动** |
| 实测 | §2.1 投影/删除不一致、§2.2 静默丢弃 | §2.4 三处自洽 |

### D2：1:1 窗的过滤语义 ✅ **定为甲（只显示单聊场合）**

- **甲（推荐）**：只显示单聊场合 —— 与直播的 `npc_id` 丢弃行为对齐，零 C# 改动；
- 乙：显示全部（= 现状），把 1:1 窗当"关系史"。

（其余细节按 §3.3 执行，不需要额外决定。）

## 九、压缩指令改造：玩家视角 → NPC 视角 · 第二人称（已完成）

> 触发一（用户）：「之前的压缩指令是以玩家为中心视角的，但加入多人群聊之后，
> 压缩指令更多的是从 NPC 本身的角度去思考了」——**轴**的问题。
> 触发二（用户）：「压缩指令最后模型看到的是 user 的形式，所以需要是第二人称」——**人称**的问题。

### 9.1 两个独立的问题：轴 与 人称

|  | 轴 = 玩家 | 轴 = NPC |
|---|---|---|
| **人称 = 我** | 最初的样子（两个都错） | 9.1 首次改写（轴对了、人称错） |
| **人称 = 你** | 轴错 | ★ **目标** |

**轴**决定「记的是谁的事」；**人称**决定「用哪个代词」。两者必须分别改对。

### 9.2 人称为什么必须是「你」——三条理由

1. **同一个通道里的既有惯例就是第二人称。** 纪要与 L1 段走**同一种消息**：`role:user` +
   `source.kind=="plugin"` + 不加说话人前缀（实测：两者的 text 原样到达模型）。而 L1 全程第二人称：
   `自身：你是林婉清，一位女子…` / `在场：…（连同你共 4 人）`。纪要用「我」⇒ 模型同时读到两套自我描述。
2. **user 消息里的「我」会被读成玩家。** 纪要写「我与韩立结着道侣之谊」，模型对 user 的默认假设是
   "玩家在说话" ⇒ 「我」= 韩立 ⇒ 语义崩掉。「你」只能指收信人（NPC 自己），无歧义。
3. **与 `_apply_speaker_labels` 的既有规则自洽**：真玩家消息才加「玩家：」前缀；plugin 类不加。

### 9.3 旧指令的内容问题（轴的层面）

| 旧分节 / 措辞 | 问题 |
|---|---|
| `## 与玩家（{player_name}）的关系` | 第三人称**档案**口吻 —— 像别人在写 {npc_name} 的评估报告 |
| `## 约定与承末 - **玩家与** {npc_name} 之间…` | 只认玩家 ⇒ 群里跟第三方立的约定无处可放 |
| `## 情绪与态度 - 对**玩家**的整体态度` | 同上，第三方被吞掉 |
| `## 信息边界 - **玩家**已知与尚不知道的信息` | ★ **上帝视角**：这是"玩家的知识状态"，不是 NPC 的记忆 |
| （无第三方分节） | 群里发生的事只能挤进「与玩家的关系」 |

### 9.4 新结构（7 节 · 标题名词化 · 正文第二人称）

分节名照 L1 抽屉的段标签风格（`自身` / `玩家` / `在场` / `同席·X` / `近况`）用**名词短语**；

## 十、P1 契约：Room 与 session 的关系（2026 待实现）

> 结论来自与用户的架构讨论（微信群模型）。**本轮只落文档，不写代码。**

### 10.1 一句话

> **`Room.log` 是「广播」，`session` 是「经历」。**
> 模型**从不读** `Room.log`；群窗**从不读** `session`。两条读路径完全独立，
> 只在「一次发言」这个写入事件上汇合。

### 10.2 三个消费者，三种取法

| 谁 | 要什么 | 从哪拿 | 用什么 |
|---|---|---|---|
| 模型 | 我经历过什么 | 自己的 `session` | `derive_messages()` |
| 1:1 窗 | 我和这个 NPC 的单聊 | 该 NPC 的 `session`，**按 `scene==""` 过滤** | `history.project_ui_history(session, scene="")` |
| 群窗 | 这个群聊过什么 | **`Room.log`** | **`project_room_history(room)`**（新，比上面简单一个数量级） |
| 投递 | 谁还没听到哪条 | `Room.log` + 各 NPC 的游标 | `Room.deliver_to(agent)` |

**群窗为什么不从某个 session 投影**：① 玩家自己没有 session；② 任何成员的 session 都可能被压缩过、
被删过回合、或是**后加入的**（没有早期发言）；③ 群窗要的是"客观发生过什么"，session 是"某个人记得什么"。

### 10.3 `scene` 的语义校正（★ 不是地点）

- `scene` = **这次交谈的身份标识**，**不透明字符串**、只做相等比较。`""` = 单聊；其它 = 某个群。
- ✘ **不是地点**：坐标不唯一（同格可能有多场聚谈）、地名会撞车（同地点多次聚谈），
  且"同一个酒楼里先跟甲单聊、再叫上乙"本来就是两个场合。
- ✘ **不能从 `roster` 派生**：微信群可以拉人踢人而记录不断，靠的是**群 id 稳定**；
  若 `scene = f(roster)`，一拉人 key 就变 ⇒ 历史在 UI 上断成两段、老段没有窗口入口（"孤儿"）。
- ✔ 因此 `set_scene` 必须保留（独立字段）。**"单聊还是多聊"看 `scene` 是否为空；"有谁"看 `Room.members`；
  "此刻在场有谁"看 `roster`。** 三者分工不同，不要塞进一个字段。

### 10.4 `Room` 的形态

```python
class Room:
    id: str                   # 稳定身份（"g3"）—— ★ 拉人踢人都不变
    title: str
    members: List[str]        # 可增可删
    log: List[Utterance]      # {seq, speaker, text, time} —— 只增不改
```

落盘：`<存档目录>/rooms/index.json`（名录）+ `rooms/<room_id>.jsonl`（流水）。
**没有** `<npc_id>.jsonl` —— 那部分已被"一个 NPC = 一个 session"的修订取消。

### 10.5 ★ 游标写进 **session**，不写进 Room

```python
session.append("room/cursor", {"room_id": "g3", "seq": 8})   # 不进 surface、UI 与模型都看不见
```

理由：**记忆与游标必须在同一个文件里**，否则两次落盘之间出错会出现"游标说听过了、记忆里没有"
⇒ 那几条**永久丢失**（投递不会再来）。同一次 flush 一起落 ⇒ 不可能不一致。
附带好处：**"没有游标记录" = 刚入群** ⇒ 默认 = `log` 末尾（看不到入群前的话），语义天然正确。

**顺序规则**：① 先投递（`agent.send(..., target="next-step")` → 落 `agent/inbox/spliced`），
② 后推进（`session.append("room/cursor", ...)`）。两条 append 到同一个 log、同一次 flush。

### 10.6 两边"不一致"的场景 —— 都应该是这样

| 场景 | `Room.log` | 该 NPC 的 `session` | 判定 |
|---|---|---|---|
| 压缩 | 不变 | 群聊段折成纪要 | ✔ 房间记录是事实，个人记忆本该有损 |
| 1:1 窗删回合 | 不变 | 单聊段被删 | ✔ 删除是个人记忆操作 |
| 加人 | 不变（id 也不变） | 新人只有入群后的 | ✔ 与微信一致 |
| 踢人 | 不变 | 被踢者停在那一刻 | ✔ |
| 存档 | 落盘 | 落盘 | ⚠ 必须**同一次 `flush_all()`** |
| 群窗删一条 | ？ | ？ | ⚠ **待设计**（见 §10.7） |

### 10.7 待定：群窗删除的语义

| 方案 | 做法 | 问题 |
|---|---|---|
| 甲 只删群记录 | 标记 `Room.log` | 群窗没了，NPC 还记得 ⇒ "假删除" |
| 乙 只删个人记忆 | 作用于某个成员 | 群窗看不出来 ⇒ 玩家不知道删成功 |
| **丙 两边都删** ★ | 标记 `Room.log` + 在各成员 session 里找那条标记 | 需跨 session 删除 |

**丙的可行做法**：给每条发言一个全局唯一 id ——
`Room.log: {seq:8, uid:"g3#8", ...}`；投递时 `source={"kind":"peer","speaker":...,"uid":"g3#8"}`。
删除 = 标记 `Room.log` + 在各 session 里扫带该 `uid` 的节点，加进 `history/delete` 的 **`drop_seqs`**。
（`history/delete` 本就支持任意 seq 的零星剔除；`user/message` 无 tool 配对，单剔一条不破坏 `pairing_balanced`。）

**建议**：v1 群窗不提供删除（1:1 窗的删除只管单聊）；v2 再做丙。

`<npc_id>.jsonl` —— 两句都要改：
