## 一条规则

**日期开头。一件事写一份就用 `.md`；一件事要写多份就用同名目录。**

不按类型分目录，因为类型会打架（同一个案子既是"事故复盘"又是"设计调研"），
而**日期永远是确定的**。类型只在这张表里记，只在一处维护。

目录里按时间排下来就是一条开发史。

## 写作要求

每份归档文档**开头必须有横幅**，回答三件事：该不该继续读、结局是什么、什么时候的事。

```markdown
> ⚠ **已归档**。现状见 `docs/features/xxx.md`（相对链接）。本文只保留当时的排查过程与被推翻的
> 中间结论，**追溯「这个结论怎么来的」时才需要读**。
>
> **结局**：<一句话——最后怎么解决的；没解决就说没解决>
>
> - **起止**：YYYY-MM-DD ～ YYYY-MM-DD    ← 事件起止，不是归档动作那天
> - **触发**：<用户原话或现象>
> - **涉及**：<代码路径>
```

**没有现状文档的**（审计、体检），横幅改成：

```markdown
> ⚠ **已归档**。本文是一次性记录，没有对应的现状文档，**日常开发不用看**。
```

### 三条硬性要求

1. **不许留裸的过期状态行** —— 「状态：待真机验收」「P1b 未验证」这类从写下那天就过期，
   要么删掉，要么标上日期并说明之后发生了什么。**状态归 `CHANGELOG.md`。**
2. **被证伪的结论要标出来** —— 标题上加 `❌ 已证伪` 或正文写清"这一条 10-18 真机推翻了"，
   不许裸着留在正文里让人当结论读。
3. **精简只留"定下了什么"** —— 逐日流水、探查命令、跑了几遍，压成索引表；
   原文用 `git log --follow` 查。**保留的是判断，不是过程。**
