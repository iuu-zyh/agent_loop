# 图片进上下文（10-18 重做 09-13 的「图片寿命 = 当回合」）

> ⚠ **已归档**。现状见 [`docs/features/image-context.md`](../features/image-context.md)。本文只保留当时的排查过程与被推翻的中间结论，**追溯「这个结论怎么来的」时才需要读**。
>
> **结局**：五个决定全部落地：字节落图片仓、账本只记 ref、发前投影成 data URI、ingest 时记 token 估算、GC 按 keep-set 回收。09-13 的「图片只进当回合」作废。
>
- **起止**：2026-09-13（旧版）～ 2026-10-18（重做完成）
- **触发**：图片只活一回合，玩家回头就看不到了
- **涉及**：`storage/images.py`、`agent/dialogue_agent.py`

## 一、改之前是什么样（问题在哪）

| 环节 | 旧行为 | 后果 |
|------|--------|------|
| 收图 | `ChatHub.handle_message` → `DialogueAgent.send(images=)` 只取 `url`，存进**内存**侧表 `_turn_images {消息id: [dataURL]}` | 图像字节没有任何持久化 |
| 拼请求 | `_attach_turn_images()` 只给「本回合领到的」消息浅拷一份挂图 | 同一回合多步都看得到 |
| 回合收口 | `self._turn_images.pop(id)` | **下一回合就没了**，账本里只剩 C# 拼的 `[图片：xx]` 占位文本 |
| 记账 | 图片的 token 只体现在那一轮请求的 `prompt_tokens`（实测） | 估算口径（`compaction.meter`）里图片 = 0 token；压缩阈值、面板「上下文≈」全都看不见图 |
| 删除/压缩 | 只作用于 `surface` 上的消息节点 | 与图片无关（因为图片本来就不在账本里） |

两个真正的痛点：
1. **模型失忆**：玩家发一张截图问「这人是谁」，下一轮模型只看到 `[图片：xx]`，答不上来；
   而 `[图片：xx]` 还是玩家消息正文的一部分，模型会把它当成「玩家提到过一个叫 xx 的文件」。
2. **记账不全**：图片是上下文里最贵的东西（一张 1024×1024 约 1.4k token，抵 1.4k 个汉字），
   却既不在估算里、也不在压缩阈值里。

## 二、设计（五个决定 + 理由）

### ① 字节存哪：外部图片仓，账本只记 `ref`

```
<sessions_root>/images/<scope_dir>/<sha1>.<ext>  ← 字节（按内容哈希命名，天然去重）
session.log 里：{"type":"image","ref":"images/<scope_dir>/<sha1>.png", ...}   ← 只有引用
```

`scope_dir` 是 NPC id 的**定长安全目录名**（`storage/images.py::scope_dir`）：可读前缀
（百分号编码后截断 40 字符，去首尾 `.`/`%`）+ 短哈希（原始 id 的 sha1 前 8 位）⇒ 长度恒 ≤49、
不会撞名、恒不是 `.`/`..`。**不要退回"直接 quote(id)"**：一个汉字编码后占 9 个字符，
8 个汉字的名字就会撑破 ref 的 64 字符上限 ⇒ 该 NPC 的图**每一张都落不了盘**（10-18 复核抓到的真 bug）。

为什么**不**把 base64 直接塞进消息块（那样确实最省事）：
- 账本是**只追加**的：删除 = 追加一条 `history/delete` 注记（`session/history_ops.py` 文件头），
  压缩 = 追加一条 `replace`。块一旦写进 log，**物理上永远回收不了** —— 一张 1.5MB 的图删掉之后
  仍然占着 log、仍然会在每次 `load_session` 被解析、仍然被 `save_session` 的**全量重写**搬一遍。
- `save_session` 是整份重写（`storage/persistence.py`），每次固化都要把整个 log 序列化一遍 ——
  内联 base64 会把这件事从「毫秒」变成「几十毫秒~上百毫秒」。
- 反过来，文件是**可删对象**：删除/压缩把消息从 surface 剔掉之后，文件就能回收（§四）。

代价（都要显式处理，见 §三）：读盘 IO（内存缓存）、文件可能丢失（降级不崩）、
文件与账本两份真相（靠「账本的 ref 是权威、文件缺失即降级」定序）。

### ② 账本里的表达：**就是消息的一部分**，不是独立事件

```jsonc
{"type":"user/message","data":{
   "role":"user",
   "content":[
      {"type":"text","text":"[1年1月3日] 这人是谁\n[图片：屏幕截图.png]"},
      {"type":"image","ref":"images/云含/ab12…cd.png","mime":"image/png",
       "name":"屏幕截图.png","w":1024,"h":576,"kb":220,"tokens":786}
   ],
   "id":"…"}}
```

为什么不做成独立事件（`image/attach`）：
- `Session.derive_messages()` 逐节点取消息 → 图片**天然出现在上下文里**，零改动；
- 删除/压缩全是 `surface` 上的**机械剔除**（`SurfaceManager._apply_delete` / `replace`）——
  图片跟着消息一起走，**不需要第二套生命周期**。做成独立事件就必须在 derive、surface、
  删除、压缩、重放、UI 六个地方各写一遍"图片跟着哪条消息走"，那是最容易漏的形状。
- `_apply_speaker_labels`（`玩家：` 前缀）已经按"只改第一个 text 块"实现，图片块原样透传。

### ③ 发给模型的那一份：`ref` → data URI（"发前投影"）

沿用既有纪律（`_attach_turn_images` / `_apply_speaker_labels` 同一套）：
**浅拷贝 + 新 content 列表，绝不原地改** `derive_messages()` 返回的对象
（那就是账本事件的 `data` 本体；原地改 = 把 base64 永久写进 log，正是旧注释警告的事故）。

三条降级（只影响**这一份请求**，账本一字不动）：
- 模型明确不支持图片（`llm.supports_image is False`）⇒ 丢弃图片块。
  旧实现是 `openai_client` 直接抛 `ModelError`；图片进了历史之后，一次配置错就会让**每一回合都 400**，
  必须改成"静默丢图 + 警告日志"（占位文本还在，模型知道当时有过一张图）。
- 文件不在了（被回收/手删/迁移丢）⇒ 丢弃 + `WARNING`。
- `ref` 非法（`../` 之类）⇒ 丢弃 + `WARNING`。

### ④ token 记账：ingest 时落一个估算值，`meter` 用它

- C# 送来的每条图都带 `w/h/kb`（`ImageInput`），`DialogueAgent` 在**收图时**算一次
  `tokens`（`compaction/meter.estimate_image_tokens`），写进块里。
- `meter.estimate_blocks` 见到 `image` 块就用这个数（缺了按 `w/h`，再缺按 `kb`，最后 85 兜底），
  **绝不 `json.dumps` 整块**（data URI 会被估成几万 token —— 这是旧实现留给未来的地雷）。
- 于是压缩阈值（`Compressor.maybe`）、面板「上下文≈」（`refresh_context_pressure` →
  `set_surface`）自动把图算进去；图片被删/被折走之后自然不算 —— **不需要额外减法**。
- 口径声明：这是**估算**（厂商口径不同：Anthropic ≈ px²/750，OpenAI high-detail ≈ 85+170×切片，
  取两者较大者做保守估计）。真实花费永远以实测 `usage` 为准，估算只喂阈值与 UI 的「≈」值。

### ⑤ 回收：GC = 「surface ∪ 待投递筐」之外的全部删掉

```python
keep = refs(surface 上的消息) ∪ refs(agent/inbox/spliced 重放出的两只筐)
for f in images/<npc>/*: 
    if f not in keep: unlink
```

- 触发点只有两个：`history_ops.append_delete`（删回合 / 群窗删消息）与
  `Compressor._replace`（压缩折走）。**resume 不跑** —— 账本读残/写残时 surface 会缺节点，
  那时跑 GC 会误删还在被引用的图；崩溃残留的孤儿图（几 MB 封顶）比误删便宜得多。
- **必须**把待投递筐算进 keep-set：压缩发生在**回合边界**，此刻玩家刚发的那条带图消息
  还在筐里（还没落面），只看 surface 会把它的图删掉 ⇒ 图片静默丢失。
- 回收是**幂等**的、失败只记日志（删不掉不影响账本）。

## 三、边界与风险

| 风险 | 处理 |
|------|------|
| 每轮重发历史图 → 请求体积变大 | 这是"进上下文"的固有代价；C# 侧已把长边压到 ≤1024、单张 ≤1.5MB。**好处**：前缀稳定了 —— 旧实现"图在下一轮消失"会让那条消息之后的前缀每轮都变，prompt cache 每次从这里断掉 |
| vision token 估偏 | 只影响阈值/UI 的「≈」，实测 `usage` 仍是权威；口径集中在 `meter`，一处可调 |
| 图片文件丢失/存档搬迁 | 降级成占位文本 + WARNING，**不崩、不重试** |
| 老账本（只有占位文本） | 零迁移：没有 image 块就没有图，行为与今天一致 |
| 老 DLL / 无图消息 | 帧里没有 `images` 字段 ⇒ 走原路，逐字节不变 |
| 群聊发图 | C# 已拦（"群聊不支持发图"）；Python 侧 `handle_room_message` 不接 `images` |
| UI 历史 | `history.project_ui_history` 只取 `text` 块 ⇒ 气泡里仍是 `[图片：xx]` 占位，不受影响 |
| 压缩材料 | image 块一律渲染成 `[图片]`（**不读字节、也不 dump 成 JSON**）；玩家消息正文里 C# 已拼好 `[图片：xx]` 时**不再重复补一行**（否则摘要以为附了两张图，10-18 复核补的加固） |

**两个实测出来的坑（都已修，别踩回去）**：

1. **变异脚本必须绕开字节码缓存**：仓库在 drvfs（Windows 盘）上，`write_text` 还原源码后
   mtime 与变异那次可能落在**同一秒**粒度里 ⇒ CPython 的 "mtime+size" 判据认为旧 pyc 仍有效
   ⇒ 跑的是上一轮的代码。后果是"真变异报没捕获"+"还原来个假绿"+**变异被留在源码树里**
   （实测发生，且当时正并行跑别的测试，观察全部失真）。现在每次跑测给一个全新的
   `PYTHONPYCACHEPREFIX`（等价于不读也不写任何旧 pyc）。
2. **压缩材料里图片只出现一次**：玩家消息正文里 C# 已经拼好 `[图片：文件名]`，
   材料再补一行 `[图片]` 会让摘要以为附了两张图（纪要是永久节点，错了会被一直喂回来）。

**顺带**：`prompts/sections/harness_identity.txt` 那句「图你已经看到了，不必追问文件名」
在旧实现里其实**只在当回合成立**（下一回合图就没了）—— 现在它才是真的。故提示词不动。

## 六、独立复核（10-18）与收口

交付后另起一个子代理做了对抗式复核（只读 + 自建变异脚本，跑完逐字节还原）。结论
**有条件通过**：运行时无阻塞级缺陷，但按本工程"改坏了必须会红"的尺子，有 4 处防线**当时没有测试**，
另有 1 个真 bug + 3 处少加固 + 4 处文档不一致。已全部收口：

| 复核发现 | 处理 |
|---|---|
| **F1（真 bug）** NPC 名 ≥8 个汉字 ⇒ `quote(id)` 后 >64 字符 ⇒ ref 非法 ⇒ **该 NPC 的图每张都落不了盘**（只有 WARNING） | `storage/images.py::scope_dir`：编码截断 + 短哈希，定长 ≤49；顺手消掉 `.`/`..` 可当 scope 的加固问题 |
| **洞1/洞2（阻塞级测试洞）** GC 的 fail-closed（surface 读残 / 待投递筐重放失败 ⇒ **放弃回收**）注释写着"绝不返回空集"，但没有任何测试；改坏了会**全删** | 新增 `test_gc_aborts_when_surface_is_corrupt` / `test_gc_aborts_when_inbox_replay_fails` + 变异 Q/R |
