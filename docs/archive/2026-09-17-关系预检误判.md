# 同一个预检把引擎的拒绝撬成了强行落刀：夫妻关系被换成师徒

> ⚠ **已归档**。现状见 [`docs/features/brain-liveness.md`](../features/brain-liveness.md)。本文只保留当时的排查过程与被推翻的中间结论，**追溯「这个结论怎么来的」时才需要读**。
>
> **结局**：★ 更正了 D.14 的码值方向：`0` 才是「引擎已执行」。**这条是 D.14 的续集与更正**。

---

**症状**（用户："为什么收徒又成功了？我自己游戏实际发现关系被覆盖了，由原来的妻子变为了师父"）：
10:50 那次收徒明明被引擎拒绝（D.14），16:14 同一个人、同一对关系、同一个 op **却成功了** ——
代价是用户原有的**夫妻**关系被清掉、换成了师徒。

**事故链（每一环都有反汇编/日志实锤）**

1. **语义读反了**（D.14 那张表的错，源头是照抄神识传音的日志写法）：
   `WorldUnitBase.CreateAction(action,isTip)` @`0x32B8D40` 的真身是
   `code = action.IsCreate(isTip); if (code != 0) return code;` 然后才 `action.Create();`
   ⇒ **0 = 同意（只有 0 会执行 `OnCreate`）；非 0 = 拒绝，数字是原因码**。
   `WorldUnitBase.IsCreateAction(action,isTip)` @`0x32BDAC0` = `action.IsCreate(isTip)`（同源）。
2. **`IsCreate` 有副作用**：`UnitActionBase.IsCreate(isTip)` @`0x35083B0` 先
   `this.isTip = isTip; if (IsDayCost(day) == 0) this.isCreateCall = true;`
   —— 而 `CreateAction` 开头就是 `if (!action.isCreateCall) { …校验… }` ⇒ **该标记一旦置位，
   后续 `CreateAction` 会跳过全部校验直接 `Create()`**。
3. **我们把预检实例递给了落刀**（11:46 那版 `StartRelationAction.onOk`）：
   `IsCreateAction(act, true)` 拿到 **3**（拒绝），却按反的读法当成"可建"，紧接着
   `CreateAction(act, …)` 因为 `isCreateCall` 已置位 → 免检直通 → `OnCreate()` 执行。
   人在 `Player.log` 里能看到的只有 `你与姜萌结为师徒。`：**引擎没放行，是我们撬开的**。
4. **`OnCreate` 是覆盖语义**：@`0x36FCF10` 先 `GetRelation(对方)` 读旧关系，再
   `ClearRelation(unit,toUnit)`（@`0x36FC370`，**双向各一次**）再写新关系 + `AddIntim`。
   `RelationData.GetRelation` @`0x3CF2390` 是"先命中先返回的单个枚举"（优先级 父母 > 子女 > 私生 >
   兄弟 > 义父母 > 义子女 > 义兄弟 > **夫妻 > 道侣 > 师父 > 徒弟**）⇒ 夫妻若还在，界面只会显示夫妻；
   用户看到师父 ⇒ **那条夫妻确实被删了**（不是被盖住）。
5. **为什么 10:50 会"失败"**：老代码只调了一次 `CreateAction(act,false)`（没有预检污染），
   引擎按规矩返回 3 → `Create()` 不执行 → 关系簿一字未动。**那次引擎的拒绝是真的。**
6. 顺带纠正 D.14 的两条猜测：收徒/拜师的引擎门槛**不是**境界、也不是师徒位 ——
   `UnitActionRelationSet.IsCreate` 只有三条：基类日耗、码 2（目标是自己）、
   **码 3（`relationData.IsRelation(对方, None)` 不成立 = 两人之间已经有一条关系）**。

**码表**（权威注释在 `csharp/tools/RelationTool.cs` 顶部（原 `ToolExecutor.cs` 关系段）；渲染措辞在
`tools/text_render.py:_RELATION_ENGINE_CODE`，两处必须同步改）：
`0` 同意｜`2` 目标是自己｜**`3` 两人之间已有一条关系**｜`4` 认义父母另有前置｜`5` 同性不能成婚/道侣｜
`6` 异性不能结义｜`7` 已婚（任一方 `married` 已占用）｜`8` 结婚前必须先结为道侣｜`9` `type=None` 解除路径。

**由此定死的引擎模型**：`married` 是**单个字符串**、其余关系字段是列表，但 `GetRelation` 只返回**一条**，
且缔结类的 `IsCreate` 要求 `GetRelation == None` ⇒ **"道侣 + 师徒共存"在本引擎不存在**，
只能覆盖。本工具**不做覆盖**：预检拒绝就如实报"未能结下"，要改结必须先解除原有关系。

**本轮落地**

* C#（`ToolExecutor`）：新增一次性实例的 `ProbeRelationSet(...)`；预检**挪到弹窗之前**
  （引擎说不能建就不让玩家白点一次"同意"），`precheck > 0` ⇒ `create_ret = -1`（未落刀）收口；
  落刀改成**现 new 现用、只调一次**、返回码进 `create_ret`（0 = 已执行）；`relation_before` 在落刀前再取一次。
  `DirectEstablish`（免窗）同款；`StartBreakWith` 预检/落刀分实例，成败判据从反的 `created == 1`
  改成 **`created == 0`**（并补"原生没跑起来/跑完关系仍在 → 字段直写兜底"）。
* **赠礼那条路的免检写成明示**：`UnitActionRoleGive.IsCreate` 真机 NRE、`CreateAction` 只在码 0 时
  `Create()`，所以一直是"先探一次"的**副作用**在暗中撑着它 —— 现在显式
  `((UnitActionBase)giveAction).isCreateCall = true;` + 注释写清"这门对赠礼是坏的、我方已自行校验"，
  不再依赖调用顺序（同一个副作用在关系那条路上就是这次事故的成因）。
* Python（`text_render`）：语义整条反转（`precheck != 0` ⇒ 预检就拒·未落刀；`create_ret != 0` ⇒
  落刀被驳回；`create_ret == 0` 却读不回 ⇒ "需人工核对"），引擎码翻成中文；**成功回执新增覆盖告警**
  （`relation_before != relation_after` 时点明"引擎把原有的「X」换成了「Y」"—— 事故真正伤人的地方
  就是这里一声不吭）；解除类改成按 `create_ret != 0` 解释"为什么走字段直写"。
* `tools/schemas.py` 的 `social_relation` 描述补一句引擎规则（一对人只记一条，缔结类撞码 3 会被拒、
  本工具不做覆盖）。

**验收**：`tests/test_relation_diag_contract.py` 重写为 **22 项**（含"注释表 0 = 同意"、"两张码表同键"、
"预检绝不复用实例"、"预检拒绝不落刀"、"成功路径必须点明旧关系被换掉"、"赠礼免检必须显式"）；

两条最初漏掉的（"已经结下…请如实告诉玩家未能结下"这种自相矛盾的回执）已把断言收紧到**判决句开头**。

**真机验证待办**：重启后试一次收徒（对方已有关系）应回"引擎码 3 · 未落刀"且**不弹窗**；
一次干净的一对（无任何关系）应正常结成；`[Relation] 预检拒绝 引擎码=3 … 未落刀` 会出现在日志里。
