# `llm.timeout` 的两个身份 —— 45s 是怎么把一个正常吐字的流砍断的

> ⚠ **已归档**。现状见 [`docs/features/brain-liveness.md`](../features/brain-liveness.md)。本文只保留当时的排查过程与被推翻的中间结论，**追溯「这个结论怎么来的」时才需要读**。
>
> **结局**：这一轮只澄清了语义；移除「整趟挂钟」是下一轮 D.21 做的。

---

排 D.18 那一幕时顺手澄清了一个**语义双身份**，它才是这次事故的直接原因：

```
config llm.timeout = 45
  ├─ ① `_attempt_deadline` → asyncio.wait_for(_call_stream(...), 45)   ← 整趟尝试的**挂钟**上限
  └─ ② `_open_stream` 下发给 SDK 的 httpx read timeout（相邻两块之间的间隔）
```

**① 才是长回复的杀手**：数据块到达**不会**重置它，所以"吐字很顺、总时长超了"的回复照样被砍
（本次：382 token 全是思考、流得好好的，第 45.03 秒被砍）。而 ② 只在"卡住不动"时触发。
`llm/openai_client.py` 的 `__init__` 注释此前只写了 ② 的语义（"持续吐字的长回复永不被它砍掉"），
**与代码行为相反** —— 已改成把两个身份都写明；`config_loader.py` 里同样过时的注释也一并改掉
（`config.example.json` 的 `_超时与重试说明` 一直是**对的**：写着"整段计时、收到数据块不会重置"）。

**数值调整（原 45 / 180 / 100 / 1 → 现 120 / 180 / 150 / 1）**：

| 键 | 旧 | 新 | 依据 |
|---|---|---|---|
| `llm.timeout` | 45 | **120** | 实测首字延迟最高 21.8s、成功回合最长 33s；思考型模型（mimo-v2.5）一条长回复在 45s 只剩不到三成余量。代价 = "真卡住"要多等这么久才判死（想更快发现卡死就调小） |
| `llm.total_budget` | 100 | **150** | 单趟上限抬到 120 之后，100 会把第二趟压成负预算（第一趟就吃光）⇒ 超时后连一次重试都做不成。玩家最坏等待 = min(150, 120×2+退避) = **150s**（原 90.5s） |

改的是三处：`config_loader.py` 的 DEFAULTS、`config.example.json`（模板）、以及**部署目录里那份
用户实际配置**（`ModAssets/config.json`，只动这两个数值，api_key / model / headers 一律不碰）。
回退备份：`backup/deploy_20260917_1649/`。

**仍未做（留给下一轮）**：`timeout` 的"挂钟上限"与"块间隔超时"要不要拆成两个键（拆开就能
"长回复给足时间 + 卡住 45s 就判死"）；以及"**只推了 think 就超时**算不算可安全重试"
（当前一刀切"推过 token 就不重试"，防的是正文重复展示）。
