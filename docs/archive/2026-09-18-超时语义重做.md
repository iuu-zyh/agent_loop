# 超时语义重做：只有「存活看门狗」，没有「整趟挂钟」

> ⚠ **已归档**。现状见 [`docs/features/brain-liveness.md`](../features/brain-liveness.md)。本文只保留当时的排查过程与被推翻的中间结论，**追溯「这个结论怎么来的」时才需要读**。
>
> **结局**：「整趟尝试挂钟」这个身份被**删除**，只留首字看门狗与停顿看门狗。

---

**用户原话**：
> 我需要首token超时，以及判断当前是否在输出的超时，**整趟耗时 完全不合理**，如果长程的任务
> 怎么可以去使用这个作为超时的依据！只有首token超过一段时间不响应那么报错，或者回复中途
> 长时间没有继续的话才显示超时。

这是 D.18.1 那条"留给下一轮"的收口：`llm.timeout` 的**两个身份**被彻底拆开，其中"整趟尝试的
挂钟上限"这一个身份**删除**（它就是 09-17 把姜萌的思考流在第 45.03 秒砍断的那把刀）。

**判据对照（旧 → 新）**

| 阶段 | 旧（≤09-17） | 新（09-18） |
|---|---|---|
| 连接 / 排队 / 响应头 / 首字 | 无独立判据（被"整趟挂钟"顺带覆盖） | **首字看门狗** `llm.timeout` = 120s：请求发出 → 第一个**内容块** |
| 吐字中途 | ①**整趟挂钟**：`asyncio.wait_for(_call_stream(...), timeout)`，收到数据块**不重置** | **停顿看门狗** `llm.idle_timeout` = 60s：相邻两个内容块之间 |
| 对端 SSE 心跳/注释 | 会重置 httpx read 计时器 ⇒ 旧的 ② 永不触发 ⇒ 才不得不加 ③ | **天然免疫**：看门狗数的是"解析出来的内容块"，心跳不是内容 |
| 整趟耗时 | ③ `llm.total_budget` = 150s（**默认开**） | **默认关**（0）；显式设了才把两个看门狗收缩进剩余额度 |
| httpx read timeout | 判据之一（②，块间隔） | **降级为背板**：= 两个看门狗之和，只负责让"被放弃的读线程"最终退出 |

**为什么"整趟耗时"必须从判据里删掉**：45s 的预算里**包含首字等待**（实测 p50≈13.5s、最高
28.5s），留给输出的只剩十几秒；而"回复长"和"卡住"是两件毫不相干的事 —— 一条一直在正常出字的
长回复不该被按秒砍断。存活判据只该问"多久没有新内容"，不该问"已经过了多久"。

**实现（`llm/openai_client.py`）**

* 消费循环里的 `await queue.get()` **本身就是看门狗**：
  `_guarded(queue.get(), _watchdog_seconds(idle_timeout if first_seen else timeout, budget_deadline))`；
  `first_seen` 在队列收到第一项时置位 ⇒ 阶段切换。这两个数都是"距上次新内容多久"，与总时长无关。
* `_guarded` = `asyncio.wait_for` + 抛**内建** `TimeoutError`（`_is_retryable` 认得 ⇒ 零产出的
  首字超时**照旧可重试**）。文案分型并自带单位：`首字超时：模型一直没开口` /
  `输出停顿超时：模型说到一半卡住了`，统一后缀「N s 内没有任何新内容（存活看门狗，与整趟耗时无关）」。
* **坑①：开流那一步必须自己进看门狗**。`_open_stream` 在 openai SDK 里是**同步**的
  （`create(stream=True)` 会一直等到**响应头**），删掉整趟挂钟后"卡在建连/等响应头"就没有任何
  判据了 —— 现在它走 `to_thread` + 首字看门狗，超时同样抛 `TimeoutError`。
* **坑②：看门狗放弃时读线程还阻塞在 socket 上**（Python 杀不掉线程）。主协程 `_close_quietly(stream)`
  尽力叫醒它（幂等、可重入、失败无副作用）；不做的话线程要等背板到点才退出，连接迟迟不还池。
  背板取**两个看门狗之和**，就是为了让"看门狗先响、httpx 后响"成为必然 —— 同值会抢跑，
  报错文案会退化成 SDK 的 `ReadTimeout`（"读取超时"），玩家看不出是"没开口"还是"卡住了"。
* **坑③：三态语义**。`idle_timeout` 缺省（不写）= 回落 `timeout`；显式 `0` = **关掉**它；
  正数 = 用它。`0/null` 在 `timeout` 上 = 不设看门狗。归一放在构造器（`_positive_or_none`），
  否则直接 `OpenAILlmClient(timeout=0)` 会得到"0 秒看门狗 = 立刻超时"这种反向事故。
* **非流式（唯一调用方 = 上下文压缩）没有"中途"可言**（一个字节都不发，要么整段回来要么没有）
  ⇒ 它只有首字语义，上界 `timeout_nonstream` = 180s，且 `total_budget` **不约束它**
  （拿玩家等待上限去卡后台压缩只会静默废掉压缩）。
* `_budget_deadline` + `_watchdog_seconds` = `min(阶段看门狗, 距绝对上限还剩多少秒)`；上限没设时
  后者恒等于阶段值 ⇒ **不存在任何形式的整趟判据**。"0 = 不设顶"有两道冗余防护
  （`not self.total_budget` 与 `b > 0`）—— 变异脚本因此把这两处**一起**回退才算一条有效变异。

**数值（仅 `llm` 块）**

| 键 | 旧 | 新 | 说明 |
|---|---|---|---|
| `llm.timeout` | 120 | **120**（语义改） | 从"整趟挂钟"改成**首字看门狗**；实测首字最高 28.5s，留约 4 倍余量 |
| `llm.idle_timeout` | —（无此键） | **60** | 停顿看门狗：正常块间隔是毫秒级（实测 ≈16ms/token），60s ≈ 上千倍，只在真死时触发 |
| `llm.timeout_nonstream` | 180 | 180 | 非流式（压缩）等待上限，量纲本来就不同，不动 |
| `llm.total_budget` | 150 | **0（关）** | 降级为**可选**绝对上限；默认不参与任何判据 |
| `llm.retries` | 1 | 1 | 不变 |

默认值下的最坏等待 = 首字看门狗 120 × (retries+1 = 2) + 退避 0.5 ≈ **240s**，
且**只有"从头到尾一个字都没有"才会走满**；一直在出字就不会被判超时。

**配置与面板（四处 + 三层）**

* 值落在四处：`config_loader.DEFAULTS`、`config.example.json`（模板）、`config.json`（本地）、
  以及**部署目录那份** `ModAssets/config.json`（只动这几个数，api_key/model/headers 一字不碰）。
  `config_store` 白名单加 `idle_timeout`（面板无此行，但手编的值要能被归一/夹取，0–600）。
* 面板侧三层：预制件里那两行标签是**烧死**的（改它要重打 AB）⇒ `AbConfigPanel.RelabelRow`
  **运行期改文案**（"AI 首字超时秒（即时生效）" / "AI 硬顶秒·0=不设限"，节点缺失时静默跳过）；
  `ConfigUiBuilder`（代码版面板）同义；`ConfigPresenter` 的**回填默认值与悬停说明**重写。
* ★ 面板文案里**不能出现 markdown 的 `**`** ★：UGUI 的 `Text` 不渲染 markdown，会原样显示星号
  （本轮把刚写进去的两处清掉了）。强调用 `★`／「」，与既有文案一致。
* 硬顶那行的提交语义**刻意与其他三个键相反**：`timeout`/`timeout_nonstream`/`retries` 是
  "空/0 = 不提交（保持文件原值）"，而硬顶 `0` 是**合法且会提交**的值 —— 它是默认值，
  也是玩家关掉一个手编过的 150 的唯一入口（留空只会保持原值）。

**仍未做（明确留给下一轮）**
