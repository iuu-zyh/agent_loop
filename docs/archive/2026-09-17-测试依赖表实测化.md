# 测试工具链：依赖表从静态猜改成实测 + 并行

> ⚠ **已归档**。本文是一次性排查记录，没有对应的现状文档，**日常开发不用看**。
>
> **结局**：依赖表改为实测采集（`--probe`），并行分片沿用至今 —— 现在的实现在 `scripts/dev/`。

---

**先量再改**（全部实测，不是估算）：

| 项 | 数值 |
|---|---|
| 全量 `pytest tests/`（10-17） | 1460 项 / **94.6s**（09-17 那版记的"893 项 / 37s"已过时 —— 套件长了 63%） |
| 全量（10-17 重做后，12 分片并行） | **15.6s** |
| 每次 `pytest` 进程的固定成本 | **~1.4s** |
| 变异脚本 | 关系 38 轮 ≈ **55s**、赠送 18 轮 ≈ **40s** —— **纯进程启动**，比全量还贵 |
| `test_run_tests_for_contract.py` 单文件 | **30.5s**（占全量 32%！`build_map()` 无缓存、被调 11 次） |

⇒ 结论：**全量本身不贵，贵的是"每轮起一个 pytest"和"我保守地反复跑全量"**。

**一、`scripts/dev/run_tests_for.py`（改哪儿跑哪儿）—— 10-17 推倒重做**

旧版按 AST 静态扫"测试源码里出现过哪些路径字面量 + import"。10-17 用实测探针对拍，
发现它**两头都错**，于是整条路线换掉：

| | 旧静态映射 | 实测真相 |
|---|---|---|
| 改 `ToolExecutor.cs` 影响 | 252 项 | **87 项** |
| 改 `agent_loop.py` 影响 | 253 项（触发全量闸门） | **1 项** |
| 漏掉的真实依赖 | — | **172 个源文件 / 346 处** |

三个具体病灶：
① **闸门打死在最该生效的地方**：旧版 `FANIN_UPGRADE=15`（扇入 ≥15 就升级全量），
而扇入最高的 6 个文件 —— `ws_channel.py` 35、`agent_loop.py` 33、`bridge.py` 20、
`ToolExecutor.cs` 18、`text_render.py` 16、`ModMain.cs` 16 —— **恰好是本仓最常改的**。
**闸门已删除**，不再有"改一个文件跑全量"这条路。
② **`--changed` 有目录盲区**：旧版只 glob 根 `*.py` + `csharp/` + `tools/` + `scripts/` + `docs/`，
`agent/ transport/ room/ session/ llm/ storage/ config/ prompts/` **一个都扫不到**。
实测 `touch agent/initiative.py` 之后它报"没扫到比改动新的源文件 ⇒ 全量" —— 想省时间却跑了全量。
③ **静态扫不出 `rglob`**：`test_log_setup.py` 用 `rglob("*.py")` 扫全仓（静态漏 58 处）、
`test_run_tests_for_contract.py` 读 `tests/*.py` 建映射（漏 101 处）。

**依赖表现在来自实测**：`scripts/dev/_read_probe.py` 是个 pytest 插件，跑全量时把这些全拦下来 ——
`Path.read_text` / `open` / `SourceFileLoader.get_data`（模块导入）/ `Path.glob`（扫描范围）/
`sys.monitoring` 的 `PY_START`（**真的执行了哪个模块的代码**）。产出 `.depmap.json`，
`--probe` 重采（~2.5 分钟，**要求全量跑绿**才装 —— 坏状态的执行路径不同，采到的是错的依赖表；
鸡生蛋时用 `--probe --force`）。

三条归属规则：模块导入 ⇒ **整个测试文件**（import 只执行一次，落点取决于执行顺序）；
用例体内显式读 ⇒ **该用例**；模块级读 ⇒ **整个测试文件**。另加两路补盲：
静态 import 表（`sys.modules` 有缓存，第二个 import 同一模块的文件不会再次触发 `get_data`）、
目录扫描范围（**新增文件**在快照里不存在，但落在扫描范围内仍要命中）。

命中规则（并集，宁多勿漏）：实测读过 ⇒ 该用例；实测**执行过** ⇒ 该用例；
直接 import / 模块级读过 / 扫描范围覆盖 ⇒ 整文件；
测试文件自身或它 import 的东西比快照新 ⇒ 整文件。

**并行**：按文件分片 + 按历史耗时 LPT 装箱，每片一个 pytest 子进程（`--jobs`，默认上限 12）。
**不引入 xdist**：进程隔离更干净，且本仓 13 个测试用**写死的** `/tmp/agent_loop_test_*` 目录，
按文件分片天然不会互相 `rmtree`。耗时表 `.test_durations.json` 每次跑完用 `--durations=0` 更新。

实测（10-17）：改 `ToolExecutor.cs` ⇒ **180 项 / 8.6s**（旧版触发全量 1460 项 / 94.6s）；
改 `text_render.py` ⇒ 219 项；改 `bridge.py` ⇒ 336 项；全量 `--all` ⇒ **15.6s**。
契约 `tests/test_run_tests_for_contract.py`（**17 项**，钉的是可靠性属性而不是"表长什么样"）。

**★ 端到端验证是唯一有说服力的判据 ★**：`scripts/dev/verify_subset_soundness.py` ——
对源文件施加变异 → 跑**全量**记录真红了哪些 → 问"子集是否覆盖"。
两个判据：**A（实用，必须过）只跑子集时它自己会不会红**（防**静默放行**）、
B（严格）全量新增红的每一条是否都在子集里。它当场抓出过两个真漏：
(i) **相对 import 被整段跳过**（`if node.level: continue` 让 `from ..tools.text_render import render`
没被记录）⇒ 变异 `text_render.py` 后全量红 48 条、子集漏 8 条；
(ii) **改测试文件时只跑了它自己**，没跑"执行了它代码"的其他测试文件。

**二、`scripts/dev/_mutate_lib.py`（10 个变异脚本共用的跑测层）**

① 同进程多轮（`pytest.main`）；② 无装饰器/非 async 的纯契约测试走**直接调函数**的快速路径
（pytest 每轮固定 0.6s vs 直调 ~10ms）。等价性靠两件事：每轮 `_purge_project_modules()` 强制重新
import（否则**模块级**读源码的常量拿旧内容 ⇒ **假绿**）、`-p no:cacheprovider`；
遇到 fixture/装饰器/async/`skip` **立刻回落 pytest**（不能把"本应 skip"跑成 fail ⇒ **假捕获**）。
实测：关系 38 轮 55s → **10.7s**；赠送 18 轮 40s → **5.3s**，两边都仍是 38/38、18/18 全捕获。

**三、两个真实踩坑（都由"跑全量"兜住的）**

1. **`cwd=` 换了目录就不能同进程跑**：`mutate_check_manual_identity.py` 靠 `cwd=ROOT.parent` +
   `agent_loop/tests/...` 避开同名外壳文件 `agent_loop.py`（`python -m pytest` 会把 cwd 塞进
   `sys.path[0]`）。第一版同进程化忽略了这个语义 ⇒ 相对路径解析不到 ⇒ 它的**基线自检当场变红**
   （脚本如实报错，没有假绿）。现在 `cwd` 不同或给了 `env=` 一律走真子进程。
2. **变异注入泄漏进源码树**：`mutate_check_manual_identity.py` 的脚手架自检会往 `contacts_store.py`
   注入一个 no-op（`return {"added": True, "count": 0}`），而备份集合只由"本次选中的变异"决定 ——
   跑 `... contract`（只跑契约层）时那个注入**没人还原**，源码树里就躺了一行，15 个 contacts 测试
   跟着红。**这正是"全量不能省"的实例**：子集跑绿了，泄漏照样在。现在自检目标一律纳入备份/还原/校验。

**★ 新增功能 / 新增测试时的行为（10-17 专门处理过）★**

这是这套机制最容易出问题的地方 —— 快照里没有的东西，静态和实测**都**不知道它依赖什么。
实测过第一版：新增 `tests/test_zz_new_feature.py` 后，`run_tests_for.py <源文件>` 与
`--changed` **一条都不会选中它** —— 新功能配的新测试等于没跑，而且看起来是绿的。现在：

| 情形 | 行为 | 为什么 |
|---|---|---|
| **新增测试文件**（快照里没有） | **一律整文件跑**，并在 `Selection.forced` 里单列 | 对它一无所知（不知道它读什么、执行什么），只能整文件跑 |
| **改了已有测试文件**（mtime ≠ 快照录的） | 该文件**整文件跑** | 它的依赖可能已经变了，快照对它不可信 |
| **新增源文件** | 由**目录扫描范围**兜住（落在某契约测试的 `rglob` 范围内就命中它） | 探针记的是"读过哪些文件"，新文件上轮没读过 |
| **删除 / 重命名源文件** | `--changed` 用快照里记的源文件清单**反查**（删除的文件没有 mtime，扫不到） | 否则"改名了却全绿" |

判据用**逐文件比对 mtime**，不是"比 `probed_at` 新" —— 后者在增量重采之后会失效
（`probed_at` 被推到 now，刚改过但这次没重采的文件反而变成"更旧"⇒ 被误当可信）。

**让新测试回到精确选择**（几秒，别重跑全量）：

```bash
python3 scripts/dev/run_tests_for.py --probe --probe-files tests/test_new_feature.py
```

它只跑这几个文件，把结果**并入**快照（其余文件原样保留）。实测：一个文件 6~14 秒。
实测效果 —— 新测试里 `test_reads_initiative` 读 `agent/initiative.py`、
`test_reads_text_render` 读 `tools/text_render.py`，采完之后：
改 `initiative.py` 只命中前一条、改 `text_render.py` 只命中后一条、改无关文件命中 0 条。

不做增量采也不会**漏跑**（那文件会被整文件跑），只是跑得比必要的多。

**结论（怎么用，10-17 重做后）**：
· 迭代时 `python3 scripts/dev/run_tests_for.py <改动文件…>`（或 `--changed`）—— **只跑受影响的**，
  并行约 8~10s；改再大的文件也不会升级成全量（闸门已删）。
· 部署前 `python3 scripts/dev/run_tests_for.py --all` —— **15.6s**，快到"全量也不心疼"。
· 改了测试文件 / 新增测试后，快照会自动把那些文件**整文件降级跑**；想恢复精确选测就
  `--probe` 重采（2.5 分钟）。`--list --explain` 可以逐条问"为什么选中它"。
· 新增源文件的覆盖靠"目录扫描范围"兜（`.cs`/`.py` 落在某个契约测试的 rglob 范围内就会被带上）。
· **交付这个 runner 本身的改动时，必须跑 `scripts/dev/verify_subset_soundness.py`** ——
  它做"变异 → 全量 → 子集是否覆盖"的端到端验证；两个真漏都是它抓出来的。
· 变异脚本是验收线，改完跑对应那一个即可。
