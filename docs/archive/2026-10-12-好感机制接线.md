# 好感机制接线

> ⚠ **已归档**。本文是一次性排查记录，没有对应的现状文档，**日常开发不用看**。
>
> **结局**：量级从 1~10 放开、自制窗各路径都挂上好感变化。

---

#### 需求与实测症状

1. **传参 ≠ 实得**：`add_intim` 请求 10 点，面板/回读涨不到 10 —— 疑似有衰减（用户实测）。
2. **量级太小**：旧 schema/C# 双双把 value 钳在 **1~10**，而游戏面板刻度是**半心=30、一星=60、满值 300**
   （社区 2021–2024 多源一致；shenshi 参照 mod 的作弊值：邀请/双修 +60、结缘 +180、结婚 +240）。
   即旧上限"一次满级交互的 1/6 都不到"。
3. **交互不挂好感**：我们自制的确认窗/直写路径（多件赠礼、纯灵石赠礼、收下赠礼、灵石讨要、
   NPC 免窗直转）**不经原生动作 ⇒ 原生那套好感副作用压根不会发生**（代码里 09-21 的注释已标明
   "代价（知情）"，本次把它补齐）。

#### 衰减系数表（`RoleClose.json`，10-15 读出原值）

**「衰减」不是模糊的阶梯，而是一张按当前好感取系数的百分表**（100 = 不衰减）：

| 当前好感 | 0~60 | 60~120 | 120~180 | 180~240 | 240~300 | 300+ |
|---|---|---|---|---|---|---|
| 加减系数 | 100% | 50% | 25% | 12.5% | 6.25% | 6.25% |

负侧同构（-60~0 → 100% / -120~-60 → 50% / -180~-120 → 25% / -240~-180 → 12.5% / ≤-300 → 6.25%）；
同表还有 `closeReduce` / `hateIncrease` / `hateReduce` 三列 —— **减好感与仇恨增减同样按此衰减**。

⇒ 复现用户症状：当前好感 150 时 `AddIntim(+30)` 实得 ≈ 30×25% = 7.5（面板只动 7~8）。
⇒ 本项目对策（**10-15 定案**）：**不绕开它** —— 传请求值、引擎换算、我们只回读并在结果里说明衰减
（10-12 版曾用 `SetIntim` 写绝对值绕过系数，已按用户意见删除；详见下「实现」）。

**讨要能不能一次多样？——不能（10-15 实查签名）**：
`UnitActionRoleAskfor(WorldUnitBase toUnit, String propsSoleID, Int32 propsCount)` —— **一次一个道具栈 × 数量，
没有 List 重载**。对照：`UnitActionRoleGive(toUnit, List<PropsData>)` 收列表（但引擎实际只处理一件，见 09-17 实证）、
`UnitActionRoleStealItem(toUnit, propsSoleID)` 连数量都没有（＝整栈）。
⇒ 本项目口径一致：`item_acquire.ask_for` 的 `count` 是**同一栈**的数量，跨栈直接报错（"单栈仅 N 个"）；
要讨多样东西就分多次调用（**每次都会各记一次好感**，别在提示词里鼓励连环讨要）。

#### 实现（`csharp/tools/IntimService.cs` —— 「好感写入层」，11-20 从 `ToolExecutor.cs` 拆出）

> **★ 10-15 口径修正（用户定案，勿回退）★**：`AddIntim/AddHate` **只传"请求值"，换算（含
> RoleClose 衰减）由引擎决定**；我们**不校正、不补差、不用 `SetIntim`**，只**回读实得**并把它
> 写进结果 —— 渲染层 `_intim_decay_note()` 据此说明"实得少于请求是引擎按当前好感档位的百分系数
> 换算（本次约 N%），不是失败"。**10-12 版的 `ApplyIntimExact`（SetIntim 校正）与单件赠礼
> "补差"已按用户意见删除**；`SetIntim` 现仅存在于本文件注释的 API 清单里（代码零调用，
> 由 `test_intim_wiring_contract.py::test_only_the_write_layer_touches_intimacy` 钉死）。

* **写入层 `ApplyIntim(holder, other, ±delta, tag)`**：唯一写入点（全仓只有它调 `AddIntim/AddHate`），
  前后回读、`[Intim] 请求±X 实得Y（A→B）｜引擎按 RoleClose 系数换算` 探针。
* **直写工具**：`value` 1~10 → **1~120**（缺省 15＝配表基准）；刻度与衰减档位写在 schema 的 `value` 上。
* **交互接线（按 `accepting_gift` 分流；我们自己落刀的路径才写，原生动作路径只探针）**：

| 路径 | 谁对谁 | 值 |
|---|---|---|
| 赠礼：多件窗 / 纯灵石窗 / 直通 / NPC 免窗直转 | 收礼方 → 送礼方（**单边**） | `roleGive.closeParaA`（回退 15，`closeOnceAddMax` 封顶） |
| **收下赠礼**（`accepting_gift=true`，道具/灵石/多件/NPC↔NPC） | 收礼方（你）→ 送礼方（**单边**） | 同上（**赠礼语义**：玩家给出、你收下） |
| **讨要达成**（`accepting_gift` 缺省）：多件窗 / 灵石窗 / NPC 免窗直转 | 取得方 → 交付方 **+**<br>交付方 → 取得方 **−**（**双边**） | `roleAskfor.closeParaA`（≈8）/ `closeParaB`（≈-8） |
| 单件道具讨要（对象=玩家） | 原生窗，引擎自算 | **不落刀**（`isAskforComplete`/`isNPCReduceIntim` 只读） |
| 单件原生赠礼 | 收礼方 → 送礼方 | 原生自算，**只探针**（补差已删） |
| 交易成交（本项目规则，原生无钩子） | 双方 | 有价：各 +5；price=0 按赠予（收下方 → 给出方 +配表值） |
| 论道完成（本项目规则，`ConfRole*` 无 lun_dao 键） | 双方 | 各 +10（直接 `ApplyIntim`，**不再 top-up**） |
| 双修/切磋/邀约/传功/偷窃 | 原生自算 | **不落刀**，双修留 `[Intim] 双修探针` 供真机核对 |

* 量级常量集中在写入层顶部：`IntimStepDefault=15`、`IntimStepMax=120`、`LunDaoIntimEach=10`、
  `TradeIntimEach=5`（要调只动这四个 + 各配表键）。
* **真机验收点**：赠礼/讨要各自做一次，看 `[Give]/[Intim]` 探针行的 Δ；交易看 `trade` 的 `intim`；
  论道看结果里的 `intim.{npc_to_player,player_to_npc}`；**衰减是否如实报**看 `social_relation` 的渲染文案。

#### 多件讨要（10-15，`item_acquire.items`）

* **为什么必须自制窗**：`UnitActionRoleAskfor(WorldUnitBase, String propsSoleID, Int32 propsCount)`
  **一次只吃一个栈**（签名实证，无 List 重载）；灵石更没有 `soleID`。
* **入口**：`item_acquire` 新增 `items:[{item_name,count}]`（与 `economy_item` 同款）；
  `ParseAcquireItems` 解析，`wants.Count > 1` ⇒ `AskMultiple`（**≥2 项才走自制窗**，单件道具仍走原生）。
* **`AskMultiple`**：预检（只读，逐项足额）→ 玩家弹 `DramaItemAcquireBase` 自制窗
  （`「想向你讨要：A×2、B×1，是否给他？」`）/ NPC↔NPC 免窗直转 → 落刀**整笔**：
  ① 逐项 `TakePropsFromBag`（跨栈；任一不足 ⇒ `RollbackGive` 全放回 + 失败）
  ② 灵石 `TransferLingshi`（自带补偿；失败 ⇒ 回滚道具）③ 入包（失败 ⇒ 道具放回 + 灵石退回）
  → ④ 好感按 `accepting_gift` 分流（见上表）。
* **渲染**：`_acquire_what()` 同时服务单件/多件（单件文案逐字不变），多件列成 `「丹药」×2、「灵石」×300`。
* 偷窃仍**一栈一次**（`item_acquire` 多件只对 `ask_for` 开放；`steal_item` 传 `items` 会被告知分次调用）。

#### 好感变化的渲染显示（10-15 用户定案补显示）

* **原则**：**我们落刀的路径才显示**——C# 走 `PutIntim` 透出 `intim`/`intim_upset`（读不到起点时字段缺失），
  渲染层 `_intim_delta(who, whom, Δ)` 有字段才追加一句；原生路径（单件赠礼/单件讨要/双修/切磋/邀约/
  传功/偷窃）没有这些字段 ⇒ **天然不显示**（字段有无即路径有无，不用额外开关）。
* **句式**：`{X}对{Y}的好感提升/降低N点`（0 实得显示「未变化」；缺失=不显示，二者不同）。
  各渲染器的称谓沿用各自既有约定——`economy_item`/`trade` 全名互称；`item_acquire` 的"你"=玩家；
  `world_ai_action` 的"你"=AI 发起方（论道双向：`npc_to_player`=你对玩家、`player_to_npc`=玩家对你）。
* **落点**：`render_economy`（收礼方→送礼方，接在送达方式后）、`render_trade`（有价双向各 +5 /
  price=0 赠予单向，独立成句）、`render_item_acquire`（讨要双边 / receiving 单边，逐分支追加）、
  `render_world_ai`（仅论道）。直写工具（`add/reduce_intim`）维持 `render_social` 的既有显示
  （含衰减说明），不变。
* **对账**：`test_tool_contract_consistency` 的 `_keys_written` 已识别 `PutIntim(o, "key", Δ)` 形态
  （键是字符串参数，索引器扫描认不出）——以后凡走收口 helper 的键自动对账，不进 DYNAMIC_KEYS 白名单。
* 契约：`test_intim_wiring_contract.py::test_renderers_surface_intim`（含"字段缺失逐字回到旧文案"
  与"双修不显示"）；变异 ㉕/㉖（方向写反 / 双边只渲染一边）。
