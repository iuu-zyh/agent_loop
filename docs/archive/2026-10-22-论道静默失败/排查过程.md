## 0. 一段话说明白（最新结论）

玩家实测给了一个决定性的对照：**同一个 NPC、同一个位置，面板上手动点「论道」成功，工具调用失败且没有 UI。**

### 0.1 已定案（2026-10-22 12:04 真机读数）

**根因：`UnitActionRoleDiscovery.IsCreate` 返回 `1` = `IsDayCost` 拒绝，因为
`action.unit.residueDay < conf.roleDiscovery.costDay(=5)`。**

真机读数（`Player.log`，两次论道完全一致）：

```
层=Discovery.IsCreate code=1 unit=江宇文 当前坐标=(46,27) day=0 isTip=False
层=CreateAction       code=1 unit=江宇文 actionType=UnitActionBase isTip=False ⇒ **拒绝**（不进 Create）
```

`code=1` **不是**禁令码 `3`（那是我上一轮的怀疑，已被证伪）。

### 0.2 为什么手工点击能成功 —— 两条路径比对的**不是同一个单位**

两条路径都调 `WorldUnitBase::CreateAction(action, isTip)`，但 `IsDayCost` 读的是
**`action.unit`（`UnitActionBase` +0x10，由 `Init(unit)` 写入）**，而不是 `CreateAction` 的接收者：

| | 造 action | 谁被 `Init` 成 `action.unit` | `IsDayCost` 查的是 |
|---|---|---|---|
| **手工面板** | `UINPCInfoUnitInfo.<InitMeum>b__19` @0x33601DE | `g.world.playerUnit`（`WorldMgr` +0x10） | **玩家的** `residueDay` |
| **工具调用** | `WorldUnitAIAction1037::ActionStart` @0x1845e22ee | `[rbp+0x18]`→`[+0x10]` = `unitAI.unit` = **NPC** | **江宇文的** `residueDay` |

```asm
; 手工路径（0x33601DE 附近）
call UnitActionRoleDiscovery::.ctor
mov  rcx,[rax+0x10]        ; ← WorldMgr.playerUnit（玩家）
mov  r8b,1                 ; isTip=true
jmp  [rax+0x1c8]           ; CreateAction(player ← receiver)

; 工具路径（ActionStart @0x1845e22f0 附近）
mov  rcx,[rbp+0x18]        ; unitAI
mov  rcx,[rcx+0x10]        ; ← WorldUnitAIBase.unit = NPC 自己
mov  rdx,[rsi+0x18]        ; discovery
xor  r8d,r8d               ; isTip=false
call [rax+0x1c8]           ; CreateAction(npc ← receiver)
```

⇒ 玩家当月剩余天数够（所以面板能成），**江宇文自己的 `residueDay` 不够 5 天**。
这解释了「同一个 NPC、同一个位置，手工成功、工具失败」的全部现象，**与 NPC 是否有禁令无关**。

### 0.3 剩余待办

1. 上机读 `residueDay=`（探针已加，`f2b44d42` 已部署）确认 `residueDay < 5`；
2. 按读数决定修法：**诚实报错**（首选，见 §9 方案 A）还是**绕过 `IsCreate`**；
3. `ToolExecutor.StartToUnitAiActionDeferred` 的失败文案必须改（现在写「他还没能站到你面前」，已证伪）。

顺着这个对照查下去，`WorldUnitAIAction1037.ActionStart` @0x45E2210 的真实流程是：

```asm
1845e22c5: call MovePoint(npc, toUnit)                    ; ① 走近距离检查
1845e22ca: test al,al
1845e22cc: je   0x1845e238a                               ; false → onEndCall(false)
1845e22ee: call UnitActionRoleDiscovery::.ctor(toUnit)    ; ② 造**真正的论道动作**
1845e2340: call [r9+0x1c8]                                ; ③ 把我们的 onEndCall 挂到它上面
1845e236a: call [rax+0x1c8]                               ; ④ npc.CreateAction(discovery)
1845e2370: ... 直接 ret                                    ; ★ ⑤ 第④步的返回码**被完全丢弃**
```

**第 ⑤ 步是本案的关键**：`CreateAction(discovery)` 的返回值没有人检查，连 `eax` 都不读。
所以 `discovery` 被引擎拒绝时，`ActionStart` **毫无反应**——不弹窗、不回调、不打日志。

**这就是「静默没有反应」的确切来源。**

那拒绝发生在哪里？`UnitActionRoleDiscovery.IsCreate` @0x3F1A070 里有**两道**关卡，
顺序是「先 day，后禁令」：

```asm
; ① 第一道：天数（`isCostDay` 为真时才走，而这个字段恒为真，见下）
183f1a0c6: cmp  BYTE PTR [rbx+0xaa],al      ; isCostDay()  ← 构造函数恒置 true
183f1a0cc: je   0x183f1a117                 ; false → 跳过
183f1a0f6: call ConfRoleDiscoveryBase::get_costDay     ; "5"
183f1a100: call Int32::Parse                ; → 5
183f1a10d: call UnitActionBase::IsDayCost   ; ← 真机返回 1
183f1a112: test eax,eax
183f1a114: cmovne edi,eax                   ; edi = 1

; ② 第二道：禁令
183f1a125: call WorldUnitEffectSpecialBannedFunc::ActionFunc(unit, 动作名)
183f1a13a: call String::op_Inequality       ; 返回的提示串 != "" ?
183f1a141: je   0x183f1a15b                 ; 没命中 → 看 edi（即第①道的结果）
183f1a14f: call UnitActionBase::AddTip      ; 挂 tip（**不弹窗**）
183f1a154: mov  edi, 3                      ; → 返回 3 = 禁令拒绝

; ③ 统一出口
183f1a15b: test edi,edi
183f1a15d: je   0x183f1a172                 ; edi==0 才放行
183f1a172: mov  eax,edi                     ; 返回 edi
```

**真机读到的是 `code=1`，走的是第①道**（`IsDayCost`），不是禁令。
按 §6 的老习惯这里要记一笔：上一轮我断定「码只可能是 3」，那是**没把 `edi` 的初值
和 `cmovne` 算进去**——`IsDayCost` 非零就直接 `cmovne edi,eax`，禁令那段根本没轮到。

`IsDayCost` @0x35083E0 的判定（读 `action.unit.data.unitData.residueDay`，`UnitInfoData` +0x38）：

```asm
183508451: cmp  DWORD PTR [rax+0x38],edi    ; residueDay vs day(=5)
183508454: jl   0x183508501                 ; residueDay < 5 → 拒（返回 1）
```

⇒ **`code=1` 的唯一含义：该 NPC 自身剩余可用天数不足 `costDay`（配置值 5）。**
与地形、格子、气运、禁令**全部无关**。

**为什么手工点击不受影响**：手工路径把 `g.world.playerUnit` 传给 `Init`，
查的是**玩家的** `residueDay`；工具路径 `ActionStart` 传的是 `unitAI.unit`（NPC 自己），
查的是**江宇文的** `residueDay`。详见 §0.2。

## 2. 两条路径的关键差异（这是全案的地基）

玩家实测：**同一 NPC、同一位置，面板手动点「论道」成功，工具调用失败。**

所以问题不在 NPC 身上，在"引擎对两种发起方式的关卡不同"。反汇编证实这是两套链：

| | 手动点击面板 | 工具调用（我们的 mod） |
|---|---|---|
| 入口 | `UINPCInfoUnitInfo.<InitMeum>b__19` @0x33601DE | `WorldUnitAIAction1037.ActionStart` @0x45E2210 |
| 中间层 | 无 | **`WorldUnitAITool.MovePoint`** @0x3EF1800 |
| 造动作 | `new UnitActionRoleDiscovery(player)` | `new UnitActionRoleDiscovery(toUnit)` |
| **`CreateAction` 接收者** | **`g.world.playerUnit`（玩家）** | **`unitAI.unit`（NPC 自己）** |
| **`action.unit` → `IsDayCost` 查谁的天数** | **玩家**（天数够 → 放行） | **NPC**（`residueDay<5` → 返回 1） |
| `IsCreate` 链 | 也走 `Discovery.IsCreate` | ① `UnitActionMoveNPC.IsCreate` → `UnitActionSetPoint.IsCreate`<br>② `UnitActionRoleDiscovery.IsCreate` @0x3F1A070 |

**关键差异在第 4、5 行**：两条路都调 `Discovery.IsCreate`，**但 `action.unit` 不是同一个单位**，
而 `IsDayCost` 查的正是 `action.unit.residueDay`。

> ⚠️ 这段我在两个阶段都写错过，两笔都记在这里：
> 1. 早期断言"手动路径不经过 `Discovery.IsCreate`"——**错**，它照样经过。
> 2. 后来断言"真正的差异在禁令 `WorldUnitEffectSpecialBannedFunc`"——**也错**，
>    真机码是 `1`（天数）不是 `3`（禁令）。
>
> 真正的差异只有一个：**谁的天数被扣**。详见 §0.2。

## 3. 已确认的引擎机制（带证据，别再重复验证）

### 3.1 `ActionStart` 的**两条**出口（⚠ 早期版本只写了一条，是错的）

```asm
; WorldUnitAIAction1037::ActionStart @0x45E2210
1845e22ba: mov  rdx, [rbp+0x30]      ; toUnit
1845e22c1: mov  rcx, [rcx+0x10]      ; unitAI.unit = NPC 本体
1845e22c5: call 0x183ef1800          ; WorldUnitAITool::MovePoint(npc, toUnit)
1845e22ca: test al, al
1845e22cc: je   0x1845e238a          ; ← 出口 A：MovePoint=false → onEndCall(false)
; ---- 出口 B：MovePoint=true 之后 ----
1845e22ee: call UnitActionRoleDiscovery::.ctor(toUnit)   ; 造论道动作
1845e2340: call [r9+0x1c8]                               ; 把 onEndCall 挂到 discovery
1845e236a: call [rax+0x1c8]                              ; npc.CreateAction(discovery)
1845e2370: ... 直接 ret                                   ; ★ 返回值丢弃，无任何检查
```

> **§3.1 的早期版本写的是「`ActionStart` 的返回值完全由 `MovePoint` 决定」——这条是错的。**
> 漏掉了出口 B：`MovePoint` 返回 true 之后还有一步 `CreateAction(discovery)`，
> 它的失败**不会**让 `MovePoint` 变 false，也**不会**让 `ActionStart` 报错，
> 而是完全静默。本文件 §6.5 记录了这个错误的成因。

两个出口的性质完全不同：

| 出口 | 触发条件 | 表现 |
|---|---|---|
| A | `MovePoint` 返回 false | 调 `onEndCall(false)`，**不弹窗** |
| B | `MovePoint` true，但 `CreateAction(discovery)` 返回非 0 | **什么都不做**——不回调、不弹窗、不打日志 |

> 真机已确认 `MovePoint` 返回 **true**（§4.3），所以本案走的是出口 B。

### 3.2 `MovePoint` 只有一个 `ret`，返回 `moveComplete`

```asm
; WorldUnitAITool::MovePoint @0x3EF1800
183ef1ada: test rdi, rdi            ; rdi = new 出来的 UnitActionMoveNPC，永远非 null
183ef1add: je   0x183ef1afb         ; 异常路径
183ef1adf: movzx eax, BYTE PTR [rdi+0x40]   ; ← moveComplete，唯一返回值
183ef1afa: ret
```

而 `moveComplete` **只在** `UnitActionMoveNPC::OnCreate` @0x38E4B50 里被置 1：

```asm
1838e4ccc: mov BYTE PTR [r13+0x40], 0x1
```

⇒ `moveComplete=true` ⇔ `OnCreate` 跑到了。
**注意**：这只说明"移动那步成功了"，**不代表论道动作被创建**——两者是不同对象（§3.1 出口 B）。

### 3.3 `day` 的公式与"整月边界"无关（这条曾误导我很长时间）

```asm
; UnitActionMoveNPC::Init @0x38E4810
call 0x1832b07970                 ; MapTool::PointDis = |dx| + |dy|（曼哈顿）
...
mulss xmm1, DWORD PTR [0x1862c9238]   ; × 0.01f
divss xmm6, xmm7                       ; ÷ speed
cvttss2si ecx, xmm6
call 0x185141f30                       ; Mathf.Clamp
1838e49af: mov DWORD PTR [rdi+0x18], eax    ; action.day
```

常量 `0x1862c9238` 从 `GameAssembly.dll` 直接读出 = **`0.0099999998`（0.01f）**。

⇒ `day = Clamp(moveDis × 0.01 × timeCostPara ÷ speed, 0, 上限)`

**同格 ⇒ `moveDis = 0` ⇒ `day = 0`。** 而 `UnitActionBase::IsDayCost` @0x35083E0 的**每一个**拒绝点
都要求 `day > 0`：

```asm
183508482: test edi, edi
183508484: jg   0x183508501      ; day > 0 才拒绝
```

⇒ `day=0` 时**移动动作**这一层必然放行。真机探针也印证了 `day=0`。

#### ⚠ 但这条只对 `UnitActionMoveNPC` 成立，**对 `Discovery` 不成立**

这是本案最大的一个坑，也是我第七次误判的根源（§6.7）。当时我看到
`Discovery.IsCreate` 里有 `call IsDayCost`，又看到探针打出 `day=0`，
就推断「day 层已排除」——**错在把两个不同的量当成了同一个**：

| | 谁传给 `IsDayCost` | 同格时 |
|---|---|---|
| `UnitActionMoveNPC::IsCreate` | `this.day`（`+0x18`，上面那个公式算出来的移动耗时） | **0** ✓ 放行 |
| `UnitActionRoleDiscovery::IsCreate` | `Int32.Parse(conf.roleDiscovery.costDay)`（**配置表常数 5**） | **恒 5** |

```asm
; UnitActionRoleDiscovery::IsCreate @0x3F1A070
183f1a0f6: call ConfRoleDiscoveryBase::get_costDay   ; 配置 RoleDiscovery.costDay = "5"
183f1a100: call System.Int32::Parse
183f1a108: mov  edx,eax                              ; ← day 参数 = 5，与 action.day 无关
183f1a10d: call UnitActionBase::IsDayCost
```

而 `IsDayCost` 读的是 **`action.unit.data.unitData.residueDay`**（`UnitInfoData` +0x38）：

```asm
183508451: cmp  DWORD PTR [rax+0x38],edi   ; residueDay vs 5
183508454: jl   0x183508501                ; residueDay < 5 → 拒绝，返回 1
```

⇒ **探针里的 `day=0` 是真的，但它跟这道关卡毫无关系**。真正要比的是
`residueDay` 和配置常数 `5`。真机 `code=1` 就是这么来的。

（探针已加 `residueDay=` 与 `costDay=` 两列，避免后来者再被 `day=0` 误导。）

### 3.4 `CreateAction` 的三段结构

### 3.5 `UnitActionSetPoint::IsCreate` @0x2B29B20 的 12 个返回码

逐分支反汇编所得（探针会把码翻成人话）：

| 码 | 含义 |
|---|---|
| 2 | 地形条件不满足（`ConfWorldTerrainDecorate::IsCondition`） |
| 3 | effect 非空（`GetEffects<T>()` 有条目） |
| 4 / 5 | 建筑相关（`WorldBuildMgr.GetBuild` 虚调用返回 1 / 非 1） |
| 6 | 障碍区且该 effect 不豁免 |
| 7 | 建筑阻挡 |
| 8 | **有未接的 AI 目标**（`GetGoalBackReceive(204)` 非空）★ 队伍/跟随 |
| 9 | 仙盟条件不满足 |
| 10 | **气运拦截**（`GetLuck` 非空）★ 队伍气运 |
| 11 | 目标点在其它单位身上且格子类型 == 11 |
| 12 | 气运/格子条件组合 |
| 13 | 仙盟提示（已异步推 UI） |

> 码 8 与 10 与"队伍"直接相关——本 mod 的队伍标记就是靠挂气运实现的
> （`MID&55`/`MID&56`「结伴而行」），而历史存档里江宇文曾是队伍 2 号位。
> **这不是本案原因**：真机探针实测这两层全 `code=0`（§4.2），而且"手动能成"也不支持它。

### 3.6 ★ 论道的关卡：`UnitActionRoleDiscovery.IsCreate` @0x3F1A070

**本案的落点。** 注意：它**不是**"工具路径独有"——两条路径都经过它（§2 已更正）。
真正的差异是 `action.unit` 指向谁。

```asm
; UnitActionRoleDiscovery::IsCreate @0x3F1A070
183f1a0b7: call UnitActionRoleToUnitBase::IsCreate    ; ① 先跑父类那套
183f1a0bc: mov  edi, eax
183f1a0c0: jne  0x183f1a15f                          ; 非 0 → 原样返回（含 100）

; ② 天数关卡 —— 只有 isCostDay 为真才走
183f1a0c6: cmp  BYTE PTR [rbx+0xaa], al              ; isCostDay
183f1a0cc: je   0x183f1a117                          ; false → 跳过
183f1a0f6: call ConfRoleDiscoveryBase::get_costDay   ; 配置表 "5"
183f1a100: call System.Int32::Parse                  ; → 5
183f1a10d: call UnitActionBase::IsDayCost            ; ★ 真机在此返回 1
183f1a114: cmovne edi, eax                           ; edi = 1

; ③ 禁令关卡
183f1a117: mov  rdx, [0x186fd6cb8]                   ; 动作名（string 常量）
183f1a121: mov  rcx, [rbx+0x10]                      ; this.unit
183f1a125: call WorldUnitEffectSpecialBannedFunc::ActionFunc
183f1a13a: call System.String::op_Inequality         ; 返回的提示串 != "" ?
183f1a141: je   0x183f1a15b                          ; 空 → 看 edi（第②道的结果）
183f1a14f: call UnitActionBase::AddTip               ; 挂 tip（**不弹窗**）
183f1a154: mov  edi, 3                               ; → 返回 3 = 禁令拒绝

; ④ 统一出口
183f1a15b: test edi, edi
183f1a15d: je   0x183f1a172                          ; 0 才放行（继续 Create）
183f1a172: mov  eax, edi                             ; 返回 edi
```

**关键顺序**：第②道先跑。`edi` 一旦被 `cmovne` 置成 1，第③道的禁令**只是"再确认一次"**，
最后从 `0x183f1a15f` 直接返回 `edi`（=1）。**真机就停在这里。**

#### `isCostDay`（`+0xaa`）恒为真 —— 别以为是"条件触发"

`UnitActionRoleDiscovery::.ctor` @0x3F1AC80 第 18 行：

```asm
183f1acac: mov WORD PTR [rbx+0xa9], 0x101     ; +0xA9 = isAward = 1 ; +0xAA = isCostDay = 1
```

全二进制里对 `+0xAA` 的写入**共 13 处**，逐一核对后**没有一处在 `UnitActionRoleDiscovery` 上**
（都落在 `UnitActionRoleSeekUpGrade` / `UnitActionRoleKill` / `SpecialBattleNN` 等别类的同名偏移）。
⇒ **这个字段创建后永远是 `true`，第②道必然执行。**

#### 为什么"面板能点成"（★ 本案最强对照的答案）

`IsDayCost` @0x35083E0 读的是 **`action.unit.data.unitData.residueDay`**（`UnitInfoData` +0x38）：

```asm
183508451: cmp DWORD PTR [rax+0x38], edi      ; residueDay vs 5
183508454: jl  0x183508501                    ; residueDay < 5 → 返回 1
```

而两条路径的 `action.unit` 不同：

| 路径 | 代码 | `action.unit` | 结果 |
|---|---|---|---|
| 面板 | `UINPCInfoUnitInfo.<InitMeum>b__19` @0x33601DE：`mov rcx,[world+0x10]` = `playerUnit` | **玩家** | 玩家天数够 → 放行 |
| 工具 | `ActionStart` @0x1845e22c1：`mov rcx,[rcx+0x10]`（`unitAI.unit`） | **NPC** | `residueDay<5` → **1** |

⇒ **"同一个 NPC、同一个位置，手动成功、工具失败"的全部原因，就是这里查了不同人的天数。**

### 3.7 `WorldUnitEffectSpecialBannedFunc::ActionFunc` @0x44D0400

```asm
1844d0468: call WorldUnitBase::GetEffects<WorldUnitEffectSpecialBannedFunc>
; 遍历列表：
1844d0480: 循环
1844d0499:   rcx = list[i]
1844d04a3:   rcx = [rcx+0x60]          ; effect.action
1844d04ad:   call System.String::op_Equality(effect.action, 传入的动作名)
1844d04b4:   jne  下一个
1844d04d2:   rax = [effect+0x68]       ; effect.errorTip
1844d04e5:   ret                        ; ← 命中：返回错误提示
1844d04e6: 循环结束 → 返回空串           ; ← 未命中：放行
```

类型定义（`WorldUnitEffectSpecialBannedFunc`）：

```csharp
public class WorldUnitEffectSpecialBannedFunc : WorldUnitEffectSpecial
{
    private string action;      // +0x60  禁止哪个动作
    private string errorTip;    // +0x68  禁止时显示的提示
    public static string ActionFunc(WorldUnitBase unit, string action);
}
```

⇒ **语义**：NPC 身上若挂了一条「禁止动作 X」的 effect，则所有走 `IsCreate` 的动作 X 被拒，
返回该 effect 配置的 `errorTip`。

> **本案没有走到这里**（真机码 1，第②道就返回了）。**但这条机制本身是真的**，
> 若将来看到 `code=3`，就按这里查。别因为本案用不上就删掉这节。

### 3.8 为什么 `ActionStart` 会让这次失败完全静默

把 §3.1 出口 B 和 §3.6 连起来：

```

  → new UnitActionRoleDiscovery
  → npc.CreateAction(discovery)      ← 内部调 discovery.IsCreate
      → IsDayCost: residueDay(江宇文) < 5 → 返回 1
      → CreateAction 见 code!=0 → 直接 return，不进 Create
  → ActionStart **不看返回值**，直接 ret
```

结果：**没有 UI、没有异常、没有任何日志**。这正是玩家说的"静默没有反应"。

> 关于 `ok=False`：我们的 `onEndCall` 在第 ③ 步被挂到了 `discovery` 上（`1845e2340`），
> `discovery` 创建失败后由引擎的某条通知路径触发，传入 `false`。
> **它是真实失败通知，不是"中间阶段"**（我一度说成中间阶段，见 §6.5）。

### 4.4 `CreateAction` 探针 0 次触发 —— 原因已定位

1. **`ProbeHooked` 自检用无参 `AccessTools.Method`** 查 `MovePoint` 这种有重载的方法会抛
   `Ambiguous match` —— 那行自检就变成"自检异常"，**而探针本身是好的**（`层=MovePoint` 正常打印）。
   修法：`ProbeHooked` 支持显式传参数类型（§7.2）。
2. **`CreateActionProbe` 用 `action as UnitActionMoveNPC` 做前置过滤**，转型失败就 `return`，
   整行被静默吞掉。修法：先无条件打一行（带真实类名 `actionType=`），再对移动族补细节。

顺带记一组事实（扫 `il2cpp` 段 `e8 rel32` 统计直接调用点）：

| 方法 | 直接调用点数 |
|---|---|
| `UnitActionBase::Create` | 30 |
| `UnitActionBase::IsCreate` | 75 |
| `UnitActionMoveNPC::IsCreate` | **0** |
| `UnitActionMoveNPC::OnCreate` | **0** |

后两个只走**虚表分发**——所以「用调用栈判断它们跑没跑」本来就不成立（§6.1 同源错误）。

## 6. 排查中下过的错误结论（★ 最重要的部分 ★）

七次里有六次是同一个毛病：**拿推理当证据**（剩下一次是探针自己写错，但结论是同一个方向——"没输出"被当成"没发生"）。
写在这里是为了后来者不必重走。

按发现顺序编号，编号越大表示越晚才发现、也越隐蔽。

### 6.1 错误一：「`Create` 没跑，因为没有 `Create` 调用栈」

**当时的推理**：引擎 `UnitActionBase::Create()` 会打调用栈；姜萌成功那局有 8 次，
江宇文失败那两次 0 次 ⇒ 江宇文没进 `Create`。

**为什么错**：`Create` 开头就分叉：

```asm
183507fe1: mov  edx, [rdi+0x18]     ; day
183507ff5: jle  0x183508169         ; day <= 0 走另一条
```

`day<=0` 与 `day>0` 是**两条分支，日志输出行为不同**（`day>0` 才经 `CodeTimeLog` 打栈）。
论道同格 `day=0`，**就算 `Create` 正常跑完也不打栈**。

⇒ 那个「8 次 vs 0 次」是**假对照**。姜萌那些栈来自传送/跨格（`day>0`），与论道成败无关。

**教训**：判据本身要先被验证。"没有日志"≠"没有执行"。

### 6.2 错误二：「`IsCreate` 拒了」

从 6.1 的错误结论直接推出"所以是 `IsCreate` 拒绝"。探针一装：`code=0` **全放行**。

**教训**：错误的前提会一路推出错误的中层结论，且看起来自洽。

### 6.3 错误三：「`isCreateCall=True` 说明对象被复用」

误以为是"上一个动作的残留标志"。实际它是 `IsCreate` **自己**置的：

```asm
; UnitActionBase::IsCreate @0x35083B0
1835083cb: mov BYTE PTR [rbx+0x28], 0x1     ; IsDayCost 通过后置 isCreateCall=true
```

Postfix 在方法**返回后**执行，读到 `True` 是必然结果。这条排除。

### 6.4 错误四：「`ActionStart` 的返回值完全由 `MovePoint` 决定」

**当时的推理**：成功路径不调 `onEndCall`，失败路径才调；而 `onEndCall(false)` 只在
`MovePoint` 返回 false 时触发 ⇒ 收到 `false` 就是 `MovePoint` 返回了 false。

**为什么错**：漏了出口 B。`MovePoint` 返回 true 之后还有
`npc.CreateAction(discovery)`，**它的返回值被完全丢弃**（§3.1）。
发现、`discovery` 创建失败时既不回调也不报错——但从外部看就是"收到了 false 但 MovePoint 是 true"，
于是成了"矛盾"。

**教训**：`call` 之后不看 `eax` 的调用点，等于一条**不存在于返回值体系里的失败路径**。
读汇编时要专门找这种"调用完直接往下走"的地方。

### 6.5 错误五：「`ok=False` 只是中间阶段，不代表工具调用失败」

**当时的推理**：既然 `MovePoint` 返回 true、`OnCreate` 也到了，那 `ok=False` 应该是
"动作已创建但还在等玩家"的中间通知。

**为什么错**：纯粹是猜测，当时**没有任何证据**。真相是 `ok=False` 是**真实失败通知**——
`discovery` 根本没被创建出来，所以 UI 才不出现。玩家当场质疑了这一点，质疑是对的。

**教训**：当观测与理论冲突时，**不要发明一个"中间状态"来消解矛盾**。
那是在给错误找台阶。要么承认不知道，要么去拿到能分辨的量。

### 6.6 错误六：「`CreateAction` 拦不到虚表分发」

**当时的推理**：`CreateAction` 是 virtual，`MovePoint` 对它是 `call [r14+0x1c8]`，
而探针 0 次触发 ⇒ 所以 Harmony 拦不到虚表分发。

**为什么错**：真相是探针自己写错了——`action as UnitActionMoveNPC` 转型失败就 `return`，
整行被吞。改成先无条件打印后就能出。**而且 `ProbeHooked` 对重载方法抛 `Ambiguous`，
让自检显示"异常"，进一步加深了"探针没挂上"的误判。**

**教训**：探针"没有输出"时，**第一嫌疑永远是探针自己**，不是被测代码。
先把探针改成"宁可多打一行废物，也不要静默"，再去下结论。

### 6.7 错误七（★ 最隐蔽 ★）：「`day=0` 说明 day 层已排除，码只可能是 3」

**当时的推理**：`Discovery.IsCreate` 里有 `call IsDayCost`；探针打出 `day=0`；
而 `IsDayCost` 每个拒绝点都要求 `day>0` ⇒ day 层必然放行 ⇒ 剩下的只可能是禁令码 3。

**为什么错**：这是**三重**错误叠在一起。

1. **把两个 `day` 当成同一个量**。`Discovery` 传给 `IsDayCost` 的是
   `Int32.Parse(conf.roleDiscovery.costDay)` = **常数值 5**，不是 `action.day`。
   探针打的 `day=0` 是真的，但它跟这道关卡**完全无关**（详见 §3.3 的对照表）。
2. **漏了 `IsDayCost` 非零时 `edi` 会被直接覆盖**。`cmovne edi,eax` 之后
   禁令那段只是"再看一眼"，`edi` 非零就从 `0x183f1a15f` 直接返回。
   所以「码只能是 3」这个枚举**根本没包含 1**。
3. **没核对 `IsDayCost` 到底读谁的天数**。它读 `action.unit.data.unitData.residueDay`，
   而两条路径的 `action.unit` 是**不同的人**（§0.2）——这才是「手工能成」的真因。

**真机读数**：`code=1`，一次就把上面三条全部推翻。

**教训**：
- 枚举返回码之前，先确认自己**把所有 `mov edi,<imm>` 和所有 `cmov*` 都读全了**；
- 同名变量（`day`）在不同类里可能是**完全不同的东西**，必须以「谁传参」为锚，不能以变量名为锚；
- 一个"能解释全部现象"的假设（禁令 ⇒ 手工绕过）如果**预测错了码值**，它就是错的，
  不该靠"其他方面很吻合"继续维护它。

### 6.8 踩过的工程坑（不是逻辑错误，但同样浪费时间）

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 把探针文件放在 `csharp/diag/` 根目录 | csproj 只包含 `diag\team\*.cs`，文件**根本没参与编译**；编译报 `0 个错误`，我误以为成功 | 新文件要先确认目录在 `Compile Include` 里；编译后**在 DLL 里搜类名**，不能只看"0 错误" |
| 只看编译错误数 | 同上，静默失败 | 用二进制搜类名/字符串验证：<br>`d.count(kw.encode('utf-8'))` 与 `utf-16-le` 两种都要试 |
| `strings` 不带 `-el` | .NET 字符串是 UTF-16，搜不到 | `strings -el`，或直接 Python 读字节 |
| 探针自检打出「**未挂**」/「自检异常」却没先查 | 白跑一趟上机测试 | 自检行必须**先读**；异常也要当"未确认"处理 |

## 10. 一句话留给后来者

这个案子绕了七圈，前六圈是同一个毛病：**用"没看到某条日志"去推断"某件事没发生"**。
第七圈更值得记：**用"看起来吻合"的机制去替代"实际读数"**。

引擎有大量"调用完不看返回值"的地方（§3.1 出口 B 就是典型），
这类失败**天生不留痕迹**——所以排查时不能靠"找日志"，
要靠**在关键函数上挂只读 Postfix，把返回值直接读出来**。

而读到了返回值，还要**确认这个返回值属于哪条代码路径**。§6.7 那次误判不是因为没探针，
是因为探针打的是 `action.day`，关卡用的却是 `conf.costDay` ——**两个都叫 day，但不是同一个东西**。
