# 单聊「关窗不丢」：整轮记录 + 渲染闸

> ⚠ **已归档**。本文是一次性排查记录，没有对应的现状文档，**日常开发不用看**。
>
> **结局**：tee 缓存范围与渲染闸两条都改了，关窗重开不再丢前半截。

---

**症状（用户实测，三条一起报）**：发一句话 → 关窗 → 重开，屏幕上只剩"后半截流式正文"：
① 没有我自己发的那句话；② 行动记录里那次工具过程也没有；③ 视图停在**顶部**（要自己往下翻）。

**根因（三条，一条比一条深）**

| # | 根因 | 位置 |
|---|---|---|
| ① | tee **只在"关窗期间"**缓冲单聊帧（`IsShowingSolo` 判据），而玩家只能在**开着窗**时发消息、工具与思考也大多发生在关窗之前 ⇒ 这些帧按设计被丢，事后零痕迹 | `ChatFrameTee` |
| ② | 重开窗的 `open_chat` 重放**只含已收口的回合**（UI 投影按完整回合投影，"说到一半"没有归属回合）⇒ 半截正文与工具行都不在快照里 | `history.py` |
| ③ | 一次画几十行时布局要好几帧才结算，而"内容变高就钉底"只覆盖第一帧；随后布局定稿让位置不再在底部，下一帧是"没长高" ⇒ 跟随被**永久关掉** | `ChatWindow.LateUpdate` |

**修法（一句分工：记录归 tee，画归闸门）**

* **记录 —— 单聊帧"始终记"**（与谁在显示无关）。段 = "**当前这一轮的全过程**"：`user_say`
  （**C# 本地产生**，单聊没有回声帧 —— Python 只在群聊里广播）开段 → `npc_reply` 闭段；
  `step` 的账本回合号**变大** = 隐式闭段（`npc_reply` 丢帧时的死段不留）；`npc_reply` 到达即清段
  （账本已闭合 ⇒ 重放必含它，留着只会重演成重复 —— 工具折叠不归 `BubbleCommitPolicy` 管，重复看得见）。
  delta **按 part 合并**成"当前全文"（段内至多两条流式文本）：逐帧列表一旦记满整轮，被裁掉的是
  **最旧**的 delta ⇒ 重开窗看到的是**被砍掉开头**的正文；合并后无损且有界。
* **谁负责画 —— `ChatPresenter._replayGate`**（渲染闸）。开窗请求**发出之前**置位 ⇒ 直播不画帧 ⇒
  回执里 `ReplaceHistory` → `DrainSoloFrames`（整段重演）→ 落位 ⇒ 之后照常直播写。
  队列是那段时间**唯一**的绘制方 ⇒ "一帧两画"不可能发生，也就不需要任何合并去重。
  落位点必须覆盖**所有出口**（回执失败/超时/窗口已关/NPC 已切/玩家自己发了消息/关窗/换 NPC/进群/离群/群解散）——
  漏一个出口 = 那个窗口的直播从此静默且**零日志**（与忙标、活跃泡那两次同类）。
* **只吞"队列会补画"的**：闸门判据 `ChatFrameQueue.IsSoloBuffered(ev, kind)` 与 tee 的收帧白名单
  **同源**（见下"复核抓到的一处"）。
* **快照过期兜底 —— 段闭合代数**：`open_chat` 回的是**请求时刻**的账本快照；若某一轮恰好在
  "请求 ~ 回执"之间收口，那份快照里没有它、段又被刚到的 `npc_reply` 清掉 ⇒ 两边都够不着
  （重开窗**凭空缺一整轮**，且没有任何日志痕迹）。判据 = `ChatFrameQueue.SoloEpoch`
  （`npc_reply` / 隐式闭段 / 安全阀清段各 +1；`user_say` 不加）—— 变了就**补一次请求**（上限 2 次）。
* **视图钉底**：`ChatWindow.HoldScrollAtBottom(6)`（批量重建后 6 帧无条件钉底），见 2026-09-16-工具结果折叠.md 那条。

**用户报的三条症状分别对应**：①②由"始终记 + 整段重演"解决（`user_say` 也补回来了），③由钉底保持解决。

**复核（同日，用户要求"复核一遍最近的修改，确认没有问题"）抓到一处真洞**

闸门最初吞**该 NPC 的每一帧**，而队列只收白名单里那几类 ⇒ `stats_update` / `compact_result` /
`step(sys|ctx)` 被吞掉后**两边都没有**（既不直播也不重演）。其中 `compact_result` 是
"正在压缩中"那一行**唯一**的收尾信号：吞掉就停在那儿直到看门狗误报"长时间无响应"
（而压缩其实成功了），且全程零日志 —— 与"漏一个落位出口"同一失效形态。
**修法 = 判据同源**：`ChatFrameQueue.IsSoloBuffered(ev, kind)` 同时被 tee（收帧）与闸门（吞帧）调用，
并把 `step` 的 kind 白名单从 tee 挪进队列（`IsPlayableStepKind`）。加新帧类型时只有这一处要动。
（同一次复核还顺带在 Python 侧抓到第二处 —— 工具结果剪枝的替换节点会进 UI 投影，见 2026-09-17-剪枝节点进UI投影.md。）

**已知取舍（改之前先读）**
* 补回来的是"**玩家开口之后**"的那一轮。重开窗后**立刻**又发下一句（或回放请求失败/超时）时，
  前一轮的补演会**让位给直播**（不叠着画）—— 那一段没丢：它仍在账本里，等那一轮收口后
  **下一次开窗**随历史一起出现。
* 回放请求失败/超时（10s 上限）时闸门照常落位，但队列里的段**不消费**：直播接着画，
  屏幕上可能缺一段；下一次成功回放（开窗 / 切人）会连它一起画出来。
* **群聊不改**：它有 baseline + `room_say` 终稿覆盖两套去重，且群窗重放读的是 `Room.log`
  （与单聊的账本口径不同）。
* 关窗重开**不补**"输入侧折叠"（`step(sys|ctx)`）：那两类按设计只实时不重放（与 UI 历史投影不投影它们同口径）。
