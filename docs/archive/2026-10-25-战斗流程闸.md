## 1. 那次"点了没反应"的完整因果链

真机 `Player.log` 10-25 18:51（一秒不差）：

```
18:51:10.638  开段（页=20203，寻仇开场页）      ← 引擎自己开（栈: TimerCoroutine:Run）
              这一页只有一枚按钮：100003（就是「战斗」）
18:51:13.086  「关窗」                        ← ⚠ 假的：那一页根本没关（见 §5）
18:51:18.251  取增量 本次 1 条 → AI 对话已发起 ✓（用户第一次点「对话」，成功）
18:51:22.014  工具 world_ai_action(attack) 完成 → 入队
              「当前发不出去，等战斗链收场后自动执行」
18:51:28.123  选项点击「战斗」（用户点引擎页上的战斗）
              选项丢弃（没有 4TTqqu 的活动段）
18:51:28.687  [DeferQueue] 落刀：攻击玩家     ← ★ 排队那条又开了一次同一页 ★
18:51:30.395  弹出进战斗的预告窗（等你点应战）
18:51:32.349  进入战斗 / 预告窗关了（同一毫秒）
18:53:54.125  闸1.5 认领 dramaId=20403【内容随结果送达：正文不投】
18:53:54.128  区间读数 共 3 行，标消费 1 行
18:53:56.757  取增量 本次 0 条 → AI 对话已发起（本段无新增内容，不重复投递） ← 静默丢弃
```

**根因**：引擎的剧情链（玩家点「战斗」）与**我们排队的工具动作**（NPC 那条攻击）**重叠**，
同一页被开了两次。第二次的页整行被标成【不投：我方工具链】，处置页也被标成
【内容随结果送达：正文不投】⇒ 段里全是不可投递的行 ⇒ `TakeDelta` 返回 0 ⇒
`Trigger` 那条 `lines.Count == 0` 提前返回 ⇒ 玩家看到的是"没反应"。

**为什么不是"分段碎裂"**：即使把两段合并，那三行仍然全是不可投递的，
`TakeDelta` 照样返回 0。分段不是根因（这一条我误判过，已当场撤回）。

## 2. 用户拍板的设计（**别自作主张扩大**）

用户原话：

> 如果选项是战斗的话就不允许去让 NPC 再调用工具了，因为会造成恶性的影响，其余的倒是没什么影响。
>
> 即将进入战斗的时候应该禁止传送切磋和攻击这些工具的调用，**而不是禁止所有的工具**。
>
> 不管是寻仇进入战斗还是进副本，只要是将处于这种状况，就应该禁止。

| 档 | 工具 | 战前 / 战中的处置 |
|---|---|---|
| **当场拒绝**（不排队、不补做） | `world_ai_action`：`attack` `spar`<br>`movement`：`teleport` `summon` | 回一句说明后作废 |
| **排队等**（此间事了自动办理） | 赠予 `economy_item`、讨要 `item_acquire`、组队 `team`、关系 `social_relation`<br>`lun_dao` `shuang_xiu` `yao_yue` `chuan_gong`、`travel` | 走既有 `DeferredActionQueue` |
| **照常** | `inspect_unit` `search_units` `query_world` | 完全不经过这道闸 |

**为什么前四样是"拒绝"而不是"排队"**：排队的语义是"等会儿办"，而攻击/切磋的语义是
"把玩家拖去打一场"。仗都已经打了，等会儿补一刀就是**把已经发生的事再办一遍** ——
18:51:28.687 那条落刀正是这么来的。

**用户明确不要的**：不要主动往回合里塞「玩家此刻正忙、不能调用工具」这种提示。
只在真被拒这一下说清楚（说三件事：发生了什么 / 为什么这次不行 / 别重试）。

## 3. 两个状态

|  | **战前** `PreBattle` | **战中** `InBattle` |
|---|---|---|
| 含义 | 游戏已经把这场架摆到台面上 | 已经在打 |
| 性质 | **记忆态**（点亮后保持，直到明确证据） | **实时电平**（不需要记忆） |
| 点亮 | ① 页上有开战按钮 ② 应战窗亮着 ③ 点了开战按钮 | `BattleActive()` / `IntoBattle` |
| 退出 | 见 §4 | 战斗位落（且确实见过它亮） |

### 3.1 为什么战前必须"记住"

实测那 20 秒里几个电平有一段**同时为假**的空洞：

```
18:51:28.141  剧情页关（页级闸灭）
18:51:30.395  应战窗才弹
       ↑ 中间 2.2 秒什么都不亮，而排队那条攻击在 28.687 落刀
```

只查"此刻这一帧"必然漏掉它。所以战前是记忆态。

## 4. 退出条件（全是明确证据，不看秒数）

| 退出条件 | 依据 |
|---|---|
| 开打了 | 转战中 |
| 战前期间点了**非开战**按钮 | 婉拒（切磋页 212041「我现在没有空」就是这一枚） |
| 开了一页**没有开战按钮**的新页，且没点过开战按钮 | 这场戏往下走了 |
| 应战窗关了但没进战斗 | 取消了应战（接受时"窗关"与"进战斗"同一毫秒，实测 18:51:32.349） |
| **兜底**：60 秒内**一条证据都没有** | 见 §4.1 |

**"点了开战按钮"之后转成"已确认"**：此后不再因"页没了/来了新页"退出，
只有真打起来（或兜底）才结束 —— 因为点了就代表这场架一定要打。

### 4.1 兜底为什么必须有、又不是"用时间猜因果"

用户 10-25 明确否掉过时间窗归因（"点了无关选项后来自己去打副本就误判了"/"超过 15s 又有问题"）。
**兜底做的是另一件事**，两者必须分清：

| | 时间窗归因（已否掉） | 兜底（保留，用户确认） |
|---|---|---|
| 回答的问题 | "是哪一枚选项引起的开战" | "这个状态已经没有任何证据支撑，还要不要挂着" |
| 出错代价 | 学出错误的开战按钮（全局污染） | NPC 早一点恢复自由（局部、可观察） |

**必须有**：战前是记忆态，没有出口的话，一个假信号能让某个 NPC **永久**不能攻击/切磋/传送，
而且**不报错**（本仓最警惕的失败形态）。
**而且是"零证据才计时"**：应战窗亮着 / 战斗位亮着 / 又来了开战页 ⇒ 一律续期，
所以 10-25 那个 2 秒的假关窗根本走不到兜底。

## 5. 一个必须记住的坑：`关窗` 会说谎

```
18:51:13.086  [SegRec] 关窗 ⇒ 起 1s 待定窗
```

**那一页根本没关。** 15 秒后的 18:51:28.123 玩家还在同一页上点到了「战斗」
（`选项点击："战斗"｜页=20203`）。

原因：`DramaWindowName()` 判的是 **UI 层层顶的名字族**。那一刻那一页被别的东西盖住了
（我们的对话面板 / 转场），层顶换人 ⇒ 名字里没有 "Drama" ⇒ 判成"关了"。

**结论：任何"页还在不在"的判据都不能用层顶。** 本功能因此**完全不看**"窗关没关"，
只看"点了什么 / 应战窗 / 战斗位"这三件独立的证据。

## 6. 三个信号源（各案子分别靠哪个）

| 案子 | 点亮战前的时刻 | 信号 | 可靠度 |
|---|---|---|---|
| **寻仇**（页 20203） | 页面弹出（18:51:10，**早于 NPC 调工具 11 秒**） | 页上有 **100003** | 配表事实（游戏自己打出的 `id=100003`） |
| **切磋**（页 21204） | 页面弹出 | 页上有 **212042** | 配表事实（`options="212042\|212041"`，仓库早有常量） |
| **进副本** | 命令跑起来那一刻 | `DramaFunction:IntoDungeon` | 真机 4 次栈帧一致 |
| 应战窗 | 窗亮起 | `NpcInitiativeMonitor.BattlePreShowing()` | 全日志只见过 1 次（今日寻仇那场） |
| 已经在打 | 进战斗 | `BattleActive()` / `IntoBattle` 前缀 | 两侧日志同毫秒，从没失手 |

**主判据是页级**：它是唯一赶得上的（比 NPC 调工具早 11 秒、比排队落刀早 18 秒）。

### 6.1 副本那一类的编号是"读"出来的，不是猜的

`ConfDramaOptionsItem.function` 在真机上**恒为 0**（10-25 四个样本：100003/240091/232071/232073），
所以读不到"这枚选项要开打"。改用**调用栈作用域**：

```
UIDramaBase:ClickOption(ConfDramaOptionsItem)      ← prefix 开作用域
  → DramaFunction:OptionsFunction(String, …)
    → DramaFunction:IntoDungeon(String[])           ← 在作用域内 ⇒ 学到"刚才那一枚"
      → WorldBattleMgr:IntoBattle(…)
```

- 作用域**内**来的进副本命令 ⇒ 把这枚编号记成开战按钮（写盘）；
- 作用域**外**来的（引擎自己发起）⇒ **一律不学**（无从知道是哪一枚引起的）；
- **零秒数**：判据是"栈里还在不在 `ClickOption`"，不是"隔了多久"。

## 7. `WorldBattleMgr.IntoBattle` 的正确定位

用户问过"不是有 `IntoBattle` 吗，用它不行吗"。**能用，但不能当主判据**：

| 时刻 | `IntoBattle` 到了吗 |
|---|---|
| 18:51:22 NPC 调攻击 | ✗（晚 10 秒） |
| 18:51:28.687 排队落刀 | ✗（晚 4 秒） |
| 18:51:32.349 进入战斗 | ✓ |

它太晚。**它的正确用途**：① 切到战中；② 作废队列里躺着的攻击/切磋；③ 兜底。

**挂的是全部重载**（三个签名都见过），重载名只进日志、**不当分类器** ——
`IntoBattle(WorldUnitBase, Int32, …)` 全日志只有 1 个样本，凭它区分"NPC 打架 vs 副本"
就是拿未校准的换已校准的。

**一个反例**：18:33 那次点「开始战斗」是**秒杀**，`OnBattleWin` 当场跑了，
整段没有 `IntoBattle`、没有战斗场景加载。但它也没进战斗场景 ⇒ 不存在"两场架叠一起"的窗口。

### 8.1 为什么闸开在工具层，不开在对话轮次里

现有的"玩家忙"闸开在**回合**上（`busy` 帧 → `speech_only_turn`）。它的漏洞：
**只有"玩家点剧情页对话"那条路会带 `busy`**。玩家**直接在聊天框打字**说话时没有任何标记 ——
战斗中他打字要 NPC 打人，旧实现会排队、打完真去打一次。

工具层读的是**当下这一刻**，不管这轮怎么起来的，一视同仁。

## 10. 真机探针要看什么（下一步）

**A. 接线是否真的挂上**（启动日志三行）：

```
[BattleFlow] 已接线：内置/落盘的认战前按钮共 2 个，兜底 60s，采样 0.25s/次
[BattleFlowHooks] DramaFunction.OptionsFunction=已挂（进副本学习可用）
[BattleStartHook] WorldBattleMgr.IntoBattle=N 个重载均已挂
```

**B. 寻仇场景**（今天那个故障）应当出现：

```
[BattleFlow] 状态：PreBattle ⇐ 页 20203 上有开战按钮 100003
[ToolExecutor] 战前/战中拒绝：攻击玩家（state=PreBattle 表=2 号 lastPage=20203）
```
而**不再出现** `[DeferQueue] 落刀：攻击玩家`。

**C. 处置页点「对话」**应当能拿到内容（不再静默）。若仍静默，看诊断行：

```
AI 对话已发起（本段无新增内容，不重复投递）：… 战场态=state=Idle …
```
⇒ 说明那一页没被点亮（据此判断该补哪一闸）。

**D. 学编号**（进副本那类）：

```
[BattleFlow] 学到开战按钮 XXXXX（由DramaFunction:intoDungeon在点击作用域内确认）
```
外加 `battle_flow_ids.json` 里多一项。**若看到"不在任何点击作用域内 ⇒ 不学"，那是正常降级**，
但连续多次都这样就要查 `OptionsFunction` 的调用栈是否与真机一致。

**E. 兜底**（只在真的卡住时出现）：

```
[BattleFlow] 状态：Idle ⇐ 兜底：连着 60 秒一条证据都没有
```
若频繁出现 ⇒ 某个点亮信号的判据有问题（不是兜底的错）。

## 11. 刻意没做的事

| 没做 | 为什么 |
|---|---|
| 拿 `IntoBattle` 的重载当分类器 | 样本太少（`(WorldUnitBase, …)` 全日志 1 次） |
| 拿"秒数"归因"哪枚选项引起的开战" | 用户明确否掉；且"点无关选项后自己打副本"会误判 |
| 拿"窗关没关"当退出证据 | 层顶会说谎（§5），用了这个 bug 会原样复现 |
| 一刀切禁全部动作工具 | 用户明确反对；且会让 NPC 变哑 |
| 主动塞"你现在正忙"的提示 | 用户明确不要；会改变 NPC 性格、浪费话 |
| 把学到的编号按存档分开存 | 编号是配表事实，不随存档变（学错了手改 json 即可） |

## A. 原来的毛病：一个"忙"字，三份互不相同的口径

| 旧位置 | 内容 |
|---|---|
| `NpcInitiativeMonitor` 1017~1467（451 行）| 底层读数 + `BusyReason` + `YieldReason` + 一堆原始件 |
| `ModMain.Init` 里一个 27 行 lambda | 排队器的五条件 |

而"忙"其实有**四个真实不同的视角**，成员与顺序都不同：

| 视角 | 谁问 | 成员（按判定顺序） | 为什么是这个集合 |
|---|---|---|---|
| `SpeechBlock` | 主动互动日节拍 | 未进世界 · 玩家死亡复活中 | 只拦"根本不该开口"；**战斗中不在此列**（战斗中允许传音，只弹横幅）|
| `BusyReason` | 发给 Python 的 `busy` 帧 | 战斗中 · 我方挂起 · 剧情窗 · 战斗界面 · 对话窗 · Mask · Window | 玩家忙 ⇒ 本回合只许言语+只读 |
| `YieldReason` | 排队器（让路）| 剧情窗 · Mask · Window | **刻意不含对话窗**：直发路径就是在对话窗开着时弹窗的；算进去会把执行拖到玩家关窗 |
| `ExecuteBlocker` | 排队器（能不能落刀）| 链收尾 · 战斗中 · 我方挂起 · Yield · 不在主世界 | 问的是"游戏能不能接住原生窗"，不是"玩家有没有空说话" |

**合并四者会立刻产生 bug**（把 Yield 并进 Busy → 直发路径永远排不上队，用户 09-24 拍板过一次）。
所以这次**不是合并，是分层**。

## B. 现在的结构

```
state/
  WorldStateFacts.cs   只读世界电平（唯一碰 g.world / g.ui 的地方，零判断）
  WorldStateCore.cs    纯逻辑，四个视角的组合（零 Unity，可单测，53 项断言）
  WorldStateGate.cs    组装快照 + 注入剧情标记 + 对外四个入口
  BattleFlow{Core,Gate,Hooks}.cs   战前/战中（第一步搬来的）
```

`NpcInitiativeMonitor` 只留**同名一行转发**（13 个），所以 24 个文件、73 处调用一行都不用改。

**为什么剧情标记要注入**：`state/` 不依赖 `drama/`（否则成环，表现为初始化顺序敏感、偶发不生效）。
`ModMain` 注入两个 `Func<bool>`（`ChainHold` / `HasPending`），与 `DeferredActionQueue.WaitBlocker`
的既有套路一致。**未注入一律当 false**（= `DramaGate` 的空态，行为同改造前）并打一行 ⚠。

## B. 核对出的问题（都已修）

| # | 问题 | 性质 | 修法 |
|---|---|---|---|
| 1 | `MaskLayerName()` / `WindowLayerName()` 把"这一层挡不挡人"编码成"名字是否非空"。改造前判的是 `UiVisible(top)`，两者**只在"层顶可见、但名字读到空"时不同** —— 那一刻旧代码算"挡着"，新代码算"没挡" ⇒ **fail-open**（模态遮罩挡着，我们却去弹原生窗，正是本模块存在的理由）| 我在重构里引入的**语义窄化** | `VisibleLayerName()` 助手：可见但没名字 ⇒ 返回占位符 `(未命名)`；两个层判据共用一处 |
| 2 | 点击作用域只在 postfix 里闭合。引擎的 `ClickOption` 内部抛异常 ⇒ Harmony postfix **不跑** ⇒ 作用域**永久泄漏** ⇒ 此后"引擎自己发起的进副本命令"会被记到一枚早就点过的选项上 ⇒ 那一页**永久被当成开战页** ⇒ 攻击/切磋/传送/召唤被持续误拒（落盘后跨存档）| 真 bug（设计里已知这个失败形态，但只防住了"postfix 不存在"，没防"postfix 没跑到"）| 作用域搬进纯逻辑核 `ClickScope`，带**帧号**：`ClickOption → OptionsFunction → IntoDungeon` 是真机栈证明的**同步调用**，同步 ⇒ 同一帧；帧号不符 ⇒ 就地作废（自愈），并报 `Expired` 与"压根没点"分开记。另外两处配套：`Enter` 先把**跨帧残留**清掉（否则 `Exit` 会把泄漏的编号"还原"成活作用域）；`NoId` 与 `Outside` 分开记（"没人点" vs "点了但字段读不到"）|

第 5 条值得单独说：那句话读起来很安全，实际把**唯一危险的失败形态**说反了。一个人照着它推理，
就会认为"学习路径随便写，反正只会少挡"，而问题 2 恰恰是从这个假设里长出来的。

### B-1. 两处**不是**逐字的（都无害，但要写出来）

复核时我对搬动部分的结论是"逐字一致"，有两处例外，方向都安全：

| 位置 | 旧实现 | 新实现 | 差异的性质 |
|---|---|---|---|
| `SpeechBlockReason` 的"没有玩家单位" | `g.world.playerUnit == null` —— 若 `g.world` 本身是 null，会抛 ⇒ 落到 catch ⇒ 文案是 **"playerUnit 读取异常"** | `g.world == null ⇒ Absent` ⇒ 文案是 **"playerUnit=null（未进世界）"** | **只有文案不同**，两边都是非空原因 ⇒ 判定相同 |
| `ExecuteBlocker` 的⑤"不在主世界" | `g.ui.GetUI(UIType.MapMain) == null` —— 若 `g.ui` 本身是 null，会抛 ⇒ catch ⇒ 跳过⑤ ⇒ 返回 ""（**放行**） | `g.ui == null ⇒ MainWorldReady=false` ⇒ 返回 "不在主世界（世界界面未就绪）"（**拦住**） | 旧的是 fail-open，新的是 fail-closed。`g.ui` 为 null 意味着界面系统还没就绪，此刻弹原生窗本来就发不出去；而排队器有 600 秒硬顶，不会永久卡住 |

第二条是**真的语义变化**（虽然只在"UI 系统整个没就绪"这个瞬时），方向上更安全 —— 但既然要让后来人
能信任"这次重构没改语义"，就得把它写出来，而不是靠"反正感觉一样"。
