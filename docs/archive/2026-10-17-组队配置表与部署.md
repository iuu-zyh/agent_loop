## 一、核心结论（本次调研验证）

### 1. 为什么市面上的组队 mod 只能带 1 个人

它的 `DungeonTrigger` 里只写了这一行：

```
addBattleNPCData_MID&003_0
                      ↑ 索引 0
```

官方文档 `配置对照表.xlsx → 副本作用功能` 第 56 行：

> `addBattleNPCData` | NPCID (NpcCondition表) | **索引** |
> 「将 NpcCondition 表中 ID 为 100201 的 NPC 组中**第一个** NPC 加入战斗 NPC 容器中」

而同一张表第 36 行：

> `clearBattleNPCDatas` | **其他清除指定索引（1-5）**

**容器有 5 个槽位，引擎原生支持 5 人。作者只写了一行。**

### 2. 重伤机制的真相

不是「队友被打倒 → 直接挂气运」，而是一条三段式链路：

```
DungeonTrigger (triggerType=14，每 1 秒刷)
  └─ unitAddEffect_<条件组>_<BattleEffect ID>
       └─ BattleEffect  typeID=6009「自身死亡时打开剧情对话」
            └─ DramaDialogue  openFunction: addNPCLuck_1_<重伤气运ID>
```

官方 `效果配置对照表.xlsx → 效果ID对照` 第 416 行：

> `6009` | **自身死亡时打开剧情对话** | 参数1 = 剧情对话ID | 一次性

### 3. 代码路径（已验证可用，不依赖配置表弹窗）

实测日志（`team_multi.log`）：

```
23:37:22  ✅ 气运反查成功：结伴而行=-2004589688  对话对象=-2004589686
23:38:00  ★ 挂气运策略 #2 成功：new DataUnit.LuckData{id} → u.CreateLuck(data)
23:38:00  [第72拍] 周围1格内NPC=3 [方成和,张票,江宇文]  本拍新挂=3
23:38:53  [第133拍] 张票(13,9)   ← 从 (12,6) 跟到玩家所在格
```

**结论：气运挂载、NPC 识别、跟随行为全部走通。**
`team` 工具因此可以不依赖 `DramaDialogue`/`DramaOptions`（少建两张表、不必覆盖原版 22604）。

> 但气运**定义**仍必须在 `RoleCreateFeature` 表里 —— 代码只能挂「已定义」的气运。

### ★ 为什么队友标记必须"一槽一枚"（10-18 真机定案，别合并回去）★

原先三个号位共用一枚「结伴而行」，靠 `NpcCondition MID&003` 的 条件1/2/3 各筛一次。
真机日志（`docs/archive/2026-10-18-组队实验记录表.md` E11）证明这样会出**重复队友**：

```
[①npcUnits]     方成和、温芸、方成和      ← 同一人两次
[②气运持有者]    方成和、温芸、祁曼荷、张票、江宇文（5 人）
```

根因（反汇编 `ConfNpcCondition::GetUnitsInID` 确证）：

- 条件组**没有去重** —— 尾部只有 `list.RemoveAll(u => u == null)`；
- `sortType=0` 走 `CommonTool.SortRandom` ⇒ 每段都是"从同一池子独立随机抽一个"，**有放回**。

⇒ 三个**相同**条件 = 抽三次。5 人池抽 3 次互不相同的概率只有 5·4·3/5³ = **48%**。

改成每槽筛一枚**不同的**气运后，每段候选集恰好 1 人，
**引擎怎么随机都只能是那一个人** —— 重复从概率问题变成结构不可能。

⚠ 代价：队伍不满 3 人时，空着的号位筛不出人，`addBattleNPCData_<槽>` 会拿到 `null`。

### 配套数据模型：气运有两层存储（10-19 反汇编定案，读写必须成对）

| 层 | 位置 | 谁读 | 写 | 删 |
|---|---|---|---|---|
| 运行时层 | `WorldUnitBase.allLuck`(+0x40) | `GetLuck(id)` ⇒ **`feature_1_*` 条件** | `u.CreateLuck(data)` | `u.DestroyLuck(lk)` |
| 存档/面板层 | `propertyData.addLuck`(+0x120) | NPC 面板、存档 | `propertyData.AddAddLuck(data)` | `propertyData.DelAddLuck(id)` |

- **挂**：两层都写（`TeamTool.AddLuck`）——缺运行时层 = 条件看不见（E13：探针挂载
  面板可见但 `GetUnits`=0，触发器整条不跑）；缺存档层 = 面板空白、读档丢失。
- **删**：两层都删（`TeamTool.RemoveLuck`）——只删运行时层，一读档又被物化回来。
- 存档层→运行时层的物化只发生在**读档**时（`WorldMgr::EnterWorldFixData`）。
`team.status` 会报 `slots_left`，模型据此知道"还差几人满编"。

### 关键实现细节（都是真机踩过的坑）

1. **气运 ID 按名反查，绝不硬编码**
   `MID&51` 导出后是 `excelMID + 51`，而 `excelMID` 由官方编辑器随机分配。
   反查走 `GetItem(id)` 在 `[excelMID, excelMID+300]` 区间探测 ——
   **不能用枚举 `_allConfList`**（Il2Cpp 的 `List<T>` 不实现 `IList<object>`，
   探针实测能读到 `Count=1372` 却取不到元素）。

2. **三条挂载策略**
   `CreateLuckInID` 返回的对象 `luckData` 是 **null**（会 NRE），
   真正可行的是 `new DataUnit.LuckData{id} → u.CreateLuck(data)`。
   每条策略都做 `GetLuck(id)` **读回复查** —— 没抛异常不算成功。

3. **玩家判定用 `unitID` 相等**
   引用判等（`u == player`）在 IL2CPP 包装器上不可靠 —— 探针实测
   把「结伴而行」挂到了玩家自己身上。

4. **摘气运用 `DestroyLuck`**
   引擎**没有** `RemoveLuck`（早期按猜的名字调，编译期就挂）。

5. **上限口径**
   `TeamTool.MaxMembers = 3` 必须与 `DungeonTrigger` 里写的容器槽数一致
   （契约测试 `test_max_members_matches_config_table` 会真的去读 xlsx 对账）。

# 八、复核结论（10-17 深夜，逐条走查）

按「表 → 代码 → 引擎」三层逐个对账，**查出 4 个会致命但完全静默的问题**，全部已修。

## 8.1 `MID&180` 表条目缺失（会让 invite/dismiss 卡 120 秒）

```
代码要开 Mod+180（MID&180）      ← DramaTeamInviteBase
DramaDialogue 里有 MID&190       ← 但偏偏没有 MID&180
```

`ShowDramaService` 文件头写过同类事故：缺条目时 `OpenUI → RandomDramaID` 查表失败，
打一句「找不到剧情ID：xxx」后**静默不开窗、不抛异常** ⇒ `DramaGate` 120 秒超时。
玩家看到的是「点了工具，屏幕上什么都没发生」。

**已补**：`DramaDialogue MID&180` + `DramaOptions MID&181/MID&182` + `LocalText` 3 条。

## 8.2 气运名指向了**别人 mod 的 key**

```
抄来的：role_feature_postnatal_nameMID&001   ← 组队 mod 的 LocalText key
我加的：team_feature_name_51                  ← 自己的 key
```

双重后果：

1. 气运名显示成一串乱码（`role_feature_postnatal_name-803158450`）
2. **更致命**：`FindLuckIdByName` 是**按中文名比对**的。翻译不出来时比对的是展开后的 key，
   永远不等于「结伴而行」⇒ 反查返回 0 ⇒ 工具直接失败「气运表里找不到『结伴而行』」

**已改**：三行气运的 `name`/`tips` 全部指向自己的 `team_feature_*` key。

## 8.3 `dismiss` 的「解散整队」是死代码

```csharp
if (who == null) { /* 解散整队 */ }        // ← 永远进不来
```

因为 `ResolveCounterparty` 在 `target` 留空时**返回玩家单位**（既有约定），`who` 不可能是 null。
于是「解散整队」永远走不到，实际走的是「请离玩家」分支。

**已改**：判据换成 **`target` 有没有点名一个具体 NPC**：

| 入参 | 行为 |
|---|---|
| `target` 留空 / `target`=玩家名 | **解散整队** |
| `target` = 某个 NPC 真名 | 只请离那一位 |

## 8.4 气运挂错了对象（最严重）

按你的口径，`target` 填玩家名 = “我这个 NPC 跟你走”。但原代码把「结伴而行」挂到了**玩家**身上。

为什么必炸：`DungeonTrigger MID&001` 靠 `npcConditionExamine_MID&003` 挑人进副本，
而 `NpcCondition MID&003` = 「带『结伴而行』的人」。气运挂在玩家身上 ⇒ 条件组把**玩家**当成队员
⇒ 容器槽里塞进玩家 ⇒ 真机必炸。

**已改**：

```
target 填玩家  →  队员 = 发起方 NPC 自己（气运挂 self）
target 填 NPC  →  队员 = 那个 NPC（气运挂 who）
玩家永远不作为队员被写入容器
```

## 8.5 队伍生成语句改成「配对」写法

原写法 `addBattleNPCData_0 / _1 / _2` + 一次 `addBattleUnit`，但 `addBattleUnit` 一次只生成一个
⇒ 很可能仍然只上来 1 人。改成**容器与生成配对三次**（mod 原版就是一对，只是它只写一对）：

```
addBattleNPCData_MID&003_0 | addBattleUnit_MID&003_-1_10_2_1_2_0
addBattleNPCData_MID&003_1 | addBattleUnit_MID&003_-1_8_2_1_2_0
addBattleNPCData_MID&003_2 | addBattleUnit_MID&003_-1_6_2_1_2_0
setBattleData_alTeamIn_ok
```

`x=-1` = 玩家面前，`y` 用 10/8/6 错开避免叠在同一格。

> ⚠ **这一条仍需真机确认**。官方文档在两处给了矛盾的证据：
> `npcConditionIndex` 写「单位索引 1-5、**0-所有**」，而 `addBattleNPCData` 的示例注释写「**第一个**」。
> 若实测仍是 1 人，按下面顺序换：
> 1. 只留 `_1/_2/_3`（若索引是 1-based）
> 2. 只留一对（若 `_0` 确实是「全部」）
> 3. 改用 `addMultiNPCLuck` 同族的批量思路，或走 C# 直接生成

# 九、动态气运描述（新需求，已实现）

## 9.1 要什么

| 谁 | 气运 | 描述 |
|---|---|---|
| NPC 队友 | 结伴而行 | 「正与**「唐炎」**结伴同行」 |
| 玩家 | 组队中（`MID&54`，新增） | 「正与**「江宇文」「张票」**结伴同行」 |

玩家的描述要**随每次邀请/解散更新**。

## 9.2 怎么做到的（反射实证）

```
ConfLocalText  {  Dictionary<String, ConfLocalTextItem> allText;
                  static String GetText(String key)  }
ConfLocalTextItem {  String key, ch, tc, en, kr  }
GameTool.LS(String) → 读的就是 allText[key].ch
```

⇒ **运行时改写 `allText[key].ch/tc/en/kr`，气运面板立刻显示新文案。**

实现 = `csharp/tools/TeamDescService.cs`：

```csharp
SetText("team_feature_tips_54", "正与「江宇文」「张票」结伴同行");
// 四种语言都写：只写 ch 的话，切繁体/英文就露出旧文案
```

## 9.3 为什么不担心“所有人串味”

改的是**共享**文案 key，所有同类气运同时变。在本设计里这是**正确的**：

- **NPC 侧**：描述只依赖「玩家叫什么」，而玩家只有一个 ⇒ 所有人显示同一句是对的
- **玩家侧**：只有玩家一个人挂 `MID&54` ⇒ 只有一条描述，不存在“两个玩家看到不同文案”

反过来说：**不要**用它表达 per-viewer 差异（“张三看到李四不同”）——那做不到。

## 9.4 触发点

```
invite 成功 → SyncTeamState()
dismiss 成功（解散整队 / 请离单人 两条路径都）→ SyncTeamState()
                    ↓
        ① 队友数 > 0 → 给玩家挂「组队中」；== 0 → 摘掉
        ② RefreshPlayerDesc(队友名单)  ← 写玩家那条描述
        ③ RefreshMateDesc(玩家名)      ← 写 NPC 那条描述
```

**写失败不阻断**：文案是展示层，`SetText` 返回 false 只让描述停在上一次的值，
组队功能本身靠气运 ID，不受影响（`test_desc_never_throws_into_business_path` 钉住）。

## 9.5 心跳监听（外部变化也能跟上）

`TeamTool.Tick()` 接到 `DiagSwitches.FrameTick`，**300 帧（≈5 秒）节流**：

```
成员签名（玩家名 + 排序后的队友名）变了才重刷
```

覆盖不经我们工具的改动：队友阵亡离队、读档换世界、别的 mod 直接摘气运。
没变就什么都不做 —— 全图扫描（百~千级单位）不能每帧跑。

**读档必须复位（`TeamTool.ResetTickState`，已接 `OnIntoWorldEvent`）**：
`allText` 会随世界重载从配置**重新初始化**，运行时覆盖全部丢失；而心跳是「签名变了才刷」，
同一存档同一批队友时签名不变 ⇒ 永远不重刷 ⇒ 描述退回配置表那句静态话。
复位 = 清掉签名，让下一次心跳必定重刷。

## 9.6 缺 key 时的表现与定位

`SetText` 遇到 `allText` 里没有的 key 会**静默失败** ⇒ 表现为「气运描述永远是配置表那句静态话」。
所以 `TeamDescService.MissingKeys()` 会自检，心跳里报一次：

```
[team] 文案表缺 key，气运描述无法动态更新：team_feature_tips_54（检查 LocalText.xlsx 是否导出）
```

# 十一、解散扣好感（10-18 补齐）

## 11.1 口径

| 项 | 定案 |
|---|---|
| **方向** | **单边**：只有被请离的 NPC「对玩家」掉好感；玩家对这位 NPC 的看法不变 |
| **实现** | **代码直接扣**，不走配表动作 |
| **数值** | 6 ~ 10（随机），对齐组队 mod 的 `abClose_1_0_-10_-6` |
| **时机** | **先扣好感、再摘气运** |

## 11.2 为什么可以直接扣

解散本来就是**代码摘气运**实现的（`TeamTool.RemoveLuck` → `DestroyLuck`），
没有原生动作可挂好感钩子 —— 配表的 `abClose` 只在**剧情命令**里有意义。

所以直接走同一条写入层：

```csharp
ToolExecutor.ApplyIntim(mate, player, -loss, "组队解散·" + tag);
//                        ↑ holder  ↑ other  ↑ 负值
//              holder = 被请离的 NPC（他的好感掉）
//              other  = 玩家（掉的是他「对玩家」的那一条）
```

`ApplyIntim` 的语义与赠礼/讨要**完全同源**：只传请求值、引擎按 `RoleClose` 系数换算、
我们只回读实得并如实报出。所以原来的 `private` 已改成 `internal`（`TeamTool` 要调）。

## 11.3 为什么是 6~10

mod 配表原文 `abClose_1_0_-10_-6`：

- 参数1 = `1` → **B**（对话对象 = 该 NPC）
- 参数2 = `0` → **A**（玩家）
- 参数3/4 = `-10` / `-6` → 随机区间

即「B 对 A 掉 10~6 点」。这正是单边、且方向与我们一致。

`UnityEngine.Random.Range(6, 11)` 取 6~10 闭区间（该 API 上界独占）。

## 11.4 为什么先扣好感再摘气运

- **先摘气运再扣**：中间若异常 ⇒「人踢走了却一点代价没付」，而且玩家无法补救
- **先扣好感再摘**：最坏是「好感掉了但人还在队里」—— 玩家看得见，重试一次即可

扣好感失败**不阻断**解散（好感是副作用，不是前置条件；与赠礼同口径）。

## 11.5 结果怎么上报

```json
{
  "op": "dismiss", "left": true, "target": "江宇文",
  "intim_lost": -8,
  "intim_detail": [{ "name": "江宇文", "delta": -8 }]
}
```

| 键 | 含义 |
|---|---|
| `intim_lost` | 总共掉了多少（实得之和，负数） |
| `intim_detail` | 逐人明细（解散整队时多人各一条） |

**读不到起点好感时不写这两个键**（缺失 = 未知）。两个理由：

1. `int.MinValue` 混进总和会把结果变成 -21 亿这种垃圾大数
2. 引擎会按 `RoleClose` 系数衰减，请求值 ≠ 实得，报实得才有意义

> 这个坑是**契约测试抓出来的**：汇总处直接 `(int)loss["delta"]`，而该键在
> "读不到起点"时不存在 ⇒ 抛异常。已加判空。

## 11.6 渲染与提示

渲染层（`_intim_tail`）把它说出来，因为**玩家不翻关系面板就看不到这个代价**：

```
江宇文已离队，各自珍重。对方对你的好感下降了 8。
队伍就此散了（江宇文、张票 各自离去）。他对你的好感随之下降：江宇文（-8）、张票（-7）。
```

模型也知道（schema 描述里写明），否则下一轮会把刚被踢的人当成还热络，说错话。
