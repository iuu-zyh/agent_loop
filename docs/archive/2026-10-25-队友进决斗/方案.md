## §1 设计总览

```
                        ┌───────────────────────────────┐
 应战窗出现 (MapBattlePre) │  TeamJoinGate（新增，唯一决策点）    │
 ─────────────────────────►│  队非空？知道对手？→ 弹确认窗       │
                        └───────────┬───────────────────┘
                                    │ 玩家点选（唯一事实来源）
                                    ▼
                        ┌───────────────────────────────┐
                        │  Consent = Yes / No + 对手身份    │
                        └───────────┬───────────────────┘
                                    │
 战斗初始化 (SceneBattle.Init)        │
 DungeonTrigger MID&004 (type=40)    │
   → addBattleNPCData ──────────────►│  TeamContainerInject.Prefix
                                    │    type==40 ?
                                    │      Yes → 注入（照现有代码）
                                    │      No  → 清空容器 + 跳过原方法
                                    ▼
                        战斗打完 (BattleEndFront / BattleExit)
                                    │
                        ┌───────────▼───────────────────┐
                        │ TeamBattleFollowup：按 type 分支  │
                        │  40 →「并肩应战」文案 + 剧情       │
                        │  其它 → 现有「同闯秘境」文案（不动）│
                        └───────────────────────────────┘
```

**三条不变量**

1. **一个决策点**：只有 `TeamJoinGate` 决定"这一场带不带队友"；注入层不复述这个判断，
   只消费它的结论。
2. **一个事实来源**：玩家在确认窗上的点击。没有点击 = 没有同意（默认不带）。
3. **判据是配表事实**：`dungeonBaseItem.type == 40`，不是页 id、不是名字匹配、不是时间窗。

## §2 判定：这场是不是"决斗"

| 时机 | 拿得到什么 | 用来干什么 |
|---|---|---|
| 应战窗出现（询问前） | 没有 `battle` 对象；只能拿**对手**（最近一页剧情的对方） | 只用于立绘与文案 |
| `addBattleNPCData`（注入时） | `g.world.battle.data.dungeonBaseItem.type` | **真正决定**走哪个分支 |
| `BattleEndFront`（收尾时） | 同上 | 决定经历文案 |

⇒ **询问时不需要知道 type**：答案先存着，注入时才知道这场是决斗还是普通副本；
不是决斗就**不消费**（见 §5 生命周期）。

> 这样可以先把功能做出来，不必等"应战窗带不带 dbi"这个探针结论（U5）。
> 若 U5 证明窗里带 dbi，可以在询问前就判掉、连问都不问（更省一次打扰）。

## §3 询问：什么时候问、问什么

### 3.1 触发点

**应战窗出现的上升沿**（`WorldStateFacts.BattlePreShowing()` 由 false → true）。

- 采样已经在 `BattleFlowGate.Tick()` 里做了（0.25s，帧预算决定，不是因果兜底）；
  在同一个 Tick 里调 `TeamJoinGate.OnSampled(preShowing, battleActive)` 即可，
  **不新增定时器、不新增帧回调**。
- 若探针 U5 能挂上 `UIMapBattlePre.InitData`，改成事件驱动（更早、更准），Tick 那条降级为兜底。

### 3.2 前置条件（缺一不问）

| # | 条件 | 理由 |
|---|---|---|
| 1 | `TeamTool.Members()` 非空 | 没队友就没有"要不要一起上" |
| 2 | 不在 `InBattle` | 打起来了不能再问 |
| 3 | 手上有**对手**（最近一页剧情的对方单位） | 确认窗要立绘；判不出对手就闭嘴（不猜） |
| 4 | 对手不是队友本人 / 不是玩家 | 自己人打自己人属于脏数据，不参与 |
| 5 | 本场还没问过（`Consent == None`） | 防重复弹窗（窗可能因重建再报一次） |

### 3.3 窗口与文案

复用 `ShowDramaService.ShowConfirmSimple`（不占 `DramaGate` 槽位，见 01-F6）：

```csharp
ShowDramaService.ShowConfirmSimple(
    ModIds.DramaTeamJoinBase,          // 新段：Mod + 200
    player,                            // left  = 屏幕左位 = 玩家
    attacker,                          // right = 屏幕右位 = 对手
    attackerName + " 来势不善。可要叫上同行之人并肩应战？",
    "一起应战", "我一个人",
    onOk: () => TeamJoinGate.ArmYes(attacker),
    onNo: () => TeamJoinGate.ArmNo());
```

文案口径（与仓里既有风格一致）：
- **不承诺战果**（"并肩"而不是"必能胜"）；
- **不剧透工具**（不说"对方要攻击你"——用"来势不善"这种舞台口吻）；
- 立绘位必须 `left=玩家 / right=NPC`（传反不报错，只会在屏幕上看出两个自己）。

### 3.4 对手从哪来

| 路径 | 来源 | 现状 |
|---|---|---|
| 工具攻击 | `ToolExecutor` 的 attack 分支手里就有 `wub` | 已有 |
| 原生寻仇 | 最近一页剧情的对方单位（`DramaAiOption` 内部就有 `WorldUnitBase npc`） | 需要加一个只读访问器（3 行） |

新增：`DramaAiOption.LastDramaUnit`（只读，最后一次 `NoteSegment` 传入的 npc）。
**判不出（null）就不问** —— 与 `DungeonDramaCore`（"判不出就写『有人』"）同一哲学，
但在"要不要打扰玩家"这件事上更保守：**判不出就不打扰**。

## §4 注入：`TeamContainerInject.Prefix` 的三分支

现在是两分支（"没队 → 放行" / "有队 → 直塞"）。改成：

```csharp
int type = DuelTypeOrZero();          // g.world.battle.data.dungeonBaseItem?.type ?? 0

if (type == 40) {                     // 决斗：由 Consent 决定
    if (TeamJoinGate.Consent == Yes)  return InjectMates(nu, mates);   // 现有直塞逻辑
    // 没同意 / 没答 / 判据坏了 → 一个队友都不许进
    nu.Clear(); TeamJoinGate.Consume(); return false;                  // 跳过原方法
}
// 其余类型：**逐字保持现状**
if (mates.Count == 0) return true;
return InjectMates(nu, mates);
```

三个细节：

1. **拒绝也要 `nu.Clear() + return false`**。不能"放行原方法"——原方法走
   `ConfNpcCondition MID&003`（条件是三枚号位气运，见 01-F1 的配表），
   它会把队友重新选出来塞进容器。**放行 = 变相同意。**
2. `InjectMates` 就是现在 `Prefix` 里从 `nu.Clear()` 到 `★直塞完成★` 那一段，
   原样抽成方法，一行逻辑都不改。
3. `type` 读不到时（`battle.data` 为空 / 字段异常）→ **按非决斗处理**（保持副本的现有行为），
   并打一行 WARNING。理由：宁可让老功能不变，也不要在读不到判据时改变行为
   （这一条的代价是"决斗识别失败时队友会不请自来"——所以 §8 的探针必须先跑）。

### 4.1 配表要新增一行触发器

**不改 `MID&001`**（副本行为一个字节都不动），新增一行：

| 字段 | 值 | 理由 |
|---|---|---|
| `id` | `MID&004` | 新行 |
| `dungeonType` | `40` | 只命中决斗 |
| `dungeonID` | `0` | 不限具体副本 |
| `triggerType` | `2` | 与 `MID&001` 同（"进入战斗时"） |
| `condition` | 同 `MID&001`（`featureNot_…`） | 同一套"别重复注入"的前置 |
| `dramaFunction` | `0` | **★刻意留空**：`MID&001` 的 `setDramaUnitData` 会改剧情单位表，决斗的处置页（20403）不该被换掉 |
| `battleFunction` | `addBattleNPCData_MID&003_0\|_1\|_2` + `addBattleUnit_3/4/5_-1_10_2_1_2_0` + `setBattleData_alTeamIn_ok` | 与 `MID&001` 的 H 列**逐字相同** |

> 为什么不是"把 40 加进 `MID&001` 的白名单"：那会连带 `setDramaUnitData_MID&003_0_0_0`
> （`BattleFunction.SetDramaUnitData`）也在决斗里生效。它改的是**剧情单位数据**，而决斗的
> 战后处置页是游戏自己的 20403（带选项与立绘）—— 影响未验证，不赌。
> **新增一行 = 可回滚（删行即可），且副本路径零改动。**
>
> **`condition` 列的两个写法**：① 与 `MID&001` 逐字相同（`featureNot_MID&003_…`）；
> ② 直接写 `0`（无条件，范围完全由 `dungeonType=40` 圈定）。
> 建议先按 ① 走（与已验证的副本路径同构）；若 P1 探针显示它把决斗挡住了，再改 ②。
> 两者都不影响"要不要带队友"这个决定 —— 那是 C# `Prefix` 的事。

## §5 状态机与生命周期（禁止秒数）

```csharp
enum Consent { None, Yes, No, Consumed }
```

| 事件 | 动作 | 依据 |
|---|---|---|
| 应战窗上升沿 + §3.2 五条 | `None → Yes/No`（等玩家点） | 事件 |
| 玩家点「一起应战」 | `→ Yes`，记下对手 | 玩家点击（唯一事实） |
| 玩家点「我一个人」 | `→ No` | 同上 |
| **没点就进了战斗** | 保持 `None` ⇒ 注入层按"未同意"处理 | 默认保守，不猜 |
| 决斗的 `addBattleNPCData` 到达 | `Yes/No → Consumed`（一次性） | 因果闭合 |
| `BattleFlowCore` 从 `PreBattle` 回到 `Idle` 且**从未进过 `InBattle`** | `→ None` | 这场没打成（取消应战/换页），答案作废 |
| `BattleExit` / 世界重载 | `→ None` | 场次结束 |

**为什么不在"应战窗关闭"时清**：应战窗关闭与 `IntoBattle` **同一毫秒**
（`Player.log:47744/47745` 同 18:51:32.349），中间没有任何可用的"窗关了但没打"窗口；
而取消应战的情况，`BattleFlowCore` 自己会给出 `PreBattle → Idle`（它的判据是
"应战窗关了但没进战斗"，同样是事件不是秒数）。**我们直接复用它的状态转移，不自己造一套。**

## §6 经历文案：决斗要另一套

### 6.1 现状为什么不适用

| 现有模板 | 用在哪 | 决斗里为什么不对 |

| `与{0}同闯秘境，并肩作战。` | 同行 | 决斗不是秘境 |

| `与{0}同闯秘境，战斗中身负重伤。` | 重伤 | 同上 |

### 6.2 新增模板（`RoleLogLocal.xlsx`）

| id | keyID | ch | 用途 |
|---|---|---|---|
| `MID&905` | `eventLogTeamDuel` | `与{0}并肩应战{1}。` | 决斗主记录（{0}=同行者，{1}=对手） |
| `MID&906` | `eventLogTeamDuelDrama` | `与{0}共历此战：{1}` | 战斗内剧情（{1}=`DungeonDramaCore.Format` 的成品句） |
| `MID&907` | `eventLogTeamDuelHurt` | `与{0}并肩应战{1}，战斗中身负重伤。` | 决斗里倒下的队友（与副本「重伤」同义，但不用"秘境"措辞） |

- `{1}` = 对手名（来自 §3.4 记录的 attacker）；取不到时退化成
  `与{0}并肩应战强敌。`（**另有一行 `MID&907` 兜底，或代码里两模板二选一**）。
- 仍走 `AddLogData(unit, keyID, values, cond)`，**只写 NPC 队友**，不写玩家。
- 模板缺失时沿用 `EnsureDramaLogTemplate()` 那套"运行时克隆注册"的做法
  （`TeamBattleFollowup.cs:878`），功能先能用，表后面补。

### 6.3 `TeamBattleFollowup` 的分支点

```csharp
// OnBattleEndFront 开头
_kind = ReadBattleKind();   // dbi == null ? None : (type == 40 ? Duel : Dungeon)

// OnBattleExit
if (_kind == Duel) {
    // ① 归队传送：照做（队友是从别处被拉进战场的，战后要回到玩家身边）
    // ② 重伤/离队：照做（判据是"战场上真倒了"，与副本同一套；不依赖 MID&002 气运）
    // ③ 击杀战报：**跳过**（决斗没有"斩杀怪"语义；且 BattleKillStats 里可能是 0）
    // ④ 同行经历：Duel 模板
    // ⑤ 剧情：Duel 剧情模板
} else {
    // 现状，逐字不变
}
```

**为什么重伤/离队照做**：判据是"战场单位 `isDie`"（`SnapshotDeadMates`），
那是**事实**；决斗里队友被打倒就是被打倒，与副本同义。
配表侧**不**把 40 加进 `MID&002`（那行会给 3/4/5 位挂「内外重伤」气运），
所以"输了就重伤"不会发生，只有"真倒了"才会。

### 6.4 剧情从哪来（现有链路，不改）

`DramaLedger` 的战斗窗已经在 `★直塞完成★` 开、`BattleExit` 关；
决斗同意注入后自然就有了窗口，战斗内与战后处置页（20403）都会进账本。

> 唯一差别：决斗的**开场页**（20203）在应战之前，不在窗口内。
> 用户口径是"战斗期间的剧情"，所以**不额外扩窗**（要扩的话是另一个决定，见 §11 的 P3）。

## §9 失败姿态与边界

| 情形 | 处置 | 为什么 |
|---|---|---|
| 确认窗弹不出来（配表没导出） | 走 `onNo`（= 不带队友），打 ERROR | `ShowConfirmSimple` 内部已经把"开窗失败"当婉拒 |
| 玩家不答就开打 | 不带队友 | 没点 = 没同意 |
| 对手判不出 | 不问、不带 | 判不出就不打扰（比"问了也白问"好） |
| 决斗里 type 读不到 | 按副本处理（现有行为） | 不改老行为是硬约束；代价写进日志 |
| 注入抛异常 | 放行原方法（现有 catch） | 不能挡战斗；但会打 ERROR |
| 剧情账本取不到内容 | 只写主记录，不写剧情条 | 现有逻辑（"不写空条目"） |
| 队友中途入队/离队 | 以战斗开始时容器里实际注入的为准 | 现有 `_mates` 快照语义 |

**明确不做**：
- 不做"决斗里队友重伤离队"的新规则（沿用现有 `isDie` 判据）；
- 不做"切磋带队友"；
- 不做"战斗结束后追问要不要再打一场"；
- 不用任何"等 N 秒"的兜底（所有退出条件都是事件或状态转移）。

## §10 备选方案（不改配表）

若不想动 `DungeonTrigger`：

**B 方案**：在 `SceneBattle.Init`（或首个帧回调）里，type==40 且已同意时，
自己调 `BattleFunction.AddBattleUnit(unit, pos, UnitType(2=盟军), moveType, …)` 把队友塞进战场。

- 优点：不依赖配表触发器；
- 缺点：① 得自己挑坐标/朝向/进场方式；② `npcUnits` 与 `_mateBattleUnits` 的一致性要自己维护
  （收尾链的 `_armed` 判据读的是 `npcUnits`）；③ `UnitType` 的枚举值需要一次真机校准。
- **结论：只在"配表不可动"时用**；主方案走 A。
