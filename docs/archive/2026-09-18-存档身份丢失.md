# 存档身份会丢：Python 重启窗口里的读写全落「扁平目录」

> ⚠ **已归档**。本文是一次性排查记录，没有对应的现状文档，**日常开发不用看**。
>
> **结局**：补了身份帧的持久化/补发，重启窗口不再落扁平目录。

---

#### 现象与病根

用户问"运行时数据都存在哪、是否按存档隔离"。逐层查下来：**隔离机制本身是对的**（`world_id`
= 玩家 unitID → `worlds/<id>/`，会话/群流水/通讯录/人名映射表全在里面），但它挂在**一个只活在
Python 进程内存里的变量**上，而"补发身份"原先**只有** `save_happened` / `load_happened`
两条事件。于是 Python 一重启（配置面板保存触发的重启 / BrainLink 崩溃拉起 / mod 在已进世界时
才被启用），`world_id` 为空 → 那段时间的读写**全落扁平目录** `~/.sessions/`（不属于任何存档）：

| # | 后果 | 严重度 |
|---|---|---|
| ① | 开窗读到的是扁平目录那份 ⇒ **看不见本存档的历史** | 中（像"失忆"） |
| ② | 下一次存档：`_apply_world` 先切到真存档、再 `flush_all`，而 `save_session` 是**全量重写** ⇒ 从扁平目录读来的**短账本整份覆盖**真存档的账本 | **高：静默丢记忆** |
| ③ | 这期间加的好友/建的群写进扁平 `contacts.json` / `rooms/`，切档后看不见 | 中 |

**实机已经发生过一次**（不是假想）：`agent_loop.log.2026-09-15` 里游戏 PID `23224` 起了**两次**
Python（`02:10:38` 与 `02:13:13`，同一个游戏进程，中途重启），第二次**没有** `shutdown 已受理`
那行 ⇒ 非优雅死亡（崩溃/被杀 → BrainLink 拉起）。当时 `02:11:33` 姜萌的对话窗还开着，之后到
`02:18:43` 关游戏为止一条消息都没发 —— **只差一条消息就踩上**。扁平根至今干净
（只有 `_legacy_flat_backup_0912/` 与 `worlds/`，没有散落的 `<npc>.jsonl`）也印证了这点。

复现（真实代码路径，`/tmp/verify_world_restart.py` 的一次性脚本）：

```
① 存档A固化后 worlds/A 账本 = ['第一段：我们在存档A里说过的话']
② 重启后 world_id = None ｜sessions_root = /tmp/agent_loop_verify_world_restart
③ 开窗读到的历史条数 = 0        ← 读的是扁平根
④ 存档后 worlds/A 账本 = ['第二段：重启后、下次存档前说的话']   ← ★ 第一段被覆盖掉了
⑤ 重启窗口内加好友 → 写到 contacts.json（扁平）→ 切回存档A后 list_contacts = []
```

#### 为什么不把 `world_id` 落盘（先否掉最直觉的那个修法）

存一个"上次的存档身份"在磁盘上，等于在**读档之前**就先信了一个可能过期的身份：玩家重启游戏
换了个档，Python 起来时拿旧身份去切命名空间 ⇒ **写进另一个存档的目录**（比扁平目录更糟：
那是精确地污染一个真存档）。所以正确方向是"**让知道真相的那一方（C#）每次连接都重新声明**"，
而不是"让 Python 记住"。

#### 修复：C# 连接即声明 + 队列不丢帧，Python 三道闸门

**C# 侧**（`ModMain`）：

* `OnWsReconnected` 补发 `world_hello`（新帧）：**只切命名空间、不丢弃、不固化** ——
  重连时 Python 可能还活着、手里正握着玩家刚聊完还没存档的内容，补身份不该把它抹掉
  （这是它与 `load_happened` 的语义分界；用后者补发会凭空吞掉增量）。
  未进世界（主菜单）时 `FillWorldIdentity` 自然不写 `world_id` → Python 沿用现状 + INFO。
* `save_happened` / `load_happened` 不再裸调 `WsClient.SendRequest`：那条路**未连接时直接回
  `ok:false` 且不排队**，而回调是 `_ => { }` 却照样打印"已发送" ⇒ 帧被静默吞掉
  （实机日志里连接与 `load_happened` 相隔 7~45s，窗口真实存在）。现在统一走
  `WorldFrameOutbox`：未连接排队、连上按**原顺序**补投一次、积压超限丢**最旧**的
  （陈旧身份比丢帧更糟：拿它切命名空间 = 指到别的存档）。
  队列规则被**切出 Unity 代码**成零依赖纯逻辑（`csharp/WorldFrameOutbox.cs` + 单测工程
  `csharp/tests/WorldFrameOutboxTests/`，26 断言）—— 理由与 `UnitIdRegistryCore` 同：
  这层出错没有界面、没有异常，只有单测钉得住。

**Python 侧**（`ws_channel` / `agent_loop` / `contacts_store`）：

* `world_hello`：切命名空间 + 补载群名录（重启后内存名录是空的，它原先只在 `load_happened`
  里载入过一次）；**身份真的变了才** `discard_all`（内存里那些活体属于另一个存档：
  写进新目录会覆盖新档账本，留着又是别人家的账本）。
* `save_happened`：身份**变了**时**先丢弃再固化**（顺序反了就是上面那条静默覆盖）。
* `flush_all`：新增**账本出处对账** —— 每个 agent 记着"发布它时的 world_id"，出处与当前
  命名空间不符一律跳过并 WARNING（纵深防御：即使将来有人绕过 handler 直接 `set_world`，
  也覆盖不了）。
* `require_world`（**生产形态闸门**）：由 `AGENT_LOOP_PPID`（与父进程看门狗同源）判定"这次是
  游戏拉起的"，未定档时**不读扁平目录**（`create` 不从那里恢复账本）、**不写**（`flush_all`
  早退、删群不落盘）、通讯录**读写都拒**（写侧抛错 → RPC 转 `ok:false`，可恢复）。
  测试 / `chat_cli` / 手跑 `server.py` 保持扁平布局的原有语义（那条链路全依赖它）。

#### 设计取舍（明确认下的）

* **未定档窗口里的对话会丢**（不落盘、不串档）：宁可丢这一段增量，也不许污染某个存档 ——
  与"不存档就退游戏 = 增量作废"同一条既有语义。
* **`world_hello` 换档时丢弃活体**：与读档同语义。它们的账本出自另一个命名空间，
  合并/重贴标签都会把别人的内容写进本档。
* **同一存档的"回滚"仍不隔离**（已知限制）：命名空间键只有 `world_id`，而游戏自带的
  `CacheData备份的存档\<时间>---1_Fr17CF` 是**同一世界**的旧快照，回滚后 id 不变 ⇒
  NPC 会记得"未来"的对话。要做需要拿到存档槽位/快照标识，当前事件载荷里没有。
