## 三、★最重要的对照：为什么"一个气运时成功，三个气运就失败"★

### 三次关键配置逐项对照

| 项 | **E08（1 人成功）** | **E09/E11（3 人成功）** | **现在（0 人失败）** |
|---|---|---|---|
| 日期 | 10-18 20:15 | 10-18 23:2x | 10-19 |
| `DungeonTrigger.condition` | `npcConditionExamine_MID&003` + 7×`featureNot` | 同左 | **同左（未变）** |
| `NpcCondition.condition1` | `feature_1_MID&51` | `feature_1_MID&51` | `feature_1_MID&51` |
| `condition2` | `0`（单段） | **`feature_1_MID&51`（相同）** | **`feature_1_MID&55`（不同）** |
| `condition3` | `0` | **`feature_1_MID&51`（相同）** | **`feature_1_MID&56`（不同）** |
| 段数 | 1 | 3（**三段完全相同**） | 3（**三段全不同**） |
| `save` / `group` / `ABC` / `probability` | 0 / 0 / 0 / 0 | 同左 | **同左（全部未变）** |
| 结果 | ✅ 1 人 | ✅ 3 人（可能重复） | ❌ **0 人** |

### 结论（确定）

1. **`npcConditionExamine_<id>` 能用** —— 三次成功全用它，有 `npcUnits Count=1/3` 日志实证。
   （虽然官方 `DungeonTrigger` 386 行里用它 0 次，但它确实工作过。）
2. **`feature_1_X` 能命中** —— E11 日志：`[①npcUnits] Count=3` 里的人和 `[②气运持有者]` 名单吻合。
3. **唯一变了的配置 = 三段从「相同」改成「全不同」。**
4. **官方 427 行 `NpcCondition` 里「三段全不同」的行数 = 0**
   （354 单段 / 4 两段同 / 16 两段不同 / 49 三段有重复 / **0 三段全不同**）

⇒ **当前最大嫌疑：我们踩进了一个官方从没用过的结构。**

### 为什么当初要改成"三段不同"

E11 发现：三段相同 ⇒ 每段从同一池子**独立随机抽 1 个** ⇒ **有放回** ⇒ 可能抽到重复的人
（实测 `[0]方成和 [1]温芸 [2]方成和`，同一个人出现两次）。
修法 = "一槽一枚专属气运，每段候选集恰好 1 人" ⇒ 结构上不可能重复。
**思路正确，但可能触发了引擎的另一条限制。**

## 四、两个候选失效机制（待定案）

### 机制 A：条件段是"级联过滤"而非"独立并集"
若 c2 在 c1 的**结果集**上再过滤：
- 三段相同：c1 选出池子，c2/c3 在同一池子再筛 ⇒ 都能出人 ✅
- 三段不同：c1 筛出"挂 51 的人" ⇒ c2 要在**这批人里**找"挂 55 的人" ⇒ 空 ⇒ c3 更空 ❌

### 机制 B：只有第 1 段能拿到 `unitB` 上下文
`feature_1_X` → `GetUnitInType(1)` → `UnitConditionData.unitB`。
若 `ABC=0` 时只有 c1 的 `unitB` 被赋值，c2/c3 拿不到 ⇒ 恒 false。

**两个机制都指向同一修法方向，但证据未闭合。**

## 十一、下一步（给下一个 AI 的唯一任务）

### P0：定案"三段全不同"为什么失败

**核心问题**：
> `GetUnitsInID`@0x185991CB0 里，`condition2`/`condition3` 段求值时，
> `UnitConditionData.unitB`（+0x18）有没有被赋成"当前候选单位"？
> 还是只有 `condition1` 段会赋？

**为什么这是唯一问题**：
- 若"只有 c1 赋 unitB" ⇒ 三段异气运必然失败，三段相同却可能成功 ⇒ **完美解释 E11 成功、现在失败**
- 若"三段都赋" ⇒ 那问题在别处，需要换方向

**怎么查**：
1. raw 反汇编 `GetUnitsInID`@0x185991CB0 的**条件段循环体**（3200B 里找 `SelectObservable` 调用 + 订阅回调 `b__8`@0x182BDD340）
2. 标出所有写 `UnitConditionData +0x18` 的指令
3. 确认它是"每段独立赋"还是"只在某段赋"
4. 顺带查 `UnitConditionData` 实例**从哪来**（`object_new` 点）—— 它不是 `GetUnits` 的 `data` 参数

### P1：若 P0 证实，给修法

**方向 1（最小改动，回到成功配置）**：三段改回**相同**
```

```
但这样会重现 E11 的"有放回随机重复"问题。**补救**：靠 C# 侧 `PurgeSlotExcept` 收敛，

**方向 2（结构防重 + 单段）**：单段 + `save=1`

save = 1
DungeonTrigger.condition 加 npcConditionSave_MID&003_1

但这只出 1 人。

**方向 3（照抄官方 133/134）**：

DungeonTrigger.condition: npcConditionExamine_MID&003 → npcConditionSave_MID&003_1

官方唯一用 `addBattleNPCData` 的两行就是这个配置。但它们的条件组是 `abGrade/abClose/abSchool/abRelation`，

   > **10-19 晚补充**：覆盖 ≠ 丢弃。覆盖前必须先归档上一局到 `logs/runs/<时间>/`（见第二十节）。
   > 用户原话："日志现在是覆盖的，我需要备份，每次都要备份"。两条规则同时成立。
3. **不确定的必须去反编译查**，不许猜。
   > 用户原话："不确定的你去反编译代码去读啊，还有就是有之前反编译代码的文档啊"
4. **需要查代码的丢给子代理**，且要求**详细返回**（不是摘要），方便自己复核。
   > 用户原话："让子代理查清楚告诉你（告诉你的不应该是简要的见轮，而是应该是详细的内容，方便你自己直接根据子代理的结果去复核）"
5. 子代理**用主模型**：`provider=codebuddy-hub, model=codebuddy-intl-deepseek-v4.1-flash`
6. 配置表改动后**必须让用户在 MOD 编辑器导出**才生效。
