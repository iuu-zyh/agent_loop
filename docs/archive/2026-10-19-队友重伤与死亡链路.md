> ⚠ **已归档**。现状见 [`docs/features/team.md`](../features/team.md)。本文只保留当时的排查过程与被推翻的中间结论，**追溯「这个结论怎么来的」时才需要读**。
>
> **结局**：战场 HP 归零 ≠ 世界死亡；重伤走 5011/6009 链路。§六 이후的实测方案与 21:32 真机日志保留原文（1 号位冲突那节已定案）。
>
- **起止**：2026-10-19
- **触发**：队友在副本里 HP 归零后，到底该死还是该重伤
- **涉及**：`csharp/tools/Team*.cs`

## 一、结论先行

1. **副本里队友 HP 归零 = 战场克隆体 `UnitCtrlBase` 死亡**，不是世界 NPC `WorldUnitBase` 死亡。
2. `WorldUnitBase.Die()` 是另一条链（真死/剧情处决）；普通副本战斗**不会**调用它。
3. 游戏原生有「重伤」气运（ID **5011**，6 个月，体力上限 -30%），但它由**剧情/选项/战斗结算脚本/搬运动作**显式挂上，
   **不是**“副本 HP 归零就自动重伤”。

> **10-19 追加纠正**：野外“攻击 NPC”打赢后，NPC 确实会带重伤。
> 那是 `WorldBattleMgr.BattleEnd` 执行 `ConfDungeonBaseItem.winFunction` / 战斗剧情脚本的路径
> （原生 `DramaDialogue` 里能看到 `addNPCLuck_1_5011`、`addFeature_5011`）；
> 副本里队友的**战场克隆体**死亡走的是 `UnitCtrlBase.Die`，不在这条结算脚本里。
> 所以“野外有、副本队友没有”并不矛盾，但**不能再说“游戏不会给重伤”**。
4. 组队 mod 的「内外重伤」是它自己用 **`BattleEffect 6009` 死亡回调 → 剧情 → `addNPCLuck`** 做出来的；
   我们的配置已复刻同一条链。
5. **未证实的关键点**：`unitAddEffect_MID&003_MID&001` 到底有没有把 6009 挂到队友身上。
   `BattleFunction.UnitAddEffect → BattleFunction.GetUnit → ConfNpcCondition.GetUnits`；
   探针直接调 `GetUnits(int,null)` 是 0 人。若触发器路径也是 0，则 6009 从未挂上，
   队友倒下也不会触发重伤剧情。必须做一次“队友真的倒下”的实测。

## 二、战场 HP 归零：实际发生了什么

### 1. 战场单位 `UnitCtrlBase`

字段（`F:\_dt_dump\types\UnitCtrlBase.txt`）：

```text
0x10  mIsDie
0x18  onDieCall
0x20  onDieCallPar
0x60  UnitDataBase data
```

`UnitCtrlBase.Die()`（`0x2CB1DB0`）：

```text
mIsDie = true
→ 调用 onDieCall
→ Emit(EBattleTypeData.UnitDie)
→ 死亡动画 / 特效
→ BattleUnitMgr 把它从 GetAllUnit() 移除
```

`BattleUnitMgr`（`F:\_dt_dump\types\BattleUnitMgr.txt`）：

```text
GetAllUnit()             → 活着的战场单位
GetAllUnitIncludeDie()   → 含尸体
OnUnitDie / RemoveUnit   → 从活动列表移除
```

### 2. 战场单位的 HP 在哪

`UnitDataBase`（`F:\_dt_dump\types\UnitDataBase.txt`）：

```text
int hp
DynInt maxHP
```

`UnitDataHuman`（`F:\_dt_dump\types\UnitDataHuman.txt`）多一个：

```text
WorldUnitData worldUnitData
```

所以：

```text
UnitCtrlHuman.data.worldUnitData.unitData.unitID
```

可以映射回世界 NPC。`UnitCtrlBase.isDie` + `UnitDataBase.hp` 就能判断“这个战场单位倒没倒”。

### 3. `WorldUnitBase` 没有被杀

`UnitCtrlHuman.Die()`（`0x2CB6860`）：

```text
→ UnitCtrlBase.Die()
→ BattleEffectMgr.Create(...)   // 死亡表现/效果
```

**没有** `WorldUnitBase.Die()`。

普通副本战斗结束后 `BattleExit` 回大地图，世界 NPC 仍在，HP 仍是世界属性，
和战场克隆体的 HP 不是同一个。

## 三、世界 NPC 真死：`WorldUnitBase.Die()`

`WorldUnitBase.Die()`（`0x32BBED0`）才做：

```text
_isDie = true                         // [this+0x78]
→ Emit(WorldUnitDieFront)
→ 调 WorldUnitBase.onDieCall         // [this+0x80]
→ DataUnitDie.UnitDie.AddUnitDie(this) // 记入死亡档案
→ UnitActionSchoolExit / 退宗门
→ LogMgr.LogPoint
→ Emit(WorldUnitDie)
```

只有 `isRealBattle`、剧情处决、特定真死战斗才会走到这里。
**副本里队友被击倒 ≠ 世界 NPC 死亡。**

官方 `RoleCreateFeature.json`：

```text
DramaOptions 6100671:
```

⇒ **原生重伤是“剧情/选项/搬运动作显式挂上”的 6 个月 debuff**，
不是“副本 HP 归零”自动产生的。

## 五、组队 mod / 我们的「内外重伤」链路

### 1. 参考组队 mod 的链路（反推自其配置）

```text
DungeonTrigger（triggerType=14，每 1000ms）
  └─ unitAddEffect_<队伍条件组>_<BattleEffect>
       └─ BattleEffect typeID = 6009
            “自身死亡时打开剧情对话”
            value1 = 重伤剧情 ID
              └─ DramaDialogue.openFunction = addNPCLuck_1_<重伤气运>
```

### 2. `Effect6009` 反汇编（`0x3522B80`）

`EffectBase` 字段：

```text
0x10  EffectDataBase data
0x18  UnitCtrlBase unit
0x20  UnitCtrlBase unitEffectSource
```

`Effect6009.Create()`：

```text
EffectBase.Create()
r14 = this.unit                         // UnitCtrlBase
rdi = [r14 + 0x18]                      // UnitCtrlBase.onDieCall
Delegate.Combine(rdi, Effect6009.<Create>b__0_0)
[r14 + 0x18] = 组合后的委托
```

死亡回调 lambda：

```text
检查战斗数据某标志
→ 条件满足时打开剧情（value1 = DramaDialogue ID）
```

⇒ 6009 = **战场单位死亡时打开剧情**，剧情里再 `addNPCLuck` 挂重伤。

### 3. 我们的配置（已复刻）

| 表 | 行 | 内容 |
|---|---|---|
| `RoleCreateFeature` | `MID&52` | 内外重伤，`duration=4`，`level=-6`，effect=`MID&001~004` |
| `RoleEffect` | `MID&001~004` | `hpMax/mpMax/atk/def` 各 `-30` |
| `BattleEffect` | `MID&001` | `typeID=6009`，`value1=MID&190`，`targetID=1001` |
| `DramaDialogue` | `MID&190` | `openFunction=addNPCLuck_1_MID&52` |
| `DungeonTrigger` | `MID&002` | `triggerType=14`、`triggerValue=1000`、condition=`isBattleData_alTeamIn_ok`、bf=`unitAddEffect_3_MID&001\|unitAddEffect_4_MID&001\|unitAddEffect_5_MID&001`（10-19 改：按战斗位直挂，不走条件组） |

> 注：`BattleEffect MID&001` 的工程注释写“剧情 MID&002（重伤）”，实际 `value1=MID&190`；
> 以字段值为准，注释是笔误。

## 六、已证实 / 未证实

### 已证实

- 战场 HP 归零只死 `UnitCtrlBase`，不自动杀 `WorldUnitBase`；
- `Effect6009` 确实注册在 `UnitCtrlBase.onDieCall` 上，死亡时会打开剧情；
- 20:21 两人局 `battleCustomData` 出现：

```text
BattleTriggerBase_Trigger-803158449 = 1
```

说明「挂重伤」触发器 `MID&002` **执行过**。

### 未证实（关键）

> `unitAddEffect_MID&003_MID&001` 到底有没有把 6009 挂到队友身上？

证据链：

```text
BattleFunction.UnitAddEffect (0x290AC40)
  → BattleFunction.GetUnit (0x29055A0)
      → ConfNpcCondition.GetUnits (0x1859938C0)
```

探针直接调 `GetUnits(int, null)`：

```text
[③引擎GetUnits] key=-803158448 ⇒ Count=0
```

如果触发器路径也拿到 0 人，`unitAddEffect` 就没有目标，6009 不会注册，
队友倒下也不会触发剧情。触发器的 `=1` 只证明“触发器跑了”，不证明“效果挂上了”。

### 10-19 根因定案（`BattleFunction.GetUnit`）

`BattleFunction.GetUnit` 对参数分两条路：

```text
"3" / "4" / "5"（纯数字）  → 战斗单位索引分支
"MID&003"（含 &）          → ConfNpcCondition.GetUnits(条件组)
```

`MID&003` 含 `&` ⇒ 走条件组 ⇒ 探针实测 0 人 ⇒ `unitAddEffect` 没有目标。
**修法**：`DungeonTrigger MID&002` 改成

```text
unitAddEffect_3_MID&001|unitAddEffect_4_MID&001|unitAddEffect_5_MID&001
```

直接按战斗单位 3/4/5 挂 6009，绕开条件组。

### 已加的 C# 兜底（10-19）

即使 6009 仍没挂上，`TeamBattleFollowup` 也会：

1. `BattleEndFront` 读 `SceneBattle.unit.GetAllUnitIncludeDie()`；
2. 对每个 `UnitCtrlBase.isDie`，用
   `UnitCtrlHuman.data.worldUnitData.unitData.unitID` 映射回队友；
3. `BattleExit` 若该队友没有「内外重伤」，直接 `TeamTool.AddLuck(m, hurtId)`；
4. 然后 `RemoveAllSlotLucks` + `SyncTeamState(0)` 自动离队；
5. 重伤者经历用 `eventLogTeamDungeonHurt`。

### 仍需实测

1. `Player.log` 是否出现 `重伤快照：战场单位 … 倒下 …`；
2. 队友身上是否出现「内外重伤」4 个月；
3. 世界 NPC 是否仍存活；
4. 重伤后是否自动离队、再邀请是否被拒；
5. 经历是否显示「战斗中身负重伤」。

## 七、三个需求的实现（10-19 已落码）

### 1. 自动离队

`TeamBattleFollowup`：

- `OnBattleEndFront` 先按 `npcUnits` 找队友，再用 `TeamTool.Members()` 补全
  （倒下的队友可能已不在容器里）；
- `SnapshotDeadMates()`：`SceneType.battle.unit.GetAllUnitIncludeDie()` →
  `UnitCtrlBase.isDie` → `UnitCtrlHuman.data.worldUnitData.unitData.unitID`；
- `OnBattleExit` → `ApplyHurtAndLeave()`：
  - 若没有「内外重伤」→ `TeamTool.AddLuck(m, hurtId)` 兜底；
  - `TeamTool.RemoveAllSlotLucks(m, out err)`；
  - `TeamTool.SyncTeamState(0)`。

### 2. 重伤期间不能入队

- `TeamTool.Invite` 在选槽前判：

```text
HurtLuckId() != 0 && HasLuck(mate, hurtId)
  → Fail「…身负重伤（剩约 N 个月），需静养，暂时无法入队」
```

- `ToolExecutor` 的 `invite` 确认窗前也做同一判，避免弹窗后才失败。

### 3. 重伤 NPC 的经历不同

- `RoleLogLocal.xlsx` 新增 `MID&2 / eventLogTeamDungeonHurt`：

```text
ch = 与{0}同闯秘境，战斗中身负重伤。
```

- `TeamBattleFollowup.WriteJourneyLogs` 对 `_hurtIds` 里的队友改用该 key；
- 普通队友仍用 `eventLogTeamDungeon`。

### 4. 同时修掉的配置问题

`DungeonTrigger MID&002` 改为按战斗单位直挂：

```text
unitAddEffect_3_MID&001|unitAddEffect_4_MID&001|unitAddEffect_5_MID&001
```

原因见第六节：`MID&003` 含 `&`，`GetUnit` 会走 `ConfNpcCondition.GetUnits`，
探针实测 0 人；纯数字 3/4/5 走战斗单位索引分支，才能把 6009 挂到队友身上。

> `TeamBattleFollowup` 现在从 `TeamTool.Members()` 补全全队，不再只依赖
> `npcUnits` —— 倒下的队友也能被传送/写经历/自动离队。

## 九、21:32 真机日志：三个问题（待修）

### 1. `lowhp` 没生效 → 本轮没有制造出死亡

```text
[TeamMulti] [lowhp] ⚠ 拿不到 SceneBattle（SceneType.battle）—— 本次没测到，不是没执行
[TeamFollowup] 重伤快照：战场单位 9 个，倒下 0 个
```

**结论：不是重伤逻辑失败，而是测试开关没把 HP 改成 1。**
没人倒下，`ApplyHurtAndLeave()` 正确地什么都没做。

关键矛盾：`lowhp` 在第一次 `dumpbattle` 时拿不到 `SceneBattle`，
但 `TeamFollowup` 在更晚的 `BattleEndFront` 拿到了 9 个战场单位。

**先纠正文档里的一个错误**：`ForceLowHp` 并不是“失败后不再重试”——

- `_lowHpLogged` 只控制**日志**，不会阻止下一次 `DoDumpBattle` 再次调用；
- 日志里只有一次 `⚠ 拿不到 SceneBattle`，且没有后续 `已重设 HP=1`，
  说明**整场战斗的探针侧 `FindSceneBattle()` 都拿不到场景**，
  不是“第一次失败就放弃”。

**修法（21:46 已实施）**：

- 确认反编译 `SceneType.battle` 是静态属性，getter 内部走 `SceneMgr.GetScene`；
- 探针版去掉 `GetGetMethod(true).IsStatic` 前置判断，改为无条件
  `p.GetValue(null)`，抛异常再退回 `SceneType.Battle` 静态字段；
- `ForceLowHp` 失败计数每 5 次打一条日志，不再只打第一条；
- 若仍然拿不到，下一步把 `lowhp` 挪到 `TeamFollowup` 同一条访问路径。

**21:?? 追加（真机仍失败）**：日志仍只有
`[lowhp] 第 1 次拿不到 SceneBattle`，说明整场探针路径都拿不到场景。

### 2. 经历重复：4 名队友 / 张票出现两次

```text
[①npcUnits] Count=2 → 张票、方成和
[TeamFollowup] 本场有 4 名队友参战：张票、方成和、张票、方成和
[TeamFollowup] 写经历 → 唐炎：与「张票」「方成和」「张票」「方成和」同闯秘境…
```

根因：`TeamBattleFollowup.OnBattleEndFront` 用 `TeamTool.Members()` 补全 `_mates` 时，
判重用的是**引用相等** `ReferenceEquals`。IL2CPP 桥接可能给同一个 `unitID`
新建包装对象 ⇒ 同一个人被再次加入。

**修法（21:46 已实施）**：`_mates` 的 `seenIds` 跨“npcUnits 扫描 + Members 补全”共用；
`MarkHurt` 也按 `unitID` 去重；`TeamContainerInject` 同样加 unitID 去重。

### 3. 特殊救助剧情：**已定位为战斗位 3 冲突**（P0）

官方配置直接给出了答案：

```text
DungeonSpecialRoom31 1000001:
  npcConditionID = 300001
  npcPosi        = 11_5
  battleFunction = unitAnim_3_Die_1
                 | addAttribute_3_6_0_100_1
                 | addAttribute_3_6_0_-60_1
                 | setBattleData_interact_0
                 | setBattleData_NPC_300001

DungeonTrigger 133:
  addBattleNPCData_300001_0
  | setDramaUnitData_300001_2
  | addBattleUnit_300001_1_0_2_1_1_982301
```

`DungeonSpecialRoom31` 用 `unitAnim_3_Die_1` 把**战斗位 3** 设成“倒地”，
再用 `addAttribute_3_...` 改战斗位 3 的属性——它默认战斗位 3 就是救助 NPC。

而我们的 `DungeonTrigger MID&001` 是：

```text
addBattleNPCData_MID&003_0/1/2
addBattleUnit_3_...   ← 第 1 个队友占用战斗位 3
addBattleUnit_4_...   ← 第 2 个队友占用战斗位 4
addBattleUnit_5_...   ← 第 3 个队友占用战斗位 5
```

同时 `TeamContainerInject.Prefix` 是**无参拦截**：所有
`addBattleNPCData` 都拦，第一次 `nu.Clear()` 后按队伍写入，
后续一律 `return false`。它无法区分：

- 我们的队伍条件组 `MID&003`；
- 救助剧情条件组 `300001`。

于是两个结果同时发生：

1. 救助 NPC 的 `addBattleNPCData_300001` 被清掉/跳过，或没有按剧情落到战斗位 3；
2. 我们的第一个队友占了战斗位 3，`unitAnim_3_Die_1` 和
   `addAttribute_3_...` 全打到**第一个队友**身上。

这正好解释现象：

- 救助 NPC 没被 `unitAnim_3_Die` 置成倒地 ⇒ **站着，还能战斗**；
- 第一个队友被 `unitAnim_3_Die` 置成倒地动画 ⇒ **腿直、身子贴地**。

> 之前文档里“可能是 `addBattleNPCData` 跳过剧情 NPC”只说对了一半；
> 真正致命的是**战斗位 3 被队友占用**。只加 `noinject=1` 也不够：
> 它只阻止容器 Clear，`addBattleUnit_3/4/5` 仍会占位。

**修法方向**：

1. `addBattleNPCData` 只拦截确认的队伍条件组 `MID&003`，不要拦 `300001`；
2. 救助战斗（`battleCustomData` 含 `rescue=1` / `NPC=300001`）里，

#### 3.1 两种“号位”不要混

队伍界面的“1/2/3 号位”是**气运槽位**；`unitAnim_3` / `addAttribute_3` 里的 `3`
是**战斗位编号**。两者不是一回事：

| 队伍气运槽位 | `npcUnits` 下标 | 配置命令 | 战斗位 |
|---|---|---|---|
| 1 号位（第一个队友） | `[0]` | `addBattleUnit_3` | 3 |
| 2 号位（第二个队友） | `[1]` | `addBattleUnit_4` | 4 |
| 3 号位（第三个队友） | `[2]` | `addBattleUnit_5` | 5 |

反编译 `BattleFunction.GetUnitWorld`：

```text
id 3..10 → CommonTool.Index(npcUnits, id - 3)
```

所以 `addBattleUnit_3` 取的是 `npcUnits[0]`，即**队伍 1 号位**，不是队伍 3 号位。
`unitAnim_3_Die_1` 打到的是第一个队友，不是第三个。

#### 3.2 方案 B（队伍改 4/5/6）的可行性

理论可行，但不是“改个数字就确定正常”。必须同时满足：

1. `npcUnits[0]` = 救助 NPC，`npcUnits[1..]` = 队友；
2. 救助 NPC 先通过 `addBattleNPCData_300001` 进入容器；
3. 队伍随后插入，不能先 `Clear()`；
4. 触发器在救助战斗里改用 `addBattleUnit_4/5/6`；
5. 官方 `addBattleUnit_300001` 先执行且确实落在战斗位 3；
6. `addBattleUnit_6` 实测能生成第 4 个容器成员（反编译支持 3..10，但原版无多人先例）；
7. 其他特殊副本不占用 4/5/6。

### 11.3 `addNPCLuck_1_xxx` 命中谁

```text
DramaFunction.AddNPCLuck(string[] values)  @0x223E270
  values[0] = 目标类型（Int32::Parse）
  target = GetUnitInType(values[0])                     // 0x182253a90
```

### 11.4 为什么 `unitRight` 会是玩家

`DramaFunctionData.get_dramaData` @0x4634AC0（`_data.dramaData`）在
`[fnData+0x70]==null` 时**新建一个 `DramaData`**，然后把
`fnData.unitLeft(+0x18)` → `dramaData.unitLeft`、
`fnData.unitRight(+0x20)` → `dramaData.unitRight` **反写回去**。

而 `DramaFunctionData.ctor()`（无参，@0x46346F0）**不填 +0x18/+0x20**；
`DramaFunctionData.ctor(WorldUnitBase u)` @0x46348E0 也**只填 +0x10**（`unitA`）。

⇒ 程序化 `OptionsFunction(openFunction, functionData)` 时，
**`unitLeft/unitRight` 保持 null**（除非调用方显式 set）。
`unitRight==null` ⇒ `addNPCLuck_1` 空转 ⇒ **重伤永远挂不上**。

### 11.5 那“立绘是玩家”是怎么来的

`Effect6009.Create` @0x3522B80 → `b__0_0` @0x3522C60：
死亡回调里取 `g.world`（0x18384E6C0 = `WorldMgr` 访问器）→ `[world+0x68]` → `[+0x10]`，
判 `isDie`，再取 `[rbx+0x10]`（`EffectBase.unit`）→ `0x1840C9370`（`EffectDataBase` 取 unit）
→ `0x18463F1F0` = **`DramaTool.OpenDrama(string, DramaData)`**。

`DramaTool.OpenDrama(string)` @0x463F1F0 最后调
`OpenDramaInID(int, DramaData)` @0x463EB80（0x18463F5C1 处）。
`OpenDramaInID` 里 `[rdi+0x10]`（`DramaData`）**为 null 就 new 一个空 `DramaData`**
（0x18463EF42–0x18463EF6D），**不会**替我们填 `unitLeft/unitRight`。

⇒ 6009 走的是**空 `DramaData`**，`unitLeft/unitRight` 全 null。
于是 `npcLeft=1 / npcRight=11` 这两列**只在静态表路径生效**，
而 6009 是**运行时程序化打开**，它带的是自己 new 的空 data。
`id==11` 取 `dramaData.unitLeft` → null；`id==0` 退回 `dramaData.unit` → 也 null。
**最终两侧都拿不到人，UI 回落到“本页无立绘”的默认槽位（玩家形象）。**

### 11.6 结论（可执行）

| 现象 | 真因 | 修法 |
|---|---|---|
| 190 立绘是玩家 | 6009 程序化打开带的是**空 DramaData**，`unitLeft/unitRight` 都是 null；`id==1` 分支画玩家 | 在 `UIDramaBase.InitData` 前缀里**显式写入** `unitLeft/unitRight/unit` = 倒下的队友 |
| 队友没有重伤气运 | `addNPCLuck_1` 取 `DramaFunctionData.unitLeft` 为 null ⇒ `AddNPCLuck` 0x18223e35f 直接 return | 同上（`DramaData.set_unitLeft` 会**回填** `functionData.unitLeft`） |

**两个对象别搞混（上一版修错就在这里）**：

| 对象 | 字段 | 谁读 |
|---|---|---|
| `DramaData` | `unitLeft +0x10` / `unitRight +0x18` / `unit +0x10` | **UI 立绘** `UIDramaDialogue.UpdateUnit` |
| `DramaFunctionData` | `unitA +0x10` / `unitLeft +0x18` / `unitRight +0x20` | **`DramaFunction.AddNPCLuck` 挂气运** |

`GetUnitInType` @0x2253A90 的 `type→偏移` 是打在 **`DramaFunctionData`** 上的：
`0→+0x10 unitA`、`1→+0x18 unitLeft`、`2→+0x20 unitRight`。
`addNPCLuck_1_xxx` 的 `1` ⇒ `functionData.unitLeft`。

`DramaData.set_unitLeft/set_unitRight` @0x223AA90/0x223AB20 **单向回填** `functionData`
（仅当那边为 null）⇒ 先写 `DramaData` 两边都生效，这正是修法。

> **撤回两条旧结论**：
> ① §3.4「`npcRight=0` 是玩家/空位 ⇒ 挂给玩家」—— 6009 这条运行时路径**根本不读配表**。
> ② 「改 `npcRight=11` 修好了立绘」—— 22:34 那次是**手动触发**（走静态表），
>    不是 6009 触发的，不能当证据。
>
> 配表本身**是对的**：官方 `npcLeft=1`(玩家)+`npcRight=11`(对手) 有 4522 行，
> 我们照抄没错。错的只是**没给运行时 `DramaData` 填人**。

### 11.8 钩子为什么必须挂在 `UIDramaBase.InitData`

```text
UIDramaBase.InitData @0x32FA590
  1832fa8f1: lea r15,[r13+0xa8]     ; &this.dramaData
  1832fa8f8: mov [r15],rdi          ; this.dramaData = 传入的 data
  1832fa949: call 0x1832FA480       ; InitCondition(dramaData)
  1832fa960: mov rcx,[rcx+0x60]     ; item.openFunction
  1832fa964: call 0x184634BD0       ; OptionsFunctionDramaData(openFunction, dramaData)
```

`OptionsFunctionDramaData` 里 `r8 = [dramaData+0xE0]` = `dramaData.functionData`，
再调 `DramaFunction::OptionsFunction` ⇒ `AddNPCLuck`。
**所以 Prefix 阶段（`InitCondition` 之前）填好 `DramaData` 就能同时修好立绘与气运。**

### 11.9 钩子签名（Harmony 参数编号，别写错）

`InitData` 是**实例方法** `public virtual void InitData(int id, DramaData data)`：

```csharp
private static void DramaInitDataPrefix(object __instance, int __1, object __2)
// __0=__instance(UI)  __1=id(int)  __2=data(DramaData)
```

写成 `(int __0, object __1, object __2)` 会把 UI 对象当 id 比 ⇒ 永不相等 ⇒ **静默不生效**。
上一版 `死亡钩子=0` 是同类问题：`Die` 的签名是
`Die(bool isEffect = true, MartialTool.HitData hitData = null)`，不是无参。

## 十三、10-21 真机成功：根因是**找错了对象**

DLL `67536f660187fa8770bbdc81326de231`。上一版（`7f104923`）是中间态，本节记的才是定案。

### 13.1 一句话根因

> 所有死亡钩子拿到的 `data` 是 **`UnitDataBase`**（非人形基类），
> 而 `worldUnitData` 只存在于 **`UnitDataHuman`**（+0x238）。
> 在一个 `UnitDataBase` 上找 `worldUnitData`，**结构上永远找不到**。

之前的诊断（"`unitID` 读出来是空串"）是**结果不是原因**。两轮都栽在这上面。

### 13.2 证据链（00:20 日志）

```
[death] OnUnitDie 非队友：UnitDataBase name="竹妖" worldUnitData=null unitID="" isDie=False
[death] Die       非队友：UnitDataBase name="竹妖" worldUnitData=null unitID="" isDie=True
[death] 队友倒下（OnUnitDie）东方亦玉(vmBqoH)，已记录
[death] 队友倒下（OnUnitDie）唐乐咏(3X52i9)，已记录
```

两条关键结论：

1. **`name` 可读**（`竹妖`/`蛇`/`蜘蛛`）⇒ `UnitDataBase.name` 是公开字段，
   不经过 `worldUnitData`，这是唯一能覆盖非人形基类的识别路。
2. **队友的 `unitID` 反而是完整的**（`vmBqoH`/`3X52i9`）——他们走 `OnUnitDie` 正常。
   读不出信息的那一批（`name="竹妖"` 等）是**小怪**，本来就只是噪音。

> 教训：**先确认对象是什么类型，再决定去哪个字段取数据。**
> 反过来（先假定字段存在、然后怀疑是空值）会连错两轮。

### 13.3 最终分工（气运归表，代码只补两件事）

| 环节 | 谁负责 | 备注 |
|---|---|---|
| 剧情窗出现 | **表** | 190 行必须存在于 `DramaDialogue.json`，否则 `GetItem` 返回 null ⇒ 静默不开窗 |
| 正文 / 选项 / `openFunction` | **表** | |
| **挂「内外重伤」** | **表** | `addNPCLuck_1_MID&52` 原生能力，**代码已退为补漏** |
| 立绘显示谁 | 代码（只填一次槽） | 填 `DramaData.unitLeft`，`set_unitLeft` 会回填 `functionData.unitLeft` 供表读取 |
| 认谁倒下了 | 代码 | 表对"谁死了"完全不知情（两个不同队友倒下开的是**同一个** dramaId） |
| 摘号位让人离队 | 代码 | `addNPCLuck` 系列没有"摘除"指令 |

**真机兑现**：

```
重伤已在身（表挂）→ 东方亦玉，无需补挂
重伤已在身（表挂）→ 唐乐咏，无需补挂
重伤处理：表挂 2，代码补挂 0，离队 2，失败 0
```

`代码补挂 0` = 表干完了全部活，代码一次没插手。这是目标形态。

### 13.4 立绘：只填一侧

```
190 立绘修正 → 左=东方亦玉（右留空）（vmBqoH，死亡钩子 1 人）
190 立绘修正 → 左=唐乐咏（右留空）（3X52i9，死亡钩子 2 人）
```

两个**不同**的人，各开一次页，各只出一个人。上一版是两次都「左=申屠阳辉 右=申屠阳辉」。

两条规则：

- **只填 `unitLeft`，`unitRight` 显式置 null。** 配表 `npcLeft=1 / npcRight=11`，
  我们已把左位 id 1 改写成 11 ⇒ 左右**都**读 `unitLeft`，填一个两侧都出人。
  删掉「两侧都写同一人」是因为那会让**同一个人出现两次**（用户截图确认）。
- **绝对不要调 `DramaData.set_unit`**：它 @0x223AB70 会**同时**写 +0x10/+0x18，
  把刚清空的 `unitRight` 又填回去。

### 13.5 `PickHurtMate` 必须去重

旧实现兜底是「取本场第一个号位队友」，而死亡钩子恒空 ⇒ **两次 190 都返回同一人**。
这就是"两个队友倒下只显示第一个"的直接原因。

现在按「本轮尚未当过 190 主角」筛（`_usedAsDramaLead`），按场清零。
