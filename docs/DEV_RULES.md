> 文档分层见 [`README.md`](README.md)；测试细节见 [`../tests/README.md`](../tests/README.md)。

## 一、开发流程（每个功能都走这五步）

```
① 开工   →  docs/journal/YYYY-MM-DD-功能名/     新建子文件夹，边做边写
② 开发   →  只跑受影响测试；代码结构保持"各司其职"
③ 验证   →  需要实机的一律实机验证通过
④ 收尾   →  按 §十二 的清单逐项过（不许缺项）
⑤ 沉淀   →  有价值的结论升格进 docs/features/
```

### ① 开工：先建 journal 子文件夹

**每次开发都要**，不要等做完了再补写。路径 `docs/journal/2026-11-19-常驻帧回调句柄化/`。

里面至少一个 `README.md`，边做边记。开发过程中的详文（真机日志逐行解读、
走过的弯路、被推翻的假设、临时探针输出）都放这个文件夹。

为什么强制：本仓的问题**几乎全是静默的**——不崩、不报错、只是行为不对。
判断"这个结论靠不靠得住"，只能靠当时的现场记录。事后再补，细节已经丢了。

### ② 开发：各司其职

**核心原则：一个文件只干一件事，界面清晰。**

| 层 | 放什么 | 例子 |
|---|---|---|
| **判据核** | 纯逻辑，零 Unity 依赖，可单测 | `state/BusyWatchCore.cs` |
| **接线层** | 碰 Unity / 打日志 / 注册回调 | `state/BusyWatch.cs` |
| **单测** | net8.0 控制台工程 | `csharp/tests/BusyWatchCoreTests/` |

纯逻辑必须切出来单独一个文件。理由：这些规则错在真机上**全是静默的**，
只能靠单测钉住；而 IL2CPP 下跑不起 NUnit，所以用控制台工程 + 返回码。

**不要**在一个文件里混"判定"和"副作用"。混了之后，想验证判定就必须
把整个游戏环境搭起来 —— 那等于验证不了。

### ③ 验证：需要实机的必须实机

改完先自问：**这个行为能不能只靠单测证明？**

- 能（纯逻辑、协议解析、状态机）→ 单测覆盖即可
- 不能（碰 `g.world` / `g.ui` / 真实游戏循环）→ **必须实机验证**

实机验证过的功能才算完成。没验证就提交，等于把"不确定"留给下一个人。

### ④ 收尾

**见 §十二。那张表是强制的，不是建议。**

### ⑤ 沉淀：升格

`journal` 里的结论如果有长期价值（"这个功能现在怎么工作"），
写成 `docs/features/<功能>.md`。过程进 `docs/archive/`（命名见 §八）。

一个功能通常长这样：

```
journal/（过程，进行中） → archive/journal/（完工归档） → features/（现状）
```

## 二、测试规范

> 完整说明见 [`tests/README.md`](../tests/README.md)。这里只讲**什么时候跑什么**。

### 铁律：全量测试只在收尾时跑

```bash
python3 -m pytest tests/ -q                    # 约 2.8 分钟，2222 条 —— 收尾才跑
```

平时**只跑受影响的部分**：

```bash
python3 -m pytest tests/ -q -k "frame or tick or battle"     # 按关键字
python3 -m pytest tests/test_resident_tick_contract.py -q     # 单文件
python3 scripts/dev/run_tests_for.py --changed                # 按改动自动挑（推荐）
```

为什么：全量 2.8 分钟，而改一个文件通常只牵出 100~250 条（3~10 秒）。
迭代时等 2.8 分钟纯属浪费，而且会让你不愿意跑测试。

### 验证强度要匹配改动性质

| 改动性质 | 判据（自问） | 要求 |
|---|---|---|
| **探针 / 诊断代码** | 产出是"一条日志读数"还是"线上行为变化"？ | 编译 → 部署 → 上机取数。**不写契约、不跑全量** |
| **定案改逻辑** | 这行为以后必须一直成立吗？搞错了会静默出错吗？ | 契约测试 + 受影响子集（收尾时全量） |

给探针写契约测试是**浪费**——探针活一轮就删，下一个人上来第一件事就是删掉它。
真正要钉死的是**定案那一版**。

### 每条真机事故配一条契约测试

本仓库最贵的教训：**"注释说它被调用了"不等于它被调用了**。

凡是"某行注册/某处接线被删掉也不报错"的地方，都要有测试**按字面**断言它还在。

```python
# tests/test_xxx_contract.py
def test_resident_callback_is_registered():
    """光有调用不够 —— 它得真的被注册（09-20 事故：注释说被调用，实际从未注册）。"""
    assert re.search(r"FrameTicker\.Ensure\(...", MODMAIN_SRC)
```

写清楚**事故现场 + 后果**，不要只写"应该如此"。

### 断言要经过变异验证

写完断言不算完，要**证明它会红**：把实现删掉/改错，跑一遍，必须失败。

```bash
python3 scripts/dev/mutate_check_*.py      # 已有的变异脚本
```

没做过变异的断言是"可能空转的断言"——本仓出现过只查 `"FrameTicker" in src`
这种永远为真的形状。

### C# 测试

```bash
python3 scripts/dev/run_csharp_tests.py                        # 29 个项目，约 30 秒
python3 scripts/dev/run_csharp_tests.py --only FrameTickerCoreTests
```

## 三、测试快照（`scripts/dev/.depmap.json`）

`run_tests_for.py` 靠它挑子集。**新增/修改/删除文件后，快照会过期**。

| 情形 | 会不会漏跑 | 要做什么 |
|---|---|---|
| 新增源文件 | 不会（扫描规则兜住） | 无需处理 |
| 新增测试文件 | 不会（强制整文件跑） | 想加速就增量采一下 |
| 改了测试文件 | 不会（强制整文件跑） | 同上 |
| **删除/重命名源文件** | **靠快照反查** | **必须重采**，否则"改名了却全绿" |

```bash
python3 scripts/dev/run_tests_for.py --probe --probe-files tests/test_new.py   # 增量
python3 scripts/dev/run_tests_for.py --probe                                   # 全量重采
```

**收尾时如果动过文件结构（增删改名），一定要重采。**

## 四、构建与部署

### 编译

```bash
"/mnt/c/Program Files/dotnet/dotnet.exe" build csharp/AgentLoopBridge.csproj -c Release -v quiet
```

### 部署：产物必须拷到**三处**

```bash
SRC=csharp/bin/Release/MOD_Jgmg5L.dll
for dst in \
  "/mnt/e/SteamLibrary/steamapps/common/鬼谷八荒/ModExportData/Mod_Jgmg5L/ModCode/dll/MOD_Jgmg5L.dll" \
  "/mnt/f/mod/ModProject_Jgmg5L/ModProject/ModCode/dll/MOD_Jgmg5L.dll" \
  "/mnt/f/mod/ModProject_Jgmg5L/ModProject/ModCode/ModMain/bin/Release/MOD_Jgmg5L.dll" ; do
  cp -f "$SRC" "$dst"
done
```

| 位置 | 谁用 |
|---|---|
| 游戏目录 `ModCode/dll/` | 游戏运行时加载的那份 |
| 编辑器 `ModCode/dll/` | 编辑器导出时打包的那份 |
| 编辑器 `ModMain/bin/Release/` | 编辑器工程编译输出 |

**三处必须 md5 一致**，否则会出现"测试的是旧的、导出的是新的"。**记下 md5**，收尾要报告。

**改了 C# 必须重启游戏**——.NET 程序集载入后无法卸载。

### ★ 部署完就结束，不要再验证 ★（用户 11-21 明确要求）

部署命令跑完、md5 打出来、备份确认存在 —— **到此为止**。

**不要再做的事**（这些都在部署之后，一件都不做）：

- 解包 exe 的 PYZ 查 code object；
- `strings` / `grep` 查 DLL 里有没有新符号；
- 再跑一次 `deploy_runtime.py --check` 确认"已经一致"；
- 抽查部署后的文件时间戳 / 大小；
- 为"确认真的生效"再补一条一次性的核对命令。

**理由**（不是省事，是这几项确实没有信息量）：

1. **`deploy_runtime.py` 已经逐字节比对过 md5**，并在写入后回读校验。再查一遍是同一个
   判据算第二次 —— 它要么两次都对，要么两次都错，不会因为多查一次变准。
2. **"源和目标都还是旧代码"这种情形它挡得住**（§四「一个反直觉的坑」的第一半），
   因为 md5 不同会写、不同会报。当年那次误判不是"没验证 md5"，而是**把
   "旧参数被接受"当成了"新代码在跑"** —— 那个教训的正确落点是
   **改契约时要盯新字段**（已写在上面的引文里），不是"部署后再解包查一次"。
3. **真正能证明生效的，只有实机跑一次**。而实机验证是收尾清单第 4 条，
   本来就该做、且有专门的"没验证的"口径。部署后解包**替代不了**它，
   只会在报告里制造一层"我验过了"的错觉。

> **判据归位**：部署的判据是 `deploy_runtime.py` 的退出码 + md5 输出；
> 生效的判据是实机日志/行为。两者都不需要"部署后再查一遍文件"。

### Python 侧：改了源码**必须让它重新生效**，否则改了等于没改

**关键前提：游戏默认跑的不是源码，是 `ModAssets/AgentLoopServer.exe`**（自包含单文件）。
在**exe 形态**下，改完 `agent_loop/` 里任何 `.py` 而不重新打包，游戏里跑的还是旧代码 ——
而且症状极其误导：功能"没生效"但报错为零、日志正常、参数照旧被接受。

所以改完 Python **必须重新打包**。开发用 PyInstaller（16 秒），发布用 Nuitka。

#### 两档打包：**开发用 PyInstaller，发布用 Nuitka**

| 场景 | 用哪个 | 命令 | 耗时 |
|---|---|---|---|
| **开发 / 自测**（改 Python 后看效果） | **PyInstaller** | `--build-exe` | **约 16 秒** |
| **正式发布**（出包给玩家） | **Nuitka** | 见 §十 / `docs/release/PACKAGING.md` | 5~15 分钟 |

两档产物**同名、同位置、同启动契约**（`ModPaths` 只认文件名 `AgentLoopServer.exe`），
所以开发期用哪个对 C# 完全透明。

| | PyInstaller | Nuitka |
|---|---|---|
| 产物 | `.py` → `.pyc` → 自解压归档 | `.py` → C → 机器码 |
| 源码保护 | **防手滑级别**（`pyinstxtractor` 一条命令还原 `.pyc`） | 没有字节码可反 |
| 用途 | **仅开发自测** | **发行必须用它** |

> ⚠ **绝不能用 PyInstaller 产物出包**。它的保护强度只够"别让玩家随手看见源码"，
> 对有心人是明文的。发行档必须 Nuitka（理由与实测见 `docs/release/PACKAGING.md` §6）。

> ⚠ **禁止源码树模式**（`_dev_root.txt` 哨兵）。本项目**只以打包形式跑 Python**：
> 打包形态与发行形态一致，才不会出现"开发能跑、打包后跑不了"。
> 实测教训（11-21）：启用源码树后 Python **启动即退出**（`进程退出，flush 日志`
> 出现在 `WS 通道已监听` 之前），历史回放全部失效 —— 而打包形态一直正常。

#### 打包与部署命令

```bash
python3 scripts/pack_release.py --build-exe \
    --exe '/mnt/f/.agent_loop_build/pybuild/dist/AgentLoopServer.exe' --deploy
```

⚠ 必须 `--exe` 显式指向刚打的包（原因见下面"三个必踩的坑"第 ① 条）。

> **绝不能用 PyInstaller 产物出包**：它的保护是"防手滑"级别
> （`pyinstxtractor` 一条命令还原 `.pyc`），对有心人是明文的。
> 发行档必须 Nuitka（理由与实测见 `docs/release/PACKAGING.md` §6）。

#### 三个必踩的坑（都实测过）

**① `--deploy` 会用 `stage/` 里的旧 exe，不是刚打的包**

`--build-exe` 的产物在 `../.agent_loop_build/pybuild/dist/`，而 `--deploy` 默认从
`../.agent_loop_build/stage/` 取。两者**可能不是同一份**（实测差 3 天：dist 15.9MB / stage 19.0MB）。
**必须显式 `--exe` 指过去**，否则部署的是上一次的包。

**② exe 被占用时 `--deploy` 直接 `PermissionError`**

游戏进程退出**不会**杀 Python（`Launcher`：`python 已在运行，跳过拉起`，
Destroy 刻意不停进程，重进世界复用）。所以要先杀：

```bash
powershell.exe -NoProfile -Command "Stop-Process -Name AgentLoopServer -Force"
# 确认：Get-Process -Name AgentLoopServer  → 应当为空
```

⚠ onefile 形态在磁盘上是一个文件、运行时是**两个进程**（bootloader + 载荷副本），
`Stop-Process -Name` 按名字杀能一并清掉；按单个 PID 杀会漏。

**③ `[Build]` 那行只验证 **DLL**，不验证 exe**

§十一 第 1 条「确认跑的是新代码」用它判断 C# 是对的，但它对 Python **无效**。
Python 的判据只有两条：

- **看 exe 时间戳** vs 你改源码的时间；
- **看日志格式**：改了日志文案就对得上（最硬的证据）。

#### ⚠ 这一节是**排查手册**，不是"部署后要执行的步骤"

**正常部署完不做任何验证**（见上面「部署完就结束」）。下面这些只在
**已经出现"改了没生效"的怀疑时**才用 —— 也就是 §十一 的排查场景。

##### `grep -a xxx AgentLoopServer.exe` 一定搜不到，但不代表没打进去

exe 里的 `.py` 被编译成字节码、放进压缩归档（PYZ），所以明文搜不到是**预期**。
只有在真的怀疑"没打进去"时才解包：

```python
# 用打包 venv 里的 Windows python 跑
from PyInstaller.archive.readers import CArchiveReader
import marshal, types
r = CArchiveReader(r'E:\...\ModAssets\AgentLoopServer.exe')
pyz = r.open_embedded_archive('PYZ.pyz')
code = marshal.loads(pyz.extract('agent_loop.session.history'))
# ⚠ 必须深挖嵌套 tuple：字典字面量的键在 co_consts 的 tuple/frozenset 里，
#   只看 co_names 会漏（第一次就是这么误判成"没打进去"的）
```

> 这段留着的价值是"排查时知道怎么查"，**不是**"每次部署都要跑一遍"。
> 两者混淆过一次：把排查手法当成常规步骤，每次部署多花几轮工具调用，
> 而结论从来都是"确实打进去了"。

#### 一个反直觉的坑：参数被接受 ≠ 新代码在跑

实测案例：`open_chat` 传 `limit=20` 返回 69 条，我据此判断"新代码生效了"——**错的**。
`limit` 是旧代码就有的参数，旧 exe 也会返回 69 条，只是**不返回新增的
`next_before_seq` 键**，于是 C# 解析成 0、判定"已到顶"、功能静默不出现。

> **判据必须是"新增的东西出现了"，不是"旧行为还在"。**
> 改协议时尤其要盯**新字段**，不能盯**新参数**。

## 五、代码约定

### 注释写"为什么"，不写"做了什么"

```csharp
// ✗ 没用：代码已经说了
// 遍历 keys 并调用 Stop

// ✓ 有用：这个决定背后有代价
// 为什么必须主动 Stop，而不是等场景销毁：真机上 `Destroy ok` 之后体检表还在继续打，
// 说明"帧回调随场景销毁"这个假设压根没验证过。详见 docs/archive/2026-11-19-常驻帧回调句柄化.md
```

**每个"看起来可以更简单"的地方，都欠一句解释。** 否则下一个人会把它简化回去，
然后重演同一个事故。

### 注释的边界：过程进文档，代码只留"为什么"

**只约束新写的代码。存量不清。**

| 内容 | 该在哪 | 代码里留什么 |
|---|---|---|
| 真机日志逐行解读、时间线 | `docs/archive/` | 一行指针 |
| 被推翻的假设、"第 N 次尝试" | `docs/archive/` | 一行指针 |
| 反编地址、字段偏移、分派路径 | `docs/reference/` | 一行指针 |
| 改动沿革（"09-22 从 X 泛化而来"） | 归档 或 `CHANGELOG.md` | 一行指针 |
| **这个反直觉决定的原因** | ✅ 留代码 | 完整写 |
| **这个常量为什么是这个值** | ✅ 留代码 | 完整写 |
| **这个顺序为什么不能换** | ✅ 留代码 | 完整写 |
| **这里静默失败过，别改回去** | ✅ 留代码 | 完整写 + 文档指针 |

**判据只有一个：把这段注释删掉，代码还能不能改对？**

- 能 → 它写的是过程，**搬走**，留一行 `// 详见 docs/archive/xxx.md`
- 不能 → 它写的是约束，**留下**，写多长都行

**不设行数上限。** 一段注释 40 行但全是"为什么不能这么改"，是好的；
10 行但全是"我那天试了什么"，是坏的。**看内容，不看行数。**

```csharp
// ✓ 合格：说的是"为什么不能改"
// 为什么必须先记页再收口：收口要读 [锚点, 现在] 的区间，先收口就缺那一行。
// 顺序钉在 DramaAiOption 里，动它之前先读 docs/features/npc-duel.md §4。

// ✗ 不合格：讲的是"09-22 那天发现了什么"
// 09-22 第一次改成 X，跑了一局发现 Y，于是又改回 Z，第二次…
```

**禁止新写这类注释**：日期开头的叙事（"09-23 改动如下"）、
"原设计是 X，那条拍板前提是错的"、多行 ASCII 时间线、`Player.log` 行号摘抄。
这些**全部**进 `docs/archive/YYYY-MM-DD-<事>.md`。

### 旧代码：不清，也不要顺手"整理"

本仓有 700+ 处超过 8 行的注释块，大量是历史叙事。**明确决定：不清。**

- **不做批量清理** —— 耗时、会碰并行开发的文件、且删错一条承重约束的代价远大于省下的行数。
- **也不"顺手整理"** —— 改功能时不要顺带把旁边那段历史注释删掉或重写。
  它可能正解释了"为什么这里是这个形状"，而你没时间验证。
- **例外**：你确认它已经**说错了**（比如指向了不存在的文件、描述的机制已被删除），
  那就改对——**写错比写长更糟**。

### 禁止出现的形状

| 形状 | 为什么不行 | 改用 |
|---|---|---|
| 用**全进程一次的布尔**守"每世界都要重做"的动作 | 守卫寿命比被守的东西长 ⇒ 重载后永远不重做，且无日志 | 存**句柄** + 帧号心跳（`FrameTicker`） |
| 裸 `g.timer.Frame(体, 1, true)` 不接返回值 | 每进一次世界叠一份、`Destroy` 撤不掉（实测 2.00 次/帧） | `FrameTicker.Ensure(键, 名, 体)` |
| `On` 订阅了不退订 | `EventsMgr` 是列表，只加不减 ⇒ 同一处理器被调多次 | `Destroy` 里 `Off` + `Init` 里注册前先 `Off` |
| `x as RectTransform` | 类型不匹配时**静默返回 null**（已翻车三次） | `UiRects.Of(...)` / `GetComponent<RectTransform>()` |
| 后台线程碰 `UnityEngine` | IL2CPP 非主线程 interop 原生崩溃 | `ModMain.P`（内部按线程分流） |

### 日志

- 主线程 → `UnityEngine.Debug.Log` → `Player.log`
- 后台线程 → `Console.WriteLine` + `MelonLoader/Logs/AgentLoopBridge-thread.log`
- 统一走 `ModMain.P(...)`，**不要**直接调 `Debug.Log`
- 一行要说清"发生了什么 + 依据是什么"。`[BusyWatch] 进忙` 不够，
  要带原因和原始电平（否则现场无法复盘）

### Python 侧

- docstring 用"一句话 + 为什么"，**不写设计长文**（同样搬 features/reference）
- `storage/images.py` 文件头那种 ~20 行是**上限的样板**，不是起点

```
AGENTS.md            ← 入口页（三分钟读完）
README.md            ← 项目总览（给用户）
docs/
├── README.md        ← 文档索引（五层分工一张表）
```

### 五层各写什么

| 层 | 回答 | 该有的 | 不该有的 |
|---|---|---|---|
| `features/` | **现在**怎么工作 | 一句话摘要、主链路、不变量、相关代码 | 排查过程、被推翻的假设、日期 |
| `reference/` | 这个字段/表/函数是什么 | 表格、地址、签名、取值 | 结论性建议 |
| `archive/` | 当时**怎么**查出来的 | 过程、被推翻的结论、时间线 | 现状描述（现状归 features） |
| `journal/` | **正在**做什么 | 边做边记 | 定稿内容 |
| `CHANGELOG.md` | 什么时候做了什么 | 追加条目 | 长篇分析 |

**唯一标准：三个月后的人能不能据此判断"这东西靠不靠得住"。**

### 命名规则

- **`archive/` 与 `journal/` 的子条目一律日期开头**：`YYYY-MM-DD-功能名`
- 一件事写一份 → `<日期>-<事>.md`；一件事写多份 → `<日期>-<事>/` 目录
- 目录内文件名用**描述性中文**，不用 `01-` `02-` 编号
  （除非文件之间有**真实的阅读顺序**，如 `草案 → 定稿 → 计划`）
- `features/` `reference/` 用功能名/主题名，不加日期

### 文档不许出现的东西

- **裸的过期状态行**（"状态：待真机验收"）—— 状态归 `CHANGELOG.md`
- **断链** —— 移动文件后必须全量校验一遍相对链接
- **"待补充""TODO"** —— 要么写，要么不写

## 九、并行开发须知

- `git status` 里**未跟踪**的 `csharp/**`、`agent/**` 文件可能是别人正在写的，
  **不要删、不要格式化、不要"顺手整理"**。

## 十一、出事时的排查顺序

> **这一节只在"已经出事了"时用。** 正常部署完就走开（见 §四「部署完就结束」）——
> 不要为了防止"万一没生效"而提前把这里的步骤跑一遍。

1. **确认跑的是新代码**
   - **C#**：`[Build]` 那行的"写入 vs 进程启动"判定（它只认 DLL）
   - **Python**：`[Build]` 对它**无效**（exe 是另一个文件）。看 **exe 时间戳**，
     或看**日志里有没有你新加的字段/文案**。⚠ "旧参数照样被接受"**不能**当证据，
     详见 §四「Python 侧」第 ③ 条
2. **确认挂钩上了**：各组件安装时会打 `InstallReport`（挂不上也会打，不是静默）
3. **确认 tick 在跑**：`常驻帧回调（60 帧后）：… idle=N`，个位数才正常
4. **看量值对不对**：`[TickProfiler]` 每 5 秒一行，`n` 与 `帧=+N` 应当一比一
5. **再读业务日志**

前三步能排掉绝大多数"改了没反应"。

### 12.2 只在收尾做的事

```bash
python3 -m pytest tests/ -q                      # 全量 2222 条，约 2.8 分钟
python3 scripts/dev/run_csharp_tests.py          # 29 个 C# 工程
python3 scripts/dev/run_tests_for.py --probe     # 重采测试快照
```

平时**不做**这三件。

### 12.3 三条铁律

1. **没真机读数的结论不写进护栏。**
   这是本仓踩过最多次的坑：按推测写的判据在真机上全部失效，还挡住了真正的修法。
   没读到就写"未验证"，等读到了再写护栏。

2. **文档里不许留"待验证"状态行。**
   要么在 `CHANGELOG.md` 的未验证段落写清"验证什么、怎么验"，
   要么标上日期和"之后发生了什么"。裸的"状态：待验收"三个月后就是垃圾。

3. **提交前 grep 一遍临时物。**

```bash
grep -rn 'TODO\|FIXME\|临时\|PROBE\|XXX\|调试用' \
     --include='*.cs' --include='*.py' csharp/ agent/ room/ tools/ | grep -v tests/
```

### 12.4 收尾报告模板

给用户的最后一条消息必须包含这四块：

```
## 改了什么
<按模块列，不按文件列>

## 验证到哪
- 单测：N 条全绿（列出新建的契约测试）
- 真机：<读了哪行日志、值是多少>
- 构建：md5 <值>，三处一致（部署命令的输出即证据，不再另行核对）

## 没验证的
<明确列出。没验证就说没验证，不要含糊过去>

## 下一步需要你做的
<重启游戏 / 点一次某功能 / 导出配表 / 改版本号>
```

**"验证到哪"和"没验证的"缺一不可。** 只报好消息的收尾，
等于把"不确定"留给下一个人。
