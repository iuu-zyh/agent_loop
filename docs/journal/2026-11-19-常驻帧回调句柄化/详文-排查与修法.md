# 排查与修法（过程记录）

## 起因

真机 11-19 01:09：NPC 传功被排进「此间事了」队列，此后**队列再也不执行**。
玩家一直催，模型一直按"已受理、等待中"答复，日志里一个字的异常都没有。

## 根因

驱动队列的那条**每帧回调**已经不存在了。`g.timer.Frame(...)` 的登记在世界重载
（回主菜单 / 读档 / 换档）时会被清掉，而代码用 `_tickRegistered` 这个**全进程一次**的
布尔去防重复登记 ⇒ 重载后仍然"记得挂过" ⇒ 永远不再重挂。

**守卫的寿命（全进程）比它守的东西（每世界的帧登记）长** —— 这是形状，不是个例。

## 先走错的路

一开始看到日志里 `WorldMgr:IntoWorld()` 出现 3 次，判断"事件触发了 3 次"。
**那是误判** —— 那是**栈帧装饰**，每打一条日志就带一整串：

```
WorldMgr:IntoWorld()
<>c__DisplayClass22_3:<OnCacheItemClick>b__12()
CallQueue:Next()
TimerCoroutine:Run()
...
```

正确判据是**数副作用条数**：`OnIntoWorldEvent` 里有 6 处会打日志，
逐个数它们出现的次数。

## 全仓扫描（这次事故的副产品）

按"守卫寿命 vs 被守对象的寿命"扫了全仓 30 处布尔守卫，结论：

- **10 处带生命周期敏感的副作用**，其中 6 处是裸 `g.timer.Frame` 注册
- 24 处是安全的（守 Harmony 补丁、一次性加载、我们自己的静态事件 —— 这些确实活到进程结束）

迁移掉的 8 个键：`disp` / `npcmon` / `brainlink` / `hotkeys` / `diag` / `prober` /
`mapbtn` / `banner`，加 `npcduel.diag`。

## 差点踩进去的坑：owner

`Init` 每次进世界都 `new MainThreadDispatcher()` / `new NpcInitiativeMonitor(...)`，
帧回调是**实例方法**。若 `Ensure` 只按句柄判活，重跑 `Init` 时会看到"句柄在、还活着"
⇒ 什么都不做 ⇒ 帧回调永远跑在被 `Dispose()` 掉的旧实例上。

后果比"少跑点东西"严重得多：主线程调度器停摆 = **Python 的每一次工具调用都超时**
（全部经 `_dispatcher.Enqueue` 派到主线程），而日志显示一切正常。

所以 `Ensure` 加了 `owner` 参数，用 `ReferenceEquals` 判引用；换实例时撤旧挂新。

## 事件订阅那半边

同一次扫描发现 `Destroy` 里只 `Off` 了 `WorldAddDay`，`SaveData` / `IntoWorld`
从来没退订过。而 `EventsMgr` 的订阅是按事件名存表、派发时全部调一遍 ⇒ 只加不减。

真机证据：会话 3/5 各出现**两次** `OnIntoWorldEvent` 的完整副作用链
（6 处条数一比一，且第一次清 3 条立绘、第二次清 0 条 = 顺序执行的空转）。

修法：`Destroy` 里补 `Off` + `Init` 里注册前先 `Off`（防"只 Init 不 Destroy"的段）。

## 遗留

`NpcDuel` / `TeamBattleFollowup` 的 `g.events.On(BattleEndFront/BattleExit)`
仍由 `_installed`（全进程一次）控制。**这个是对的** —— `g.events` 订阅不随世界销毁，
反而会累积，所以那两处需要防重复而不是防失效。（订正了先前"订阅会随场景销毁"的错误判断。）
