## 二、中间走过的两次错，以及为什么错

### 错① 按「一个工具一个类」切 → 20 个文件

第一版严格照工具名切：`InspectTool` / `SearchTool` / `WorldQueryTool` / `MovementTool` /
`WorldActionTool` / `TradeTool` / `TeamCallTool` …共 20 个。问题：

* 文件壳 **+220 行**（每份 4 个 using + namespace + class + 花括号），
  跨类限定 **318 处**（`ToolArgs.` 92、`IntimService.` 65…），而逻辑一行没少；
* `TeamCallTool`（130 行）根本不是一类，它只是 `TeamTool` 的参数适配器；
* `SearchTool`（141 行）单独成类的价值低于它的文件壳；
* 宗门被按"查/改"劈成两个文件，但改"入宗"时要同时看名册和写入两边 —— **那是同一个域**；
* `movement` 与 `world_ai_action` 判据同源（同格、确认窗、返回码），却被分开。

**教训**：切分维度必须是**职责**，不是**入口名**。一个入口 ≠ 一个类。

### 错② 为了"省行数"把不相关的东西并一起

第二版试图把 20 个收到 12 个，其中三处是**按行数凑的**：

| 错误合并 | 实际关系 |
|---|---|
| `PropsService` → `IntimService` | 好感代码与背包/灵石**互调 0 次**；只有 `EconomyTool` 23 处、`AcquireTool` 17 处在用 |
| `GameText` → `ToolArgs` | 调用者全是查询侧（`QueryTool` 9、`SectQueryTool` 12） |
| `MartialService` → `NativeActionService` | 唯一调用者是 `chuan_gong` 的 5 处 |

`IntimService` 那条尤其有害：并进去会让人以为"送东西改好感"和"搬灵石"共用判据，
而它们没有 —— 以后改好感写入层时，背包回滚会被无辜牵连。

**教训**：合并的依据只有两条 ——「**同一个判据**」或「**只有这一家使用者**」。
不是"都是通用件"，更不是"行数差不多"。

### 最终形态

`PropsService` / `IntimService` / `NativeActionService` 各自独立；`GameText` 并进 `QueryTool`；
`MartialService` 并进 `ActionTool`；`SectQueryTool` 单独一个文件（并进 `QueryTool` 会变成 1830 行，
比原来的大文件还难翻）。

## 三、唯一收掉的重复：`ToolArgs.BindActor`

六个动作工具（关系 / 位移 / 互动 / 赠予 / 取得 / 组队）开头这七行**逐字相同**：

```csharp
string initiator = (string)args["initiator"] ?? "";
var wub = ResolveActor(args);
if (wub == null)
{
    string dn = UnitSnapshot.DeadNotice((string)args["initiator_id"] ?? "", initiator);
    if (dn != null) return Fail(dn);
    return Fail("未找到发起方 " + initiator);
}
```

收成一行：

```csharp
var wub = ToolArgs.BindActor(args, out string initiator, out JObject bindFail);
if (bindFail != null) return bindFail;
```

为什么值得收：这句话是**给模型看的**。措辞不一致它就会按不同的错去自纠 ——
"名字打错"（该重查）和"人已死"（该换人）是两条完全不同的路。以前改一处，另外五处不跟着改。

**为什么不用基类**：没有多态需求（每个工具一条直路，永远不需要基类指针虚分派）；
net472 + C# latest **没有静态抽象成员**，用基类就得把成员从 `static` 改成实例方法、
配单例、改所有调用点 —— 为省 90 行引入一层继承和一套实例化约定，不划算。
函数式收口达到同样效果，零继承成本。

## 四、保真度怎么验的

拆/并都按**花括号配平**切成员（连同紧贴其上的注释块、以及夹在两个成员之间的分节横幅），
然后做**代码行多重集比对**：原文件与新文件的代码行去掉注释/空白/修饰符/类名前缀后
`Counter` 相减。

* 第一次拆（1 → 20）：**丢失 0 行**
* 归并（20 → 13）：丢失 0 行（差额全是文件壳）

这比"编译过了"强：编译只证明能跑，它证明**没有哪一句被顺手改了**。

搬移中暴露的三处（都不是逻辑改动）：

* 原文件第 6481 行有个**悬空的 `/// <summary>`**（`UnitNameById` 被删后留下的）；
* `FateText` 上方有同类孤儿 doc 注释（写的是"unitID → 中文名"，正是被删的那个函数）；
* 三处注释里的"本文件 1534-1573"（指裁决码表）改成"`RelationTool.cs` 里的裁决码表"。

唯一的语义改动：`ToolExecutor.ApplyIntim` → `IntimService.ApplyIntim`（2 个外部调用点），
函数体一字未改。

## 十、复核时删掉的过度防御（这一轮真的动了代码）

结构优化不只是搬文件。复核时逐条问"这条兜底有没有可能发生"，确认多余的就删：

| 删掉的 | 为什么多余 |
|---|---|
| `ToolArgs.NameOfUnit(u, fallback)` | 一行委托 `UnitIdentity.Name`，7 个调用点全改成直接调 —— 少一层跳转，也少一个"两处都能改"的地方 |
| `ToolArgs.IntOf(JToken)` | 只有 1 个调用点（榜单排序），语义与 `SafeInt(t, 0)` 完全相同 |
| 4 处 `try { target = wub.data.unitData.propertyData.GetName(); } catch { target = initiator; }` | 手写版 `UnitIdentity.Name(u, fallback)`，而且原版在**抛异常**和**返回 null** 两种情况下行为不同（前者用 initiator、后者用 null）—— 收敛后两种都退回 initiator，是原来想要的那个语义 |
| `Execute(name, args, npcId)` 里两次 `IsActionTool(name)` | 同一个入参调两遍；提成局部变量 `isAction` |

**没有删的**（查过，不是过度防御）：

* `IntimService.IntimBetween`（读不到返回 **-1**）与 `ToolArgs.GetIntimBetween`（返回 **0**）——
  看着像重复，实际**语义不同**：前者是"未知"哨兵（`NativeActionService` 靠它算 `Δ`，
  并在 `PutIntim` 里过滤 `int.MinValue` 不写进结果），后者是"给结果字段一个数字"。
  合并会把"未知"和"零"混成一个。两处各自有测试（`test_unknown_delta_never_leaks_into_result_fields`）。
* `TeamTool.IsPlayer`（指针兜底）/ `UnitSnapshot.IsPlayerUnit`（名字兜底）/ `ToolArgs.IsPlayerUnit`
  （纯指针）—— 三份确实不同，`TeamTool` 文件头写着为什么不能换。这属于"需要单独拍板"的一条，
  不在本轮范围。
* `ToolExecutor.IsOk` 的 `try/catch` —— `res["success"]` 在 `JValue` 上会抛，不是多余。

## 十二、为"改动是否生效"加的日志（11-20 傍晚，用户要求）

拆分的风险不是崩溃，是**看起来一切正常**：旧 DLL 能跑、新 DLL 也能跑，日志长得几乎一样。
所以要两行**运行时事实**，而不是又一句手写文案。

### 12.1 `[ToolLayer]` —— 启动时一行，证明这份 DLL 里真有这 13 个类

```
[ToolLayer] 工具层 13 类（13 在册）：ToolExecutor ToolArgs QueryTool SectQueryTool RelationTool
            MovementTool ActionTool EconomyTool AcquireTool TeamTool IntimService PropsService
            NativeActionService｜分发 10 个工具名
```

做法是 `Assembly.GetType("AgentLoopBridge." + 类名, false)` 逐个查，**不是打印一句话**：

| 情况 | `[Build]` 手写戳 | `[ToolLayer]` 反射 |
|---|---|---|
| 部署了旧 DLL | 照样说"新版"（分不出） | 缺类 → `★旧 DLL 或编译没带上★` |
| csproj 漏了新文件 | 照样编译过、照样打印 | 同上，缺项点名 |
| 类被改名 | 无感 | `｜缺失：XxxTool` |

缺类时那一行会明确写出缺哪几个，并点名最可能的原因。这就是为什么它必须 `GetType` ——
一个只拼字符串的版本在"没生效"时**照样说 13 个都在**，那正是要避免的假阳性。

### 12.2 `[Tool]` —— 每次调用一行，带落点文件

```
[Tool] inspect_unit 3ms ok → QueryTool.cs
[Tool] query_world 41ms ok → QueryTool.cs        ← topic=sects 时另有 [Sect] 行
[Tool] economy_item 812ms FAIL「背包中没有，可先 inspect_unit(classes=inventory)」 → EconomyTool.cs
```

四个要素：工具名 / 耗时 / 成败 / **落到哪个文件**。落点文件名是"新分层真的在跑"的直接证据 ——
拆分前所有工具都在同一个文件里，那个信息根本不存在。

写在 `finally` 里，所以三条出口都覆盖：正常返回 / 抛异常 / `__pending__` 模态挂起。

### 12.3 顺带补的四处（原先**成功路径上完全静默**）

| 前缀 | 位置 | 补的理由 |
|---|---|---|
| `[Props] 灵石转移` | `PropsService.TransferLingshi` | 唯一真的动钱的函数；出事后原本只能靠余额差反推 |
| `[Props] 拆栈` | `PropsService.TakePropsFromBag` | "道具离手"的唯一时刻；之后哪条路吞了都看不出它出来没有 |
