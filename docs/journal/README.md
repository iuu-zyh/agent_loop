# 开发日志（journal）

> 本目录是**过程记录**，不是"现在是什么样"。
> 想知道**某个功能当前怎么工作**，去 [`../features/`](../features/)；
> 想知道**某个结论是怎么来的**，才来这里。

---

## 一、这套东西怎么用

开发分**三段**，每段落在不同位置：

```
① 开工  →  journal/YYYY-MM-DD-功能名/     新建子文件夹，边做边写
              ├── README.md               概要：做什么、为什么、结论（长期保留）
              └── *.md                    过程详文：真机时间线、走过的弯路、被推翻的假设
                                                          │
② 完工  →  archive/journal/YYYY-MM-DD-功能名/    详文移到这里（保留原文），
                                            子文件夹只留 README.md，薄成"一句话索引"
                                                          │
③ 沉淀  →  ../features/功能名.md              有长期价值的结论升格成"现在是什么样"
           ../archive/            ←──────  过程（按日期开头，见 archive/README.md）
```

**`journal/` 这一层只装"带日期的进行中子文件夹"。** 不放 `archive`、不放散文件
（除了本说明 `README.md`）。完工的东西一律离开 `journal/`，去 `docs/archive/journal/`。

### 为什么"完工要归档"

一个子文件夹做到最后常有 5~10 篇文档，其中**九成只对当时当事人有用**：
第 3 次推翻假设的推理、某条日志的逐行解读、临时探针的输出现场。

留着的代价是真实的：下次接手的人要在一堆过程稿里找"到底哪个结论算数"，
而过程稿之间往往**互相矛盾**（那是正常的 —— 后一篇推翻了前一篇）。
不标清楚，读者会把已经被推翻的结论当成现状。

所以：**归档保留原文，但把"当前的答案"收敛到 `README.md` 一处。**

## 二、子文件夹命名

```
journal/2026-11-19-常驻帧回调句柄化/
journal/2026-11-20-工具层拆分/
```

规则：

| 项 | 要求 | 理由 |
|---|---|---|
| 日期 | `YYYY-MM-DD`，开工那天 | 按时间排序即优先级顺序 |
| 内容 | 2~6 个汉字，动词+对象 | `常驻帧回调句柄化` 比 `frame-ticker` 可读 |
| 不用英文 | 除专有名词 | 本仓库文档一律中文，检索时不必中英两头找 |

## 三、`README.md`（每个子文件夹必须有）

完工之后它是这个文件夹里**唯一**该被读的文件，所以只写四块：

```markdown
# 2026-11-19 常驻帧回调句柄化

## 一句话
把"全进程一次的布尔"换成句柄表，让帧回调在世界重载后能自愈重挂。

## 结论（现在的状态）
- 8 个常驻 tick 全部经 FrameTicker，Destroy 时 StopAll
- 每帧只跑一份（Once 去重）
- 详细见 docs/features/frame-ticker.md

## 关键证据
- 真机日志：deferq 恒 1.00 次/帧，裸注册的从第 3 段世界起恒 2.00

## 详情
已归档 → ../../archive/journal/2026-11-19-常驻帧回调句柄化/
```

**不要**把这四块写成散文。它的读者是三个月后想快速确认"这东西现在靠不靠得住"的人。

## 四、过程详文该写什么

不是流水账。值得写下来的只有三类：

**① 真机事实**
> 20:25 那份 Player.log 里，`mapbtn` 只在第 1、2 段世界出现（各 1.00 次/帧），
> 第 3 段起彻底消失，再也没回来。

**② 走过但确认不通的路**（最有价值，能省下一个人两天）
> 曾想把 `WorldMgr:IntoWorld()` 的行数当调用次数 —— 那是**栈帧装饰**，
> 每打一条日志就带一整串。判据应改用副作用条数。

**③ 被推翻的自己的判断**
> 先前说"`g.events` 订阅会随场景销毁，所以 `_installed` 会永久失效"。
> 方向反了：实际是订阅**不会消失、反而累积**。

①③ 对读的人最有用的地方在于：**它们让"不要重走这条路"变成可执行的信息**，
而不只是"前辈说这条路不行"。

### 不要写

- 逐条罗列改了哪些文件（`git log` 已经有了，且更准）
- 复述代码注释（注释就在代码里，会一起改）
- "本次优化提升了性能"这类没有量值的结论

## 五、归档动作（完工时）

```bash
# 1) 详文移进 archive，保留同名文件夹（便于对照）
mkdir -p docs/archive/journal/2026-11-19-常驻帧回调句柄化/
mv docs/journal/2026-11-19-常驻帧回调句柄化/*.md \
   docs/archive/journal/2026-11-19-常驻帧回调句柄化/

# 2) 把 README.md 留下并改薄（留住上面那四块）

# 3) 若结论有长期价值，升格成 docs/features/<功能>.md，并在 README 里指过去
```

## 六、归档去向（别搞混）

`docs/` 下只有**一个** `archive`，就是 `docs/archive/`。它里面按"是什么"分层：

| 路径 | 装什么 |
|---|---|
| `docs/archive/journal/` | **开发日志的归档**：完工的 `<日期-功能名>/` 子文件夹 |
| `docs/archive/<日期>-<事>.md` | 一件事写一份（事故复盘、体检、单份调研） |
| `docs/archive/<日期>-<事>/` | 一件事写多份（设计 + 计划 + 进展） |

`journal/`（无 archive 后缀那个）**只放进行中的子文件夹**。

## 七、历史记录

`docs/archive/journal/` 下另有 2026-09 那批逐日开发记录（9 篇，原 `.workbuddy/memory/`）。

它们**没有**按上面这套"子文件夹 + README"组织 —— 那是逐日流水，不是按功能切分。
作为历史资料原样保留，检索时按日期找即可。`MEMORY.md` 是当时的索引。

> ⚠ 这批文档里出现的 `.workbuddy/binaries/...` 之类路径是**当时开发机**的位置，
> 现在已不存在。只当历史看，不要照着它去配置环境。
